## 1. 企业要什么知识：本体、语义、记忆？

### 1.1 企业为什么必须有知识

**同样的数据、同样的工具，交给不同的人，结果往往不一样。**

业务提出一个需求："统计本月新车销量"，三个人给出三个答案：

| 执行人 | 结果 | 差别在哪里 |
|---|---|---|
| 小王 | **12,860 台** | 统计口径不同 |
| 小李 | **10,415 台** | 统计时间不同 |
| 小孙 | **8,972 台** | 用的表和去重字段不同 |

要得到正确结果，还需要知道三件事：

- **销量口径**：销量如何统计——包括哪些订单状态？是否剔除取消单、测试单？
- **统计时间**：按下单时间还是完成时间统计？
- **可信数据**：哪张表可信？应该按什么字段去重？

由此引出全书最基础的一组定义：

> **数据**：记录业务发生了什么。
> **知识**：帮助我们理解数据，并决定如何行动。

> 【金句】**这些定义、规则、判断方法和经验，就是企业运行所依赖的知识。**


---

### 1.2 为什么这些知识需要沉淀下来

企业需要把知识沉淀下来，主要有三个原因：

| # | 痛点 | 说明 | 沉淀带来的价值 |
|---|---|---|---|
| 01 | 反复找人确认 | 每次遇到问题都要找人确认，经验难以复用 | 跨人员复用 |
| 02 | 团队理解不同 | 不同团队各自理解，同一业务产生不同结果 | 跨团队一致 |
| 03 | 业务经验断层 | 人员离开或岗位调整，业务经验难以延续 | 跨时间延续 |

到了 **Agent 时代，这个需求更加直接**：

> **模型通用能力 + 企业业务知识 → 完成企业任务**

例如：不知道"有效订单"的定义，模型即使生成了能执行的 SQL，也可能回答错问题。

> 【金句】**模型具备通用能力，但完成企业任务，还需要企业自己的业务知识。**


---

### 1.3 行业内的多种做法

行业内存在多种知识建模路线，可以排成一条"保证换自由"的光谱：

> 强保证（口径唯一 · 可验证 · 可写回）→ 开放接口（跨工具交换 · 不绑定引擎）→ 高灵活（覆盖广 · 低建模 · 弱保证）
> **每向右一步：用一种保证，换一种自由。**

| 方案 | 建模方式 | 强项 | 局限 |
|---|---|---|---|
| **Palantir Ontology** | 三层建模：属性式对象模型，建设对象、链接、行动三层能力 | 行动能力从表达层深入到运行层，全面性与深度最好 | 垂直领域、高成本的治理闭环，不是开放的起点 |
| **Semantic View 家族** | 属性式对象模型，对象 = 逻辑表（分析语义） | 确定性 + 准确性，查询时编译 SQL | 只针对结构化语义；是主流起点 |
| **Apache Ossie** | 本体层：事实式实体模型，更宽泛；语义层同 Semantic View | 同样确定、准确，且是开放标准，无锁定 | 仍限结构化，本体层刚起步，无运行时；是另一个起点 |
| **Agent Memory** | 情景 / 语义记忆（episodic / semantic） | 自由文本、个体偏好与经验，覆盖广、低建模 | 无 Schema，不承担组织级真值，弱保证 |

> 【核心总结】**不同方案的设计目标和方向不同，因此在不同场景会采用不同的知识建模形态。**

## 2. 企业建设知识的几个痛点

### 2.1 痛点一：知道要做语义建设，却不知道该提供什么信息

两个具体困惑：

- **从哪梳理**：信息散落在报表、文档、代码和群聊里，不知道该先整理哪些。
- **给到什么程度**：给少了覆盖不全；给多了，噪声和互相矛盾的说法会一起混进来。

**信息来源与可信度对照表**：

| 信息来源 | 提供什么 | 可信度 |
|---|---|---|
| 报表 Query | 业务实际在用、被认可的取数逻辑 | 高 |
| 数据资产 Pipeline 加工 | 指标在数据上真实是怎么算出来的 | 高 |
| 指标口径文档 | 已梳理好的定义、统计规则和适用范围 | 高（需确认是否为最新版本） |
| 业务黑话物料 | 内部简称、俗称，如「烧车」「热扩散」 | 中（用于理解提问，需要和数据对上） |

**小例子**：用户问「上周烧车了多少台」。但用户只提供了统计异常车型的口径——Agent 能找到车辆信息，但不知道「烧车」是什么，最后随意猜了一个车型名称很像的类别的车。

> 【要点】**信息给对、给全，语义才建得准：用报表、Pipeline、口径文档给出算法，用业务物料补齐业务说法。**


---

### 2.2 痛点二：知识很多，同名指标，口径各不相同

以车企的"新车销量"为例，相关定义分散在业务文档、数据加工管道和报表查询中：

| 来源 | 口径原文 / 逻辑 | 结果 |
|---|---|---|
| **业务文档** | 新车销量指当月签订购车合同的订单数量 | 本月新车销量 **12,860 台** |
| **数据加工管道** | COUNT(order_id) WHERE 已付定金且未退订 | 本月新车销量 **10,415 台** |
| **历史查询** | COUNT(DISTINCT vin) WHERE 交付日期在本月 | 本月新车销量 **8,972 台** |

**同样叫"新车销量"，为什么统计结果不同？哪个才正确？**

这些口径可能分别用于衡量**订单获取、有效订单和实际交付**，也可能存在定义更新后文档未同步、加工逻辑遗漏等问题。

> 【要点】**仅凭名称和片段内容，无法判断哪个口径正确。**


---

### 2.3 痛点三：不同角色之间关注视角与 Agent 全链路理解的 Gap

跨部门协作时，双方需要建立**业务定义与数据实现的对应关系**，但视角天然不同：

| 角色 | 关心什么 |
|---|---|
| **业务** | 业务逻辑对不对，背后有没有数据支撑 |
| **数据** | 语义全不全，口径对不对，数据可不可信 |
| **Agent** | 从业务问题走到指标口径 |

**案例：成功率 98%，为什么「远程开空调没反应」是客诉 Top 3？**

用户点一次「开空调」的全链路（数字为示意）：

| 步骤 | 环节 | 流转 | 流失 |
|---|---|---|---|
| 1 | 平台校验 | 1000 → 850 | 流失 150（**数据看不到**） |
| 2 | 唤醒车辆 | 850 → 750 | 流失 100（**数据看不到**） |
| 3 | 下发指令 | 750 → 750 | — |
| 4 | 车端检查 | 750 → 750 | — |
| 5 | 执行返回 | 750 → 735 | 流失 15（**数据口径覆盖内**） |

于是出现两个完全不同的答案：

> **数据口径**：735 ÷ 750 = **98%**
> **用户感受**：735 ÷ 1000 = **73.5%**

**根因**：本体里写明该车型部分配置款不支持远程开空调，但 APP 照样显示按钮，用户点了就在平台校验被拦截。

> 【要点】**不同角色关注点有差异，但特定场景下只有两者结合，Agent 才能从「是多少」答到「为什么」。**

## 3. 知识工程产品能力介绍

### 3.1 云器知识工程产品架构

产品分三层，自下而上：

| 层级 | 组成 | 说明 |
|---|---|---|
| **数据底座** | 云器 Lakehouse 数据底座 | 湖仓一体、增量计算、AI ETL、Studio 开发组件 |
| **知识引擎（核心产品能力）** | SingKnowledge：统一知识整合、建模与消费 | 知识接入：文档、查询 SQL、开发链路等多源数据；知识蒸馏：意图选择、抽取转化、归并与质量评估并产出知识模型；知识的管理：提供本体概念图、语义视图、mapping 映射等多重视角管理 |
| **Agent 应用与服务** | 云器自有 Agent + 企业自有 Agent | Data Agent（数据开发链路 Agent）、Analytics Agent（数据分析产品 Agent）；企业自有 Agent 可对接现有智能应用 |


---

### 3.2 核心能力一：知识接入

**核心原则**：一个来源里常混着多类知识，按分类识别、拆分；接入后先评估质量。

**知识分类与常见来源**：

| 知识分类 | 常见来源 | 至少要包含 |
|---|---|---|
| 报表 Query | 报表 / BI 系统 | SQL，以及对应的报表名和指标名 |
| Pipeline 加工 | 数仓 / 调度平台 | 加工 SQL 和上下游表 |
| 业务文档 | 业务 Wiki、本地文件、报表附带的指标说明 | 口径定义、统计规则、流程与约束，带版本或更新时间 |
| 业务黑话 | 业务 Wiki、本地文件 | 词条及其对应的业务含义 |
| 本体模型 | 已有本体文件（OWL / OSSIE YAML） | 对象、关系和约束的定义 |

**评估维度**：覆盖度 · 完整度 · 可对齐 · 时效性 · 噪声——输出总分、问题清单和补充建议；低于阈值时先补充，再开始建设。

**示例**（接入销售域业务 Wiki，数字为示意）：

- 识别出：口径文档 **8 篇**、黑话 **30 条**、流程 **3 篇**
- 时效性：**2 篇**口径文档一年多未更新
- 可对齐：「大定」对应不到订单表字段
- 建议：补充销售日报的报表 Query

> 【要点】**来源再多，也先识别成清楚的知识分类，并评估质量，语义建设的输入才可靠。**


---

### 3.3 核心能力二：知识蒸馏 ⭐

**定位**：将多源信息转化为可信知识。

**Raw——一份业务文档里的两段话**：

> 《业务需求》"GMV：用户下单成功的商品金额合计，按下单时间统计。"
> 《2025 Q3 口径勘误》"GMV 自 Q3 起剔除退款，改按支付时间统计；报表里的成交额即 GMV。"

**SQL**：`SUM(dgmv) … WHERE is_test_seller = 0`

**大模型抽出三条候选——还不是知识**：

1. GMV = SUM(金额)，按下单时间
2. SUM(金额) − 退款，按支付时间
3. 别名：成交额 = GMV

候选的问题：**互相冲突；没有绑定到表和列；没有证据编号；不知道哪条还有效** → 还差四步：

| 步骤 | 动作 | 解决什么 |
|---|---|---|
| 绑定 | 表和列 | 候选没有落到具体数据 |
| 裁决 | 哪版有效 | 冲突的说法谁说了算 |
| 校验 | 错了能发现 | 错误可被发现 |
| 发布 | 带版本可追溯 | 可信消费 |

**知识蒸馏五步流程**：

| 步骤 | 内容 |
|---|---|
| **01 抽取** | 从两段话和 SQL 抽出三条候选，每条带来源段落编号 |
| **02 转换** | 归并同名对象；绑定到 dgmv 列；冲突只标不裁；补单位、别名 |
| **03 索引** | 结构化部分进语义视图；原文进全文与向量索引；中英文词桥接 |
| **04 评估** | 金标题库测口径正确率；证据校验确认表列可查；冲突交人工裁决 |
| **05 服务** | 证书 PASS → 语义视图 v+1：GMV = SUM(dgmv)，剔除退款、按支付时间 |

> 【金句】**抽取出来不等于有了知识：绑定、裁决、校验、发布之后，Agent 才能可信消费。**


---

### 3.4 核心能力三：知识管理

**定位**：连接业务含义与数据实现。遵循 Apache Ossie 的语义模型、本体与映射规范，形成三类关联产物：

| 产物 | 面向谁 | 表达什么 | 以车企"新车销量"为例 |
|---|---|---|---|
| **业务本体 Ontology** | 业务人员、领域专家 | 业务术语、对象、属性与关系，统一业务概念 | 业务视角：区分购车订单、车辆、交付等概念，明确"订购"和"交付"的业务含义 |
| **语义视图 Semantic View** | 数据开发、分析人员 | 数据集、字段、维度、指标及关联，明确查询与计算口径 | 数据视角：定义订单数、交付车辆数，以及状态、时间、去重等计算规则 |
| **业务数据映射 Mapping** | 业务与数据协作双方 | 将业务对象、属性和关系映射到语义模型中的数据实现 | 映射视角：建立业务概念与具体数据对象、字段和计算定义之间的对应关系 |

> 【要点】**支持不同用户以熟悉的视角理解知识，同时保持业务概念与数据实现的一致。**

## 4. 产品功能 DEMO

### 4.1 DEMO 背景说明

**数据业务背景**：车主通过手机 App 向车辆下发远程指令（如远程开锁、空调控制等），车辆同时上报状态快照和信号数据，平台对指令执行全链路进行追踪和分析。

**DEMO 内容**：

1. **知识蒸馏**：基于存量的确定性 query 信息，加工成相应的语义资产
2. **基于语义资产的数据开发设计**
3. **基于语义资产的分析消费**

### 4.2 DEMO 一：基于历史的查询信息批量蒸馏

Lakehouse 平台的"语义视图"管理页面：

- 工作空间：bazhwin_test05，共 **1 个 Semantic Views**
- 语义视图：`ev_car_demo`（Schema：cars），表格化管理名称、Schema、责任人、更新时间、描述
- 支持搜索、新增、分页（20 条/页）等管理操作
- 左侧导航含数据资产、集成、开发、知识、知识库、语义视图等模块

### 4.3 DEMO 二：基于蒸馏后的知识产物进行数据建仓

Data Agent 新会话中，用户引用语义视图 `cars/sv_cars_analytics`，用自然语言提需求：

> "基于这个 semantic view，我现在需要一个每日车辆远程控制汇总【日期/重叠周/旬】的看板，做一个车辆驾驶每日汇总，包含每天有多少车在使用控制端，整条表数据如下【核心指标：当日活跃车辆数 / 总设备数 / 成功次数 / 超时次数 / 成功率，P95 / P99 远程平均加载耗时】，设计一个表结构，记录指标和数据加工逻辑。"

- 左侧知识库挂载了"车辆远程控制日汇总""ev_cars_analytics 语义视图""查看当前 schema"等存量知识条目
- Agent 基于语义资产自动完成建仓设计与加工逻辑

### 4.4 DEMO 三：基于蒸馏后的知识产物进行数据查询

在 Cars_Demo 知识库中以自然语言提问：

> "用户感知到的痛，到底痛在哪"

- 系统展示「执行详情」卡片，Agent 逐步执行分析
- 模型选择器、知识库问答与全链路执行过程均可在界面查看
