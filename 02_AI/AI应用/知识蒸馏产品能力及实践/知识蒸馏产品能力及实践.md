## 1. 开场：为什么要学

- **痛点**：同样的数据、同样的工具，交给不同的人，结果往往不一样
- **案例**：业务说"统计本月新车销量"——小王 12,860 台、小李 10,415 台、小孙 8,972 台
- **差别**：不在数据，在知识——销量口径（剔不剔除取消单、测试单）、统计时间（下单 vs 完成）、可信数据（哪张表、按什么去重）
- **定义**：数据 = 记录业务发生了什么；知识 = 帮助我们理解数据，并决定如何行动
- **Agent 时代**：模型通用能力 + 企业业务知识 → 才能完成企业任务；不知道"有效订单"定义，模型生成了能跑的 SQL 也答错问题
- **预热思考题一**：同样叫"新车销量"，为什么统计结果不同？哪个才正确？
- **预热思考题二**：成功率 98%，为什么「远程开空调没反应」是客诉 Top 3？

> 【金句】这些定义、规则、判断方法和经验，就是企业运行所依赖的知识。

- **沉淀三价值**：跨人员复用（不再反复找人确认）｜跨团队一致（不再各自理解）｜跨时间延续（人员离开经验不断层）

## 2. 建审美：4 个案例

### 案例1：小王的"新车销量"——三个答案

- **背景**：车企月度经营分析，业务提数"统计本月新车销量"
- **三个口径**：
  - **小王**：按业务文档——当月签订购车合同的订单数量 → **12,860 台**（衡量订单获取）
  - **小李**：按加工管道——COUNT(order_id) WHERE 已付定金且未退订 → **10,415 台**（衡量有效订单）
  - **小孙**：按历史查询——COUNT(DISTINCT vin) WHERE 交付日期在本月 → **8,972 台**（衡量实际交付）
- **结论**：三种口径可能都对，也可能存在定义更新后文档未同步、加工逻辑遗漏——仅凭名称和片段内容，无法判断哪个正确
- **启示**：同名指标不是知识；带版本、被裁决过口径的指标才是

### 案例2：「烧车」黑话——信息给不全，语义建不准

- **背景**：用户问「上周烧车了多少台」，但只提供了统计异常车型的口径
- **经过**：Agent 能找到车辆信息，但不知道「烧车」是什么，最后随意猜了一个车型名称很像的类别
- **启示**：用报表、Pipeline、口径文档给出算法，用业务黑话物料补齐业务说法——信息给对、给全，语义才建得准

### 案例3：远程开空调——98% 成功率为什么是客诉 Top 3

- **背景**：车企 APP 远程控车功能，数据口径显示成功率 98%，但「远程开空调没反应」是客诉 Top 3
- **全链路拆解**（数字为示意，用户点一次「开空调」）：
  - **平台校验**：1000 → 850，流失 150（数据看不到）
  - **唤醒车辆**：850 → 750，流失 100（数据看不到）
  - **下发指令**：750 → 750
  - **车端检查**：750 → 750
  - **执行返回**：750 → 735，流失 15（数据口径覆盖内）
- **两个答案**：数据口径 735 ÷ 750 = **98%**；用户感受 735 ÷ 1000 = **73.5%**
- **根因**：本体里写明该车型部分配置款不支持远程开空调，但 APP 照样显示按钮，用户点了就在平台校验被拦截
- **启示**：业务视角（逻辑对不对）+ 数据视角（口径全不全）结合，Agent 才能从「是多少」答到「为什么」

### 案例4：GMV 口径勘误——从两段话到一条可信知识

- **Raw**：一份业务文档里的两段话
  - **《业务需求》**："GMV：用户下单成功的商品金额合计，按下单时间统计。"
  - **《2025 Q3 口径勘误》**："GMV 自 Q3 起剔除退款，改按支付时间统计；报表里的成交额即 GMV。"
- **SQL**：`SUM(dgmv) … WHERE is_test_seller = 0`
- **大模型抽出三条候选**：
  - **候选①**：GMV = SUM(金额)，按下单时间
  - **候选②**：SUM(金额) − 退款，按支付时间
  - **候选③**：别名：成交额 = GMV
- **候选的问题**：互相冲突｜没有绑定到表和列｜没有证据编号｜不知道哪条还有效

> 【金句】抽取出来不等于有了知识：绑定、裁决、校验、发布之后，Agent 才能可信消费。

- **结果**：三条候选过完五步流程，最终发布语义视图 v+1：GMV = SUM(dgmv)，剔除退款、按支付时间
- **启示**：LLM 抽取只是第一步；"还不是知识"的判断标准是——冲突未裁决、未绑定表列、无证据、无版本

## 3. 建体系：知识工程三层架构与三大核心能力 ⭐

> 一条主线：多源信息 → 知识接入 → 知识蒸馏 → 知识管理 → Agent 可信消费

### 3.1 行业光谱：用一种保证，换一种自由

- **光谱**：强保证（口径唯一·可验证·可写回）→ 开放接口（跨工具交换·不绑定引擎）→ 高灵活（覆盖广·低建模·弱保证）
- **结论**：不同方案设计目标和方向不同，不同场景采用不同的知识建模形态

| 方案 | 建模方式 | 强项 | 局限 |
|---|---|---|---|
| Palantir Ontology | 对象、链接、行动三层建模 | 行动能力深入到运行层，全面性与深度最好 | 垂直领域、高成本治理闭环，不是开放的起点 |
| Semantic View 家族 | 属性式对象模型，对象=逻辑表 | 确定性 + 准确性，查询时编译 SQL | 只针对结构化语义；主流起点 |
| Apache Ossie | 事实式实体模型，语义层同 SV | 确定、准确，开放标准无锁定 | 仍限结构化，本体层刚起步，无运行时 |
| Agent Memory | 情景/语义记忆（episodic/semantic） | 自由文本、个体偏好与经验 | 无 Schema，不承担组织级真值 |

### 3.2 产品三层架构

| 层级 | 组成 | 内容 |
|---|---|---|
| 数据底座 | 云器 Lakehouse | 湖仓一体、增量计算、AI ETL、Studio 开发组件 |
| 知识引擎 | SingKnowledge（核心） | 统一知识整合、建模与消费：接入/蒸馏/管理 |
| Agent 应用 | 云器自有 + 企业自有 | Data Agent（开发链路）、Analytics Agent（分析）；企业 Agent 可对接现有智能应用 |

### 3.3 能力一：知识接入——按分类识别，接入先评估

- **原则**：一个来源里常混着多类知识，按分类识别、拆分；接入后先评估质量
- **分类**：报表 Query｜Pipeline 加工｜业务文档｜业务黑话｜本体模型（OWL / OSSIE YAML）

| 分类 | 常见来源 | 至少要包含 | 可信度 |
|---|---|---|---|
| 报表 Query | 报表/BI 系统 | SQL + 报表名和指标名 | 高 |
| Pipeline 加工 | 数仓/调度平台 | 加工 SQL 和上下游表 | 高 |
| 业务文档 | 业务 Wiki、本地文件 | 口径定义、统计规则、流程与约束，带版本 | 高（需确认是否最新版） |
| 业务黑话 | 业务 Wiki、本地文件 | 词条及对应的业务含义 | 中（需和数据对上） |
| 本体模型 | 已有本体文件 | 对象、关系和约束的定义 | — |

- **评估维度**：覆盖度｜完整度｜可对齐｜时效性｜噪声 → 输出总分、问题清单和补充建议
- **规则**：低于阈值时先补充，再开始建设
- **示例**（接入销售域业务 Wiki，数字为示意）：
  - **识别**：口径文档 8 篇、黑话 30 条、流程 3 篇
  - **时效性**：2 篇口径文档一年多未更新
  - **可对齐**：「大定」对应不到订单表字段
  - **建议**：补充销售日报的报表 Query

### 3.4 能力二：知识蒸馏五步流程 ⭐⭐

> 五步：抽取 → 转换 → 索引 → 评估 → 服务；候选变知识还差四步：绑定、裁决、校验、发布

| 步骤 | 做什么 | 关键动作 |
|---|---|---|
| 01 抽取 | 从文档和 SQL 抽候选 | 每条带来源段落编号（证据编号） |
| 02 转换 | 归并同名对象 | 绑定到 dgmv 列；冲突只标不裁；补单位、别名 |
| 03 索引 | 双路存储 | 结构化进语义视图；原文进全文与向量索引；中英文词桥接 |
| 04 评估 | 三道质检 | 金标题库测口径正确率；证据校验确认表列可查；冲突交人工裁决 |
| 05 服务 | 证书 PASS 才发布 | 语义视图 v+1：GMV = SUM(dgmv)，剔除退款、按支付时间 |

### 3.5 能力三：知识管理——三类关联产物

- **规范**：遵循 Apache Ossie 的语义模型、本体与映射规范

| 产物 | 面向谁 | 表达什么 | 车企"新车销量"例 |
|---|---|---|---|
| 业务本体 Ontology | 业务人员、领域专家 | 业务术语、对象、属性与关系 | 区分购车订单、车辆、交付；明确"订购"和"交付"的业务含义 |
| 语义视图 Semantic View | 数据开发、分析人员 | 数据集、字段、维度、指标及计算口径 | 定义订单数、交付车辆数，及状态、时间、去重规则 |
| 业务数据映射 Mapping | 业务与数据协作双方 | 业务对象映射到数据实现 | 业务概念 ↔ 具体数据对象、字段和计算定义 |

- **要点**：支持不同用户以熟悉的视角理解知识，同时保持业务概念与数据实现的一致

## 4. 重新理解"知识蒸馏"

- **金句1**：模型具备通用能力，但完成企业任务，还需要企业自己的业务知识
  - **递进**：数据（发生了什么）< 知识（如何理解与行动）< 可信知识（可验证、带版本、可追溯）
- **金句2**：抽取出来不等于有了知识：绑定、裁决、校验、发布之后，Agent 才能可信消费
  - **图解**：LLM 抽取候选 → [绑定表列] → [裁决版本] → [校验] → [带版本发布] → Agent 可信消费
- **收尾金句**：每向右一步：用一种保证，换一种自由
- **修炼顺序**：先接入（把来源理清）→ 再蒸馏（把口径裁决干净）→ 后管理（让业务和数据各看各的视角）
- （老王批注：这份分享其实回答了企业落地 Agent 最被低估的一环——大家都在卷模型和提示词，但答错问题往往败在"有效订单是什么"这种口径没沉淀；知识蒸馏本质是把"数据治理"从 IT 工程升级成 Agent 时代的生产资料加工）

## 5. 产品功能 DEMO（车联网远程控车场景）

- **背景**：车主通过手机 App 下发远程指令（远程开锁、空调控制等），车辆上报状态快照和信号数据，平台对指令执行全链路进行追踪和分析
- **DEMO一**：基于历史的查询信息批量蒸馏——存量确定性 query 加工成语义资产，Lakehouse 平台"语义视图"页面（工作空间 bazhwin_test05，1 个 Semantic View：ev_car_demo，Schema: cars），按名称/责任人/更新时间表格化管理
- **DEMO二**：基于语义资产的数据开发设计——Data Agent 引用语义视图 sv_cars_analytics，自然语言生成"每日车辆远程控制汇总"看板设计（核心指标：当日活跃车辆数/总设备数/成功次数/超时次数/成功率、P95/P99 远程平均加载耗时），Agent 自动完成建仓与加工逻辑
- **DEMO三**：基于语义资产的分析消费——在 Cars_Demo 知识库自然语言提问"用户感知到的痛，到底痛在哪"，Agent 展示执行详情逐步分析

## 6. 落地五步走（小白版）

1. **列一张来源清单**：把部门里在用的取数 SQL、BI 报表、口径文档、黑话词条各列一行（举例：报表 Query 10 条 + 口径文档 3 篇 + 黑话 20 词）
2. **按可信度排优先级**：报表 Query 和 Pipeline 加工排最前，口径文档先确认"是不是最新版"再收——"给少了覆盖不全、给多了噪声混进来"要靠排序解决
3. **挑一个同名多口径指标做试点**：把"销量"在业务文档、加工 SQL、历史查询里的口径全部抄出来对拍（参考：12,860 vs 10,415 vs 8,972 的三口径对照表）——能说出三个数各自衡量什么，才算过关
4. **给候选口径立四道关**：每条口径必须过"绑定表列 → 裁决版本 → 校验 → 带版本发布"才算知识，过不了的标"待裁决"挂给人看（举例：GMV 按下单时间 vs 按支付时间，Q3 勘误后只留一版）
5. **每周补 10 分钟黑话映射**：把本周业务对话里出现的新黑话（如"烧车""大定"）和真实数据字段对上——记进黑话词条表，避免 Agent 靠猜

> 目标：两个月内把你负责域的核心指标全部过完四道关，得到一张 Agent 可信消费的语义资产表；之后再让 Data Agent 基于它建仓、分析。
