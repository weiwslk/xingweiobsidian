## 第一章 从“修好了”走向“可信”

![Skill 调用、过程观察、独立验收与项目复用组成的四类证据框架](https://typora-photo1220.oss-cn-beijing.aliyuncs.com/DataAnalysis/Leo/agent-skills-application-practical-intro-part-2/2026-07-30/ch01-01-evidence-ladder-0f66c309.png)

前三节的 A/C 对照已经帮助我们区分 Skill 是否可用、是否被调用以及结果是否发生变化。进入真实项目后，判断还要再收紧一步：功能恢复只能说明任务到达了一个结果，可信还要求我们能够指出结果来自什么过程、由什么证据验收，以及结论能够外推到哪里。

这一章先建立一套统一尺度。我们先把结果轴与过程轴分开，再把证据整理成调用、过程、结果、复用四类，最后用同一套框架分析三个案例。章内产物是一套四类证据判断框架，后续案例都用它区分证据对象、适用状态、允许结论和不能外推的内容。

### 1.1 两条评价轴

两条评价轴把“任务做成了什么”和“任务怎样被做成”分开记录。先校正一个常见判断——“接口恢复 HTTP 200，修复就可信”。HTTP 200 只能支持功能恢复的一部分结论；如果缺少故障复现、失败证据、回归检查和真实复验，我们仍然无法确认这次修改是否覆盖了原问题。

表 1-1　结果轴与过程轴

| 评价轴 | 主要证据 | 能够回答的内容 | 不能单独证明的内容 |
|---|---|---|---|
| **结果轴** | 功能状态、接口语义、测试结果、真实请求、独立评分 | 最终实现是否满足明确的验收条件 | 修复顺序是否规范、未来是否容易复查 |
| **过程轴** | 复现记录、失败证据、工具顺序、修改路径、回归检查、清理记录 | 记录中出现了怎样的工作过程，A/C 过程有哪些差异 | 最终结果是否已经合格 |

结果轴关注功能、语义和独立验收是否通过；过程轴关注是否先复现、是否保留失败、是否补回归检查、是否完成真实复验和清理。两条轴需要同时保留，但不能相互替代。过程完整不代表结果自然正确，结果正确也不代表过程已经留下可重复证据。

同样是恢复 HTTP 200，一条记录如果只有最终状态，只能支持“当前请求成功”；另一条记录如果同时保留旧实现上的失败测试 RED、修复后的通过测试 GREEN、完整自检和真实请求复验，就能进一步支持“目标故障在旧实现上被测试复现，并经过闭环验证”。这不是给结果重复加分，而是在回答不同的问题。

> **提示：**耗时、工具调用次数和代码量只适合记录过程差异。它们会受模型分析、任务路由和实现选择影响，不能单独推出“Skill 更有效”或“某条路径更可信”。

### 1.2 四类证据

四类证据分别回答“Skill 是否调用、加载前后或 A/C 记录中出现了怎样的工作过程、结果是否合格、方法是否具备复用条件”四个问题。它们彼此相关，但不是必须依次通过的等级。独立验收指不以 Agent 自己的完成声明为准，而是由测试、真实接口行为或独立评分器按照预先写明的条件作出判断。缺少某一类证据，只限制这一类问题的结论，不会自动否定其他类别已经成立的判断。

表 1-2　四类证据判断框架

| 证据类别 | 证据对象 | 允许结论 | 不能外推 |
|---|---|---|---|
| **调用证据** | 动作记录、Skill 加载记录 | 有 Skill 路径可以判断目标 Skill 是否被调用；无 Skill 路径标记为“不适用” | 核心步骤已经执行，最终结果已经合格 |
| **过程证据** | 工具顺序、测试行为、修改路径、清理记录 | 可以描述当前记录中的工作过程及 A/C 差异 | 过程差异由 Skill 导致，或必然带来正确结果 |
| **结果证据** | 自动测试、真实接口输出、独立评分 | 当前结果满足已登记的验收条件 | 所有边界都已覆盖，方法适合长期复用 |
| **复用证据** | **复用准备：**稳定触发条件、工作步骤、边界和完成门 **实际复用：**跨任务重复触发、独立验收记录、通过率和维护变化 | 复用准备证据支持“具备沉淀为项目 Skill 并进入复用验证的条件”；实际复用证据支持评估持续使用价值 | 只有复用准备证据时，不能声称已经稳定复用或适合长期维护 |

调用证据回答“Skill 是否出现”，过程证据回答“记录中出现了怎样的工作方式”，结果证据回答“结果是否通过”，复用证据回答“方法是否具备沉淀条件以及能否持续使用”。无 Skill 路径没有调用对象，因此调用证据标记为“不适用”即可；只要结果证据通过独立验收，这条路径仍然可以得到结果合格的结论。反过来，Skill 名称已经出现，也不能代替过程检查和结果验收，单样本过程差异也不能自动解释为 Skill 的因果作用。

复用证据需要再分两层看。稳定步骤同时写清触发条件、排除条件、执行顺序、完成门和清理要求，只能说明这套方法具备沉淀为项目 Skill 并进入复用验证的条件。持续使用价值还要看跨任务重复触发、独立验收通过率和后续维护变化；一次成功、一次漂亮回复或一次接近满分的评分，都不能替代实际复用观察。

> **提示：**缺少哪一类证据，只限制哪一类结论。我们可以同时写“调用证据不适用、结果独立验收通过”，也可以写“Skill 已调用、结果仍需验收”。四类证据各自诚实记录，不需要用推测补齐空缺。

### 1.3 三个案例递进

三个案例分别检查过程、结果与复用问题。前两个修复案例使用同口径 A/C 对照，第三个案例把完整源码、未执行安装指南、最新 06-A/C 同请求行动与未通过的完成门项目分开。它们形成课程内容的先后顺序，但不构成证据等级。我们对每个案例都保留“证明了什么”和“没有证明什么”，避免把局部证据扩大成普遍结论。

`minimal-runnable-demo` 是第四章使用的当前完整 Skill。最新结果只对应这个同请求 A/C 样本，不代表自然语言自动匹配、跨任务复用或平台发布信息。

表 1-3　三个案例的证据落点

| 案例 | 案例任务 | 主要证据落点 | 结论边界 |
|---|---|---|---|
| **案例一** | 测试驱动修复上下文裁剪 | 同时比较结果轴与过程轴，检查 RED、GREEN、回归检查和真实复验 | 两条路径最终都修好时，差异主要落在修复顺序和可重复证据，不能推出 Skill 保证单次结果更优 |
| **案例二** | 治理公共接口的错误语义 | 把调用证据与结果证据分开，用状态、结构、提示和脱敏条件独立验收 | Skill 被调用只支持调用证据，不能替代对最终实现的检查 |
| **案例三** | 展示 `minimal-runnable-demo` 完整源码与未执行安装指南，再比较同请求 A/C 独立运行 | 核对同名显式调用、过程动作、静态结果、精确 PID 和端口释放，并登记完成门缺口 | 不证明加载文件与展示源码相同，不把单次差异写成固定因果，也不声称协议、时间间隔、浏览器视觉、自动匹配或跨任务复用已经通过 |

本课的平台契约把两类提示词分开使用：Codex 只用于课内证据整理与课程收束提示；Claude Code 只用于已经核查的 A/C 案例，以及同名项目 Skill 实验。提示词标签标明实际提交平台，两类提示不得跨平台粘贴，本课也不声称 Codex 与 Claude Code 的 Skill 发现、加载或执行机制等价。

## 第二章 用 TDD Skill 修复上下文裁剪

![上下文裁剪 A/C 修复对照：A 组无测试 RED，第一次自动检查通过后真实请求仍为 HTTP 500，第二次修改至步骤 40 才恢复 HTTP 200；C 组保留 RED、GREEN 与复验链](https://typora-photo1220.oss-cn-beijing.aliyuncs.com/DataAnalysis/Leo/agent-skills-application-practical-intro-part-2/2026-07-30/ch02-01-tdd-red-green-updated-r2-d0b983a4.png)

这一章先从源码追踪第三轮 HTTP 500，再读取项目级 `test-driven-development` Skill。确认规则之后，我们才重建 A/C 两组操作、查看已登记的实测结果，并判断 Skill 对修复过程产生了什么作用。

> **动手实验：**准备内容一致、彼此独立的 A/C 干净基线副本。保存历史实测修改的源目录只用于核对证据，不直接操作；两份实验副本不能跨组复制修改结果。

### 2.1 从源码定位裁剪故障

案例中的客服 Agent 是 Python 3.12 单文件后端，`MAX_MESSAGES = 4` 把发送给模型的历史消息限制为四条。下面代码块的上半部保留基线裁剪函数的真实故障逻辑，并为 Notebook 独立执行补入 `Any`、`Message` 类型依赖和三行说明注释；下半部是本课加入的最小离线复现，因此整块代码不是基线文件的连续逐字摘录：

```python
from typing import Any

Message = dict[str, Any]

def trim_history(messages: list[Message], max_messages: int) -> list[Message]:
    """在消息数量预算内保留系统消息和最近对话。"""

    # 非正数预算不保留任何消息
    if max_messages <= 0:
        return []
    # 首条为 system 时，将系统约束固定在裁剪结果开头
    pinned = [messages[0]] if messages and messages[0].get("role") == "system" else []
    remaining = max_messages - len(pinned)
    if remaining <= 0:
        return pinned[:max_messages]
    # 在剩余预算内直接截取尾部消息，不检查工具回合是否完整
    return pinned + messages[len(pinned) :][-remaining:]

# 最小离线输入只保留复现裁剪故障所需的角色与工具调用关系
offline_messages: list[Message] = [
    {"role": "system"},
    {"role": "user"},
    {"role": "assistant", "tool_calls": [{"id": "offline-call"}]},
    {"role": "tool", "tool_call_id": "offline-call"},
    {"role": "assistant"},
    {"role": "user"},
]
trimmed_messages = trim_history(offline_messages, 4)
trimmed_roles = [message["role"] for message in trimmed_messages]

assert trimmed_roles == ["system", "tool", "assistant", "user"]
role_path = " → ".join(trimmed_roles)
print(f"离线裁剪结果：{role_path}")
```

`messages` 是待裁剪的完整消息列表，`max_messages` 是总消息预算，返回值是即将交给协议校验和模型的消息列表。函数先固定首条 `system` 消息，再从其余消息尾部截取 `remaining` 条；源码没有检查 `assistant(tool_calls)` 与后续 `tool` 是否仍然成组。

第三轮请求进入裁剪前，消息角色依次为：

```text
system
→ user
→ assistant(tool_calls)
→ tool
→ assistant
→ user
```

总预算为四条时，`system` 占用一条，尾部切片只能再保留三条非系统消息。裁剪后的角色序列因此变成：

```text
system → tool → assistant → user
```

这组消息中的 `tool` 已经失去对应的 `assistant(tool_calls)`，协议校验会拒绝孤立的工具结果。故障根因是裁剪函数拆散了工具回合，不是模型无法理解第三轮追问。

表 2-1　基线三轮请求记录

| 轮次 | 请求内容 | 历史实测状态 | 源码定位 |
|---|---|---|---|
| **第一轮** | 普通问答 | HTTP 200 | 尚未形成工具回合 |
| **第二轮** | 通用商品退款政策 | HTTP 200 | 工具回合在当轮完整执行 |
| **第三轮** | “那定制商品呢？” | HTTP 500 | 尾部切片留下孤立 `tool` |

表中的状态来自已经批准的历史实测记录，不是本次写作重新运行得到的输出。源码已经解释了错误怎样产生；下一步需要读取目标 Skill，确认它要求我们按什么顺序修复。

### 2.2 读取 test-driven-development Skill

项目级 `test-driven-development` Skill 的 frontmatter 明确要求在实现功能或修复缺陷、编写实现代码之前使用该 Skill。Skill 的 Overview 要求先写测试、亲眼看到测试失败，再写最小代码使测试通过；其中的 Iron Law 原文是：

```text
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

这条原文把测试驱动开发约束为一条可检查的工作顺序。TDD 是 Test-Driven Development 的缩写；本案例中的 RED 指新增测试在旧实现上因目标故障而失败，GREEN 指最小生产代码修改后该测试与其余测试全部通过。

Skill 的核心硬约束是：没有先看到失败测试，就不能先写生产代码。仅仅补一个测试文件不够；我们还要确认测试确实因第三轮故障而失败，而不是语法错误、环境错误或无关断言失败。

表 2-2　Skill 规则与本案例观察点

| Skill 原文规则的含义 | 本案例应观察的动作 | 动作成立的证据 |
|---|---|---|
| **修复缺陷前先使用 Skill** | 修改 `trim_history` 前先加载项目级 Skill | 动作记录中的 Skill 加载步骤 |
| **RED：先写一个最小失败测试** | 新增只复现第三轮 500 的回归测试，并在旧实现上运行 | 测试失败且失败原因正是第三步得到 500 |
| **必须核对 RED 的失败原因** | 区分目标断言失败与测试代码、环境或配置错误 | 失败名称与“第三步应返回 200”信息一致 |
| **GREEN：只做让测试通过的最小修改** | 修复裁剪逻辑，不提高消息预算，也不放宽协议校验 | 新增测试转绿，`MAX_MESSAGES = 4` 保持不变 |
| **GREEN 后运行完整测试** | 重新运行新增测试、完整自检与真实环境冒烟检查 | 目标测试和其余测试通过，真实请求再验证功能结果 |

表 2-2 只定义我们接下来要找的证据，还不能提前证明 C 组已经遵守规则。尤其是“调用了 Skill”“看到 RED”“得到 GREEN”和“真实请求恢复”属于不同观察点，必须分别核对。

### 2.3 按操作手册完成 A/C 对照

本节沿用操作手册的 Python 3.12 环境、Bash 命令和 A/C 操作流程，但不沿用手册早期的简化结果描述。手册早期曾把修复后角色序列写成 `system → user`；该两条消息序列不是本课的验收标准。

本课以已批准的历史实测结果为验收口径，并按组核对角色序列。A 组最终为 `system → user → assistant(tool_calls) → tool`，C 组最终为 `system → user → assistant → user`；两组都要保持协议完整、保留当前问题与政策语义，并维持 `MAX_MESSAGES = 4`。HTTP 200 不能替代这些检查。

准备内容一致、彼此独立的 A/C 干净基线副本，不要直接操作保存历史实测修改的源目录。两份基线副本使用同一份任务主体和同一组三轮请求；A 组不提供目标 Skill，C 组提供项目级 Skill，并在任务开头明确要求使用该 Skill。下面的命令与项目自带 `.venv/bin/python` 路径按已验证的 macOS/Linux Bash 环境编写；Windows 原生 PowerShell 不在本案例已批准的验证范围内，应使用与已验证口径一致的 Bash 实验环境，不能把外部系统的虚拟环境直接复制过来执行。

### 3.1 从源码定位错误语义失真

这个客服 Agent 的真实请求链路分为三段：`deepseek-v4-flash` 只识别用户意图、选择工具并生成参数；后端随后通过 HTTP 调用同一进程中的本地工具接口；工具结果由后端直接转换成公共 `/api/agent` 响应，不会再次发送给模型。模型选对工具，只能证明路由环节完成，不能证明公共错误状态、结构和信息边界正确。

本地工具接口会产生 `200 / 401 / 403 / 404 / 409 / 422 / 429 / 500 / 503`。共同基线的 `call_selected_tool` 在 `HTTPError` 分支中没有保留 `exc.code`，而是固定返回 200，并把工具原始响应体作为字符串放入 `error`；`TimeoutError` 和 `URLError` 分支也固定返回 200，并直接暴露异常字符串。

下面代码块保留基线 `call_selected_tool` 的真实异常处理逻辑。为让 Notebook cell 在空白 Python 3.12 命名空间中独立运行，函数前补入了标准库依赖、最小类型和纯内存 `urlopen` 替身，函数后补入合成输入与断言；这些独立运行所需的辅助代码不属于基线文件的连续逐字源码。

```python
# 所有运行依赖均来自 Python 标准库，不需要网络或第三方包
import json
from dataclasses import dataclass
from io import BytesIO
from typing import Any
from urllib.error import HTTPError, URLError

# 最小类型只保留 call_selected_tool 读取的工具名和参数
@dataclass(frozen=True)
class ToolSelection:
    tool: str
    arguments: dict[str, Any]

# 离线请求构造器只生成内存标记，不创建网络连接
def _tool_request(
    selection: ToolSelection,
    *,
    tool_base_url: str,
) -> str:
    return f"{tool_base_url}/{selection.tool}"

# 成功分支所需的解析函数同样只使用标准库
def _read_json_bytes(raw: bytes) -> dict[str, Any]:
    value = json.loads(raw.decode("utf-8"))
    if not isinstance(value, dict):
        raise ValueError("JSON 响应必须是对象")
    return value

# 这个 urlopen 替身合成 404 HTTPError，确保 cell 不联网
def urlopen(request: str, timeout: int) -> Any:
    del timeout
    # 合成错误体故意包含两个待观察字段，字段值不是真实诊断或凭据
    synthetic_body = json.dumps(
        {
            "error": "POLICY_NOT_FOUND",
            "diagnostic": "synthetic-offline-detail",
            "access_token": "synthetic-offline-token",
        },
        ensure_ascii=False,
    ).encode("utf-8")
    raise HTTPError(
        request,
        404,
        "synthetic offline error",
        None,
        BytesIO(synthetic_body),
    )

# 以下函数体保留基线的真实故障分支
def call_selected_tool(
    selection: ToolSelection,
    *,
    tool_base_url: str,
    request_id: str,
) -> tuple[int, dict[str, Any]]:
    """调用模型选中的工具接口并形成 Agent 对外响应。"""

    request = _tool_request(selection, tool_base_url=tool_base_url)
    try:
        with urlopen(request, timeout=5) as response:
            tool_status = response.status
            tool_body = _read_json_bytes(response.read())
    except HTTPError as exc:
        raw_body = exc.read().decode("utf-8", errors="replace")
        # 基线固定返回 200，并把完整原始错误体放入字符串字段
        return 200, {
            "ok": False,
            "error": raw_body,
            "request_id": request_id,
            "selectedTool": selection.tool,
        }
    except (TimeoutError, URLError) as exc:
        # 基线网络异常同样固定返回 200，并直接暴露异常字符串
        return 200, {
            "ok": False,
            "error": str(exc),
            "request_id": request_id,
            "selectedTool": selection.tool,
        }

    return tool_status, {
        "ok": True,
        "data": tool_body.get("data", tool_body),
        "requestId": request_id,
        "selectedTool": selection.tool,
    }

# 合成调用只触发上面的 HTTPError 分支，不读取文件或外部配置
public_status, public_body = call_selected_tool(
    ToolSelection(tool="query_public_policy", arguments={}),
    tool_base_url="offline://tool-service",
    request_id="req-offline",
)
# 基线把原始 JSON 放进字符串 error，先还原对象才能检查字段
raw_error = public_body["error"]
decoded_error = json.loads(raw_error)
# 固定字段顺序，便于断言与运行报告比较同一份正向证据
leaked_fields = [
    name for name in ("diagnostic", "access_token") if name in decoded_error
]

# 断言同时约束状态失真、字符串错误体和敏感字段外露
assert public_status == 200
assert isinstance(raw_error, str)
assert leaked_fields == ["diagnostic", "access_token"]

# 三行输出让实际分支状态在运行报告中直接可见
print(f"公共状态：{public_status}")
print(f"错误字段类型：{type(raw_error).__name__}")
print(f"泄露字段：{', '.join(leaked_fields)}")
```

这个离线 cell 只复现一个合成 404 怎样进入共同基线分支，不冒充真实模型或 HTTP 服务复跑。实际历史基线中的 401、403、404、409、422、429、500 和 503 都经过同一个 `HTTPError` 分支，因此全部被公共接口包装成 200；原始错误体还可能携带 `diagnostic`、示例访问令牌、内部服务地址或内部代码位置。

源码已经说明错误语义在哪里失真。下一步需要读取目标 Skill，找出状态、结构、提示和脱敏分别对应哪条规则，再带着这些观察项进入 A/C 操作。

### 3.2 读取 api-error-handling Skill

项目级 `api-error-handling` Skill 把 API 错误处理拆成标准结构、HTTP 状态、客户端提示、请求追踪和敏感信息边界。Skill 的 Quick Start 使用统一 `error` 对象，并列出 `code`、`message`、`statusCode`、`requestId` 和 `timestamp`；Best Practices 同时明确要求使用正确的 4xx/5xx、提供可操作提示，并禁止用 HTTP 200 承载错误。

表 3-1　Skill 原文规则与本案例观察项

| Skill 原文规则 | 本案例观察项 | 需要看到的证据 |
|---|---|---|
| **统一错误响应结构** | 公共错误是否统一放入 `error` 对象 | `code`、`message`、`statusCode`、`requestId`、`timestamp` 字段 |
| **使用标准 4xx 与 5xx** | 401、403、404、409、422、429、500、503 是否保留明确公共状态 | 完整中文输入矩阵的公共 HTTP 状态 |
| **不得用 HTTP 200 返回错误** | 错误路径是否仍被固定包装成 200 | 成功路径为 200，明确错误路径返回对应 4xx/5xx |
| **提供可操作的客户端提示** | 中文 `message` 是否告诉客户端发生了什么或下一步怎么办 | 逐错误码比较提示的具体程度 |
| **保留请求识别信息** | 错误响应是否包含请求标识与时间 | `requestId` 与 `timestamp` |
| **不得泄露内部细节或敏感数据** | 公共响应是否包含栈、内部诊断、内部地址、令牌或原始异常 | 对响应正文执行敏感字段与内容扫描 |

这些规则定义了后续对照要找的证据，但不能提前证明 C 组已经落实。完整中文输入矩阵来自 A/C 共用的操作手册与任务要求，不是 `api-error-handling` Skill 独有规则；同矩阵复验能够增强两组的结果证据，却不能用来识别 Skill 对过程或结果的因果贡献。

Skill 的范围还包括重试、熔断、监控和告警；本案例任务明确禁止扩展这些能力，因此它们既不进入 A/C 提示词，也不能因为没有实现而判为失败。

### 4.1 Skill 创建时机

重复出现、稳定顺序、可描述的触发与排除、可验收结果，是工作流型 Skill 的四个常见强信号，不是所有 Skill 必须同时满足的硬条件。任务命中其中多项，并且按需加载与复用带来的收益高于编写和维护成本时，就可以考虑创建 Skill。本课的当前完整 Skill 同时满足四项，因此适合作为完整工作流型 Skill 案例。

普通提示词、`CLAUDE.md` 和 Skill 解决的是三种不同的信息寿命。普通提示词只约束当前任务，`CLAUDE.md` 保存每个会话都需要知道的项目事实与稳定约定，Skill 则在匹配到特定任务时按需加载一套重复流程。判断的关键不是内容长短，而是这段信息需要出现一次、每次出现，还是只在特定工作流出现。

表 4-1　三类机制的使用边界

| 机制 | 适合保存的内容 | 进入条件 | 完成检查 |
|---|---|---|---|
| **普通提示词** | 一次性目标、当前任务特有的文件范围、输出格式和临时限制 | 内容只服务当前请求，下一次任务很可能变化 | 当前回复或当前文件满足本次要求 |
| **`CLAUDE.md`** | 项目结构、固定构建命令、运行环境和每个会话都必须遵守的稳定约定 | Claude Code 每次进入项目都需要知道，不依赖某个特定任务触发 | 项目内的日常操作持续遵守这些事实与约定 |
| **Skill** | 按需加载的重复说明、清单、参考知识或多步流程，以及风险边界、清理要求和独立验收条件 | 工作流型任务命中上述多项强信号，且按需加载与复用收益高于编写和维护成本；反复说明、清单或按需知识同样比较复用收益与维护成本 | 调用、过程和结果三类证据分别成立 |

一次性的小修改继续使用普通提示词。项目固定使用的运行时、测试命令和目录约定写入 `CLAUDE.md`，避免每次会话重新声明。本课重点讨论“某类任务出现时才需要加载”的多步方法，因为当前完整 Skill 正好覆盖触发、执行与验收。Skill 也可以承载需要反复说明的指引、重复清单，以及只在特定任务中按需参考的知识；这些内容同样要比较复用收益与维护成本。

表 4-2　六类任务的放置判断

| 任务 | 建议位置 | 判断依据 |
|---|---|---|
| 只修改本次请求指定的三个文案 | 普通提示词 | 文件范围与目标只对当前任务有效 |
| 本次结果必须输出为一段 JSON | 普通提示词 | 临时输出格式不需要进入后续会话 |
| 项目固定使用 Python 3.12 | `CLAUDE.md` | 每个会话都需要遵守的项目事实 |
| 项目的构建、测试和检查命令 | `CLAUDE.md` | 所有相关任务都需要知道的稳定入口 |
| 每次发布前都要执行同一组检查和收尾 | Skill | 重复清单具有稳定顺序与明确完成条件 |
| 反复创建最小实验验证技术判断 | Skill | 触发场景明确，流程、边界和验收可以复用 |

机制选对之后仍要控制结论。任务具备创建条件，只能说明它值得沉淀并进入复用验证；后续还要积累跨任务的实际加载记录、过程观察与独立验收，才能判断触发、过程和结果是否反复成立。

当你面对一个新任务时，我们先问它是一次性目标、项目常驻事实，还是会反复出现的专用流程。一次性约束由你留在普通提示词，所有会话都需要的事实写进 `CLAUDE.md`；只有触发、步骤和完成条件能够重复描述时，我们才进入 Skill 创建。

### 4.2 抽取触发与步骤

Skill 的主体不是一段更长的提示词，而是一套能够被匹配、执行和验收的工作规则。创建时先从重复任务中抽取四组内容：触发条件说明任务何时加载，排除条件限制不适用场景，稳定步骤固定执行主链，完成门阻止 Agent 在验证和清理之前结束。

| 组成 | 需要写清的内容 | `minimal-runnable-demo` 当前完整 Skill 的落点 |

`SKILL.md` 顶部元数据中的 `description` 先写“做什么、何时用”，Claude Code 据此判断自然语言请求是否匹配。名称只负责标识 Skill，过宽的 `description` 会让无关任务也被加载，过窄的表述又会漏掉同义请求。因此，创建时要同时写具体触发表达和明确排除条件，不能只留下一个宽泛功能名称。

稳定步骤需要保留主链，不必把所有背景材料都挤进入口文件。当前完整 Skill 的主链是明确假设、定义成功标准、盘点环境、选择实现、隔离实验、完成最小实现、先写流程文档草稿、真实启动与验证、清理资源、明确边界、最终复核。这个顺序把“能运行”与“已完成”分开，服务启动只是中间状态。

```markdown
# minimal-runnable-demo

## 设计目标

用户经常需要快速验证一个技术想法，但 Agent 容易默认选择 React、Vite、Express 等较重方案，顺手添加数据库、登录、UI 美化、测试框架等无关组件。本 Skill 的核心原则是**移动部件最少**：用最轻量的方式验证假设，不做任何多余的事。

## 什么时候使用

### 应该触发
- 用户说"最小 Demo""最小实现""快速验证""做个 PoC"
- 用户想"验证一下"某个 API、SDK 参数、协议行为、浏览器特性、运行时行为
- 目标是判断一个技术假设是否成立，不是交付可用的产品功能

### 不应触发
- 用户明确要求完整产品功能、生产级实现
- 任务涉及现有项目的功能开发、全面重构或正式上线
- 用户要求的是"完成某个功能"，而不是"验证某个想法"

## 工作流程

按以下 11 个步骤执行。每一步都有明确的目的——理解目的比机械遵循更能做好这件事。

## 硬性完成门

以下条件未满足时，不得结束任务、向用户索取观察结果或把服务留在后台：

- README 已经写入项目，包含完整启动、验证、停止和技术边界
- 确定性机器验证已经完成并记录真实结果
- 当前 Demo 的进程已经按精确 PID 停止，监听端口已经释放
- 需要人眼判断的视觉现象已标注为“待人工确认”，但不会阻断其余收尾工作

除非用户明确要求代为打开页面，否则不要执行 `open`、`xdg-open` 等 GUI 命令。视觉观察不能由机器证明时，提供访问地址和观察方法即可；不要停下来等待用户回复。

### 1. 明确假设
用一句话写出待验证的技术假设。

**为什么**：假设不明确时，Demo 容易膨胀成完整功能。一句话假设划定了边界，也让你和用户对"要验证什么"达成一致。

### 2. 定义成功标准
写出一个可观察、可判定的成功标准，确保任何观察者都能独立判断是否通过。

**为什么**：没有明确标准就无法判断 Demo 是否"通过"。标准应该具体到任何观察者都能独立达成一致。

**补充**：环境文件和用户原始约束也是成功标准的一部分。在实现前，提取所有与验证相关的约束条件（如绑定地址、端口范围、文件路径、不修改现有项目等），将其纳入成功标准，以便完成前逐项复核。

### 3. 盘点环境
查看当前目录结构、可用运行时（python3、node、go 等）和已有依赖。选择移动部件最少的方案。

**为什么**：已安装的运行时不需要额外安装步骤。如果 python3 就能完成，就不需要 `npm install` 或 `go mod init`。

**命令边界**：
- 所有文件路径都按可能包含空格处理，传给命令时使用引号或先进入目标目录。
- 不假设系统存在 GNU 专属命令；在 macOS 上限制请求时间优先用 `curl --max-time`，使用其他工具前先检查是否可用。

### 4. 选择实现
优先使用标准库或已安装运行时。只有假设本身需要时才引入依赖、包管理器或构建工具。

**判断原则**：
- 如果假设是关于框架/库的行为，才使用该框架/库
- 如果假设是关于浏览器原生行为，优先使用纯 HTML + 标准库服务端
- 如果假设是关于 shell 行为，直接在脚本中验证
- 如果假设是关于某个语言运行时特性，用该语言的标准库

### 5. 隔离实验
把实验限制在独立目录或少数明确文件中。不改任何无关业务代码。

**为什么**：不隔离的修改可能破坏现有项目，且让清理变得困难。一个干净的 Demo 目录可以随时删除。

### 6. 最小实现
只实现验证假设所需的一条主路径，以及必要的错误提示或清理行为。

**不做什么**：不添加数据库、登录、UI 美化、路由系统、状态管理、测试框架、CI、部署配置、容器化、性能优化、兼容性处理。这些都不是验证假设所需要的。

**代码说明**：
- 给入口、协议端点、关键数据流和清理逻辑添加简短注释或 docstring，让用户能看懂每个文件和关键函数的作用。
- 注释解释功能、输入输出和边界，不逐行翻译代码，也不写“这里故意有问题”“预留 bug”“正确答案是”等会污染验证的信息。

### 7. 先写流程文档草稿
在启动后台服务前，先在项目 README 中写好以下七个明确小节；小节标题可以增加说明，但不能省略其职责：

1. `验证目标`
2. `最小方案`
3. `创建文件`
4. `启动`
5. `验证与真实结果`
6. `停止与清理`
7. `未包含内容与边界`

其中必须提供可复制的启动命令、访问地址、验证步骤、预期现象和停止命令。明确说明是否使用外部 API、环境变量或凭据；没有使用时也要写出“未使用”。

`未包含内容与边界` 不能只罗列“未使用外部 API、凭据或 Git 提交”。至少写出两个与本次技术假设直接相关、但本 Demo 没有验证的能力，例如断线重连、异常恢复、多客户端并发、生产安全、性能或浏览器兼容性。

此时“验证与真实结果”可以先写待验证项；完成下一步后必须回填实际命令结果，不能保留“应该成功”之类推测。

### 8. 真实启动、验证并回填结果
真实执行 Demo，执行确定性验证并把结果回填 README。区分两类结果：
- **命令或协议层已经验证的事实**：如 curl 返回了预期响应头或状态码、命令行输出了预期文本
- **仍需用户在浏览器中人工观察的现象**：如页面是否逐段显示文字、动画是否流畅。把它记录为人工观察项，继续完成清理和文档，不得等待用户回复
- **默认绑定到回环地址**：如果 Demo 涉及网络服务，默认绑定到 `127.0.0.1` 或 `::1`。只有假设本身需要局域网或外部访问时，才扩大监听范围，并明确说明风险。
- **验证地址和端口**：验证服务状态时同时检查监听地址和监听端口，不能只检查 HTTP 200。需要检查监听进程时，使用只匹配监听套接字的过滤条件，例如 `lsof -nP -iTCP:8080 -sTCP:LISTEN`。
- **时间型现象要按完整单元观察**：如果假设依赖分段、轮询或状态变化，先定义什么算一个完整内容单元，至少观察 3 个完整单元和 2 次可区分的到达间隔。不能把半个协议帧、HTTP 分块边界或单纯的换行数量当成内容。
- **观察窗口覆盖实现节奏**：如果实现声明了发送周期，验证窗口至少覆盖 3 次发送周期并留出约 0.5 秒余量；没有声明时，默认最多观察 5 秒，达到完整成功标准后才提前结束。
- **分清机器证据与视觉现象**：记录完整单元的到达时间，分别说明协议头是否正确、内容是否分批到达，以及浏览器视觉效果是否仍需人工观察。

**为什么**：Agent 常说的"应该成功"不是证据。必须在真实环境中运行并捕获输出。同时让用户清楚哪些是机器已经确认的，哪些需要人眼判断；人眼判断不应成为遗留后台进程或缺失文档的理由。

### 9. 清理资源
停止后台进程，确认端口或临时资源已经释放。

**进程清理规则**：
- 后台进程清理不能依赖跨 Shell 的 jobspec（如 `%1`），因为后续 Shell 会话中该 jobspec 不再有效。
- 首选在启动服务时保存子进程 PID，并在同一 Shell 中完成启动、验证和停止。
- 如果只能按端口反查进程，只允许匹配监听套接字，例如 `lsof -nP -tiTCP:8080 -sTCP:LISTEN`；不要使用 `lsof -ti :8080` 或 `lsof -i :8080` 作为清理依据，因为它们还可能匹配“远端端口为 8080”的已建立连接。
- 发出信号前，先用 `ps -p "$DEMO_PID" -o pid=,command=` 或 `lsof -nP -a -p "$DEMO_PID" -iTCP -sTCP:LISTEN` 展示并核对进程，只有确认它属于当前 Demo 后才可停止。
- 不要把未经核对的 PID 列表直接通过 `xargs kill` 等方式批量终止。无法确认归属时，停止操作并向用户说明。
- 停止后再次使用同一监听过滤条件确认端口已经释放，例如 `lsof -nP -iTCP:8080 -sTCP:LISTEN` 应无输出。

**为什么**：不清理会留下端口占用，影响后续实验；清理条件过宽又可能误伤无关进程。用户可能连续运行多个 Demo，端口冲突让人困惑。依赖跨 Shell 的 jobspec 会导致清理实际失败但 Agent 仍报告"已停止"。

### 10. 明确边界
最后列出本次没有实现的内容和适用边界，让用户清楚 Demo 的局限。例如："本 Demo 仅验证了流式传输的基本行为，没有覆盖断线重连、错误处理、大文件传输等场景。"

### 11. 最终复核

在宣称完成前，将实际运行结果与用户原始限制逐项对照。检查清单示例：

- 所有约束条件是否满足？（如绑定地址、端口、不修改现有项目、不创建 Git 提交）
- 成功标准中的每个可判定点是否都验证通过？
- 清理步骤是否执行并确认？
- 停止前是否核对了 PID 与当前 Demo 的归属，并避免匹配或终止无关连接进程？
- 启动命令是否可复制（用户直接粘贴即可运行）？
- 关键代码是否有功能注释，且注释没有泄露实验答案？
- 时间型现象是否观察到至少 3 个完整单元和 2 次可区分的到达间隔？
- README 是否具备第 7 步规定的七项职责，尤其是独立的“未包含内容与边界”？
- “未包含内容与边界”是否列出至少两个与技术假设直接相关的未验证能力，而不是只写外部资源未使用？

**为什么**：Agent 常说的"都完成了"不等于约束都满足了。逐项对照能发现"功能正常但忽略了一个关键约束"的遗漏，例如服务功能完全正常但监听地址不符合安全要求。

## 默认边界

除非验证假设确实需要，否则不要添加以下内容：

- React、Vue、Next.js、Vite、Express 等框架
- 数据库、登录、权限、后台管理、路由系统、状态管理
- 测试框架、容器、CI、部署、遥测
- 真实外部 API、密钥或需要付费的服务
- 产品化 UI、兼容性矩阵、性能优化
- "顺便完成"的业务功能
- Git 提交
- 终止不属于当前 Demo 的进程

**不要把"最小"理解为省略运行和验证。** 最小 Demo 仍必须能够启动、观察、验证和清理。一个无法启动的 Demo 没有验证价值。

## 最终回答结构

使用以下固定小节，每节保持简洁，不展开长篇论述：

1. **验证目标**：一句话说明要验证的假设
2. **最小方案**：实现方案和选择理由（移动部件最少原则）
3. **创建文件**：列出创建的文件及作用
4. **启动**：可复制的启动命令
5. **验证与真实结果**：真实运行输出（命令结果截图级描述），区分自动验证和人工观察
6. **停止与清理**：停止命令和端口释放确认
7. **未包含内容与边界**：本次没有验证的至少两个技术能力，以及 Demo 的适用范围。不能用“未使用外部 API / 凭据”替代技术边界

## 示例（非限定）

以下是一个可能的方向，但不要视为唯一模板——Skill 的核心是泛化到各种验证场景：

- 流式响应验证：标准库 HTTP 服务器 + 纯 HTML 页面
- Shell 行为验证：自包含 bash 脚本 + 注释说明
- 并发行为验证：标准库多线程 + 简单日志
- 协议行为验证：标准库客户端 + 抓包或日志输出

```

### 4.3 触发产物后的最小验收

本节是触发生成产物后的验收指南，不是安装前可直接运行的起步命令。第一次阅读先了解验收要求；真正执行前必须先完成 4.4 的安装和 4.5 的触发，并确认当前练习项目中已经由本次任务创建 `server.py` 与 README。任一文件缺失时立即停止，不猜测文件内容，也不从历史案例或其他目录复制；先回到 4.4、4.5 补齐安装、发现与触发证据。

当前问题是“浏览器能否逐段显示服务端流式返回的中文文本”。最小方案由标准库 HTTP 服务、根路径中文页面、`/stream` 分段响应和 README 构成，不引入框架、数据库、登录、部署或产品化界面。最小指移动部件少，不代表省略真实启动、验证与清理。

本案例实际协议不是事件流。静态 curl 记录同时出现 `HTTP/1.0 200 OK`、`Content-Type: text/plain; charset=utf-8`、`Transfer-Encoding: chunked` 和 `Cache-Control: no-cache`，并按顺序显示六段完整中文文本。

依据 [RFC 9112 第 6.1 节](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.1)，`Transfer-Encoding` 是 HTTP/1.1 引入的机制，接收方应把带有该字段的 HTTP/1.0 消息视为错误分帧；因此这组 `HTTP/1.0` 与 `Transfer-Encoding` 的组合不符合协议分帧要求。curl 接受响应且依次显示六段文本，只支持本次演示的静态观察，不能证明协议实现正确。

这份静态输出也没有为每个完整文本单元记录到达时间，无法区分段与段之间是否存在可辨认的时间间隔。因此，它不能证明内容在时间上分批到达，也不能满足 4.2 完整源码要求的“至少 3 个完整单元和 2 次可区分的到达间隔”；浏览器视觉是否逐段显现仍待人工确认。

下面命令是与操作手册一致的执行入口，不是新增运行输出。如果你希望在终端一直接观察服务，就选前台分支；如果你需要保留 4.2 要求的精确 PID 证据，就选后台分支。我们选择一条完整执行，不混用两条分支的停止方式。

**前台分支：**在终端一进入练习项目根目录并启动服务，让该终端保持运行：

```bash
python3 server.py
```

在终端二使用有界请求检查响应头和六段内容，避免无界等待：

```bash
curl -v -N --max-time 8 http://127.0.0.1:8080/stream
```

根路径另行检查 HTTP 状态、内容类型和响应大小，不用 `/stream` 的结果替代页面检查：

```bash
curl -s -o /dev/null -w \
  'HTTP %{http_code}\nContent-Type: %{content_type}\nSize: %{size_download} bytes\n' \
  http://127.0.0.1:8080/
```

前台验证完成后，回到终端一按 `Ctrl+C` 停止当前服务，再在终端二检查监听端口。下面命令无输出才说明 8080 已经释放：

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

**后台分支：**在同一个 Shell 中启动服务并立即保存子进程 PID；不要只运行第一行后换到新的 Shell：

```bash
python3 server.py &
DEMO_PID=$!
```

服务启动后，可以在另一个终端执行与前台分支相同的 `/stream` 和根路径验证。验证完成后必须回到刚才保存 `DEMO_PID` 的同一个 Shell。`DEMO_PID` 未赋值或为空时不要执行 `ps` 或 `kill`；下面的检查会先阻止这种误用：

```bash
if [ -z "${DEMO_PID:-}" ]; then
  printf '%s\n' 'DEMO_PID 未赋值，停止清理。' >&2
else
  ps -p "$DEMO_PID" -o pid=,command=
fi
```

先阅读 `ps` 输出并确认它属于当前最小演示；无法确认归属时立即停止，不执行 `kill`，更不能停止无关进程。确认后只停止这个精确 PID，并复核端口：

```bash
kill "$DEMO_PID"
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

后台分支最后一条命令无输出才说明 8080 已释放。不要依赖跨 Shell 的 jobspec，也不要按宽泛进程名或未经核对的 PID 列表批量终止进程。

### 5.2 Skill 保留四问

保留判断从四个问题展开：是否在正确场景反复留下加载记录，加载后观察到怎样的工作过程，是否通过独立且可重复的结果验收，是否值得作为项目工作流持续复用和维护。这四问是本课基于前三个案例整理出的综合判断方法，不是 Claude Code 官方标准。

表 5-2　Skill 保留四问

| 检查项 | 回指证据 | 缺证据时的处理 |
|---|---|---|
| **触发** 是否在正确场景反复留下加载记录 | 目标 Skill 的加载记录、手动触发记录和自然语言匹配记录，并同时核对排除条件 | 匹配范围过宽或过窄时收紧触发；没有实际记录时继续观察 |

我们逐项回答四问后，再把证据结论送入三个决策出口。跨任务证据能够持续支持正确触发、过程记录、独立结果和复用价值时，可以保留；过程与结果可用，但匹配范围过宽、过窄或排除条件不清时，先收紧触发；任一关键问题仍缺证据时，继续观察，不强行给出正向结论。
