# Agent Skills 应用实战入门

这门课把 Skill 放进平时的工作任务，关注任务结果有没有提升、处理流程有没有改善。我们从选择合适的任务开始，逐步建立 Skill 接入、结果验收与流程复盘的方法，让 Skill 带来的变化能够被看见、被复核，也能在实际工作中继续使用。

## 第一章 把 Skill 用到实际工作中

![平时的工作任务接入 Skill 后进行结果验收与流程复盘的闭环](https://typora-photo1220.oss-cn-beijing.aliyuncs.com/DataAnalysis/Leo/agent-skills-application-practical-intro/2026-07-23/ch01-01-daily-skill-loop-698f6b03.png)

把 Skill 放进工作任务后，最先看到的通常是一次调用记录。然而，“Skill 已加载”“Skill 已调用”和“任务得到改善”是三个不同判断。调用只能证明一份工作流进入了上下文，不能证明它改变了后续动作，更不能直接证明结果更好。

本章沿着一条完整证据链建立评价方法：先固定任务边界，再从 Skill 原文中找出可能起作用的规则，随后检查规则有没有改变实际动作和中间产物，最后分别比较结果与流程。这样得出的结论能够说明 Skill 改善了什么，也能说明哪些部分没有改善。

> **【名词解释】****Agent Skill**（Agent Skill，智能体技能）：以 `SKILL.md` 为入口的目录化工作流，用来按需向 Agent 提供处理步骤、边界与配套资源。

### 1.1 从调用转向效果

一次 Skill 应用至少包含四层状态。前两层确认 Skill 能不能参与任务，后两层才回答它有没有价值。只停在“调用成功”，容易把运行条件误写成效果结论。

Skill 应用的四层判断

| 判断层 | 需要确认的内容 | 能够支持的结论 |
|---|---|---|
| 可用 | 项目中存在目标 Skill，运行时能够识别 | Skill 具备进入任务的条件 |
| 调用 | 动作追踪中出现目标 Skill | Skill 已经进入本次处理过程 |
| 生效 | Skill 原文中的规则改变了后续工具、顺序或产物 | Skill 与流程变化存在可观察联系 |
| 改善 | 结果或流程优于可比的无 Skill 路径 | Skill 在当前任务中产生了实际价值 |

课程中的三个任务对应三种不同结果。能力选型中，Skill 同时改变搜索渠道和候选类型；依赖修复中，两条路径都能解决冲突，但文件职责与恢复顺序不同；仓库接手中，两条路径得到的报告质量相当，Skill 的主要价值落在探索方法的规范化。**Skill 的价值不只有“答案更好”这一种形态。**

步骤反复出现、判断容易遗漏、失败后恢复成本较高的任务，更适合引入 Skill。已知文件的一次读取、确定命令的单次执行或无需判断的格式修改，直接使用普通工具通常更合适。任务是否适合先由流程需求决定，而不是由“有没有现成 Skill”决定。

### 1.2 建立作用证据链

Skill 不会跳过过程直接改变结果。它先提供规则，规则再影响工具选择、处理顺序、检查动作或文件组织，最终才可能改变任务产物。因此，效果评价需要沿着“规则—动作—产物—结果”逐层检查。

从 Skill 原文到效果结论

| 证据位置 | 检查内容 | 三个项目中的对应对象 |
|---|---|---|
| 任务边界 | 目标、输入、允许动作、禁止动作和完成条件 | 选型报告、依赖恢复、只读仓库接手 |
| Skill 原文 | 哪些规则会在当前任务中触发，哪些分支不会触发 | 专用搜索、requirements 工作流、仓库打包与定向阅读 |
| 实际动作 | 工具、命令、读取顺序和失败恢复是否符合规则 | Skills CLI、uv compile/sync、Repomix 聚合搜索 |
| 中间产物 | 规则是否留下可检查的文件或结构 | 候选清单、依赖声明与解析文件、仓库快照 |
| 最终结果 | 产物是否更准确、完整、可复核或可复现 | 选型报告、可重建环境、仓库接手报告 |

并非 Skill 原文中的每条规则都会在一次任务中生效。任务禁止安装时，安装分支没有触发；项目没有 `pyproject.toml` 时，uv 的项目工作流不适用；仓库已经明确到单个文件时，全量打包可能没有必要。只有在追踪中出现对应动作，并且动作与产物变化相关，规则才能进入效果解释。

这条证据链还可以暴露执行缺口。Skill 要求推荐前核验来源，但追踪只记录安装量时，我们只能确认发现了候选，不能声称完成了来源核验。效果评价不仅寻找 Skill 做对的部分，也要保留原文规则没有落地的部分。

### 1.3 保持对照可比

无 Skill 与有 Skill 运行只有在任务条件足够接近时才能比较。任务主体、项目基线、运行环境、允许动作、禁止动作和目标产物都应保持一致；有 Skill 组只增加目标 Skill 及其使用要求。

对照实验需要固定的条件

| 对照项 | 固定方式 | 条件不一致的影响 |
|---|---|---|
| 任务提示 | 两组使用相同任务主体、完成条件和禁止动作 | 无法判断差异来自 Skill 还是任务要求 |
| 项目基线 | 每轮从相同文件与相同故障状态开始 | 上一轮产物会成为下一轮的额外上下文 |
| 运行条件 | 保持模型、工具权限和关键环境一致 | 工具可用性和耗时失去可比性 |
| 记录方式 | 分别保存动作、耗时、失败和最终产物 | 只能比较回复，无法重建过程 |
| 样本口径 | 只统计完整返回并形成目标产物的运行 | 卡住或缺失结果会扭曲耗时与调用统计 |

模型任务存在随机性，单次差异可能来自搜索结果、网络状态或临时决策。重复运行用于观察流程是否稳定复现，不是为了挑出表现最好的一次。某一轮卡住、没有完整返回或没有形成目标产物时，它应退出成对统计，不能与另一组强行比较。

对照控制的是主要变量，不会消除所有外部影响。因此，耗时和工具调用需要与动作路径一起解释。两次运行都更快只能写成当前样本中的观察结果，不能直接写成 Skill 会稳定提升固定比例。

### 1.4 分开评价结果流程

结果评价检查任务产物有没有变好，流程评价检查任务沿什么路径完成。二者可以同时改善，也可以只改善其中一项。把它们分开，才能解释“结果相当但方法更规范”这一类常见变化。

结果轴与流程轴

| 评价轴 | 检查内容 | 不能单独作为结论的信号 |
|---|---|---|
| 结果 | 是否回答原任务，范围是否完整，结论能否复核，产物能否再次使用或重建 | 回复中出现“完成”、产物篇幅更长、候选数量更多 |
| 流程 | 工具顺序是否合理，无效尝试是否减少，失败能否定位，维护入口是否清楚，重复运行是否稳定 | Skill 被调用、单次工具调用更少、单次耗时更短 |

结果轴需要使用任务自己的验收对象。能力选型要检查候选是否确属 Agent Skill；依赖修复要检查项目能否从保留文件重建环境；仓库接手要检查架构结论能否回指源码。相同的“正确、完整、可复核、可复现”，在不同任务中对应不同证据。

流程轴不能只数工具调用。调用较少但遗漏核验，流程没有改善；调用增加但顺序固定、失败位置明确、维护职责更清楚，流程仍可能更好。耗时、调用数和失败数是过程指标，只有与工具顺序和最终结果放在一起才有解释力。

双轴结论的四种情况

| 结果变化 | 流程变化 | 结论写法 |
|---|---|---|
| 改善 | 改善 | Skill 同时提高产物质量并规范处理路径 |
| 改善 | 没有稳定改善 | 保留结果收益，同时说明流程成本或波动 |
| 相当 | 改善 | Skill 的价值主要是工作方法、维护边界或恢复能力 |
| 相当或下降 | 没有稳定改善 | 当前任务没有足够证据支持继续使用这套 Skill |

### 1.5 写出结论边界

一条可复核的效果结论需要同时包含任务、规则、动作、变化和边界。我们先写“哪条 Skill 规则进入了任务”，再写“追踪中出现了什么动作”，随后说明结果轴或流程轴发生了什么变化，最后限定样本与未完成的核验。

Skill 效果评价卡

| 评价项 | 需要记录的内容 | 结论用途 |
|---|---|---|
| 任务边界 | 输入、目标、允许动作、禁止动作和目标产物 | 确认无 Skill 与有 Skill 运行可比 |
| 原文规则 | 当前任务可能触发的步骤、限制和回退分支 | 提出 Skill 可能如何起作用 |
| 实际动作 | Skill 调用后的工具、顺序、失败和恢复 | 确认规则是否进入处理过程 |
| 结果证据 | 报告内容、文件变化、验证结果和源码回指 | 判断结果是否改善 |
| 流程证据 | 工具路径、调用次数、耗时、失败和维护入口 | 判断流程是否改善 |
| 重复情况 | 完整运行数量、稳定动作与波动项 | 判断差异是否能够重复观察 |
| 证据边界 | 未执行的规则、缺失核验和不能外推的结论 | 避免把关联写成确定因果 |

评价卡完成后，“使用了 Skill”就能改写成更准确的工作结论：在什么任务边界下，哪条规则改变了哪些动作，结果或流程改善在哪里，哪些变化能够重复观察，以及哪些判断仍需补充证据。

## 第二章 用 find-skills 提高选型质量

![find-skills 从任务拆分到候选核验与项目级建议的搜索流程](https://typora-photo1220.oss-cn-beijing.aliyuncs.com/DataAnalysis/Leo/agent-skills-application-practical-intro/2026-07-23/ch02-01-find-skills-workflow-c350fb16.png)

`find-skills` 是用于发现可安装 Agent Skill 的目录化工作流。它把“帮我找能力”拆成需求识别、专用目录搜索、候选核验和结果呈现，避免模型把 Agent Skill 误解成普通软件、Python 包或通用平台。

第一章建立了结果与流程两条评价轴，本章把它们放进同一项选型任务。我们不仅检查 Skill 是否被调用，还要找到 Skill 原文中可能起作用的规则，再用动作追踪和最终报告判断这些规则是否真的进入了处理过程。

> 📌 **动手实验**：课程项目中的 `01_find_skills/操作手册.md` 提供了完整操作路径。我们可以按手册自行完成 Skill 加载检查、行动观察台、无 Skill / 有 Skill 对照、重复实验与结果比较。每次运行都要单独记录；未返回完整结果的运行不能纳入完整配对统计。

### 2.1 选型任务拆分

任务要求为八类工作分别寻找开源 Agent Skill。这里最容易发生的偏差，不是完全找不到答案，而是回答了另一个问题：把“寻找可安装 Skill”改成了“寻找能解决问题的软件”。Aider、uv、pytest 和 LiteLLM 都可能有用，但工具名称本身不等于 Agent 可以加载并遵循的 Skill。

`find-skills` 原文的第一步是 `Understand What They Need`，要求识别领域、具体任务和复用可能。我们因此先把八类需求改写为可检索的工作意图，再用候选身份、用途和安装入口验收结果。**搜索对象必须是 Agent Skill。**

八类能力需求与搜索意图

| 能力类别 | 具体工作意图 | 候选验收重点 |
|---|---|---|
| 陌生仓库理解 | 梳理项目结构、入口和调用关系 | Skill 提供仓库理解流程，而非只推荐代码工具 |
| 项目环境与依赖 | 管理 Python 3.12 环境和依赖关系 | Skill 覆盖依赖处理步骤、边界和验证 |
| 复杂故障定位 | 建立可复核的根因定位顺序 | Skill 提供系统化调试工作流 |
| Bug 回归测试 | 把问题复现、修复和回归验证连起来 | Skill 明确测试设计与验收动作 |
| 第三方库版本用法 | 核对当前版本的接口与推荐写法 | Skill 强调来源、版本和文档核验 |
| Agent 安全 | 检查权限、输入、凭据和高风险动作 | Skill 给出安全审查范围与限制 |
| API 错误处理 | 统一异常分类、重试和降级边界 | Skill 提供错误处理流程，而非只推荐代理平台 |
| 完成前验收 | 在交付前核对结果、变更和验证证据 | Skill 提供完成判据与复核清单 |

三次有 Skill 运行都把任务拆成多组查询。例如，追踪中出现了 `codebase`、`dependency`、`debug`、`python testing`、`agent security`、`python error` 和 `pr review`。这些词把八类工作转成了独立搜索入口，也为后续更换同义词留下了空间。

两个完整的无 Skill 报告都覆盖了八类需求，却没有出现一个 `owner/repo@skill` 形式的候选，反而分别写入 25 处和 39 处 `pip install`。这说明覆盖面看起来完整，搜索对象却已经偏离。选型质量首先要看答案是否对题，然后才看候选数量。

### 2.2 读取 find-skills

`find-skills` 原文给出了六个主要步骤：理解需求、先看排行榜、使用 Skills CLI 搜索、推荐前验证质量、按固定字段呈现候选，以及在用户同意后安装。原文还要求使用具体关键词，空结果时尝试替代词；完全没有候选时，再回退到通用能力或建议自建 Skill。

> **【名词解释】****Skills CLI**（Skills Command-Line Interface，Skills 命令行界面）：开放 Agent Skill 生态的命令行工具，本章只使用其中的 `find` 搜索能力。

Skill 原文规则与三次有 Skill 运行

| Skill 原文规则 | 追踪中的实际动作 | 可能带来的效果 | 执行判断 |
|---|---|---|---|
| `Understand What They Need`：识别领域、具体任务和复用可能 | 三次运行都把八类需求拆成多组具体查询 | 减少宽泛搜索，把每类需求变成独立检索入口 | 三次稳定执行 |
| `Check the Leaderboard First`：搜索前先看排行榜 | 只有第二次运行先访问 `skills.sh` 首页；另外两次没有留下排行榜访问记录 | 可能优先发现高安装量候选 | 未稳定执行，不能计为稳定效果 |
| `Search for Skills`：使用 `npx skills find` | 三次运行都先调用 `find-skills`，随后使用 Skills CLI；三次均未使用 WebSearch | 把搜索渠道收敛到 Agent Skill 目录 | 三次稳定执行 |
| `Tips for Effective Searches`：使用具体词和替代词 | 第一次的 `code review` 为空后改用 `pr review`；第三次的 `project understanding onboarding` 为空后改用 `codebase understand` | 把空结果变成调整关键词的反馈，不因一次未命中而结束 | 两次出现清晰的空结果恢复链 |
| `Verify Quality Before Recommending`：检查安装量、来源信誉和 GitHub Star | 三次都取得安装量和仓库名；只有第二次打开候选详情页，三次都没有形成逐仓库 GitHub Star 核验记录 | 安装量线索进入报告，但不足以证明来源信誉和仓库质量 | 部分执行 |
| `Present Options to the User`：呈现名称、用途、安装量或来源、安装命令和详情链接 | 三份报告都使用 `owner/repo@skill` 标识，并给出 `npx skills add` 与详情入口 | 候选可以继续定位、核验和安装 | 三次稳定执行 |
| `Offer to Install` 与无结果回退 | 任务明确禁止安装；个别查询为空，但其他关键词仍找到候选 | 没有产生越权安装，也没有进入完全无候选分支 | 分支未触发，不能计为效果 |

这张表把“原文写了什么”和“运行时做了什么”分开。最稳定生效的是需求拆分、专用目录搜索和固定字段呈现；质量核验只完成了一部分。报告中的“来源可信度高”不能仅凭安装量、作者名称或仓库名成立。

```text
npx skills find [query] [--owner <owner>]
```

这条命令可以拆成“启动 CLI、选择搜索动作、传入搜索条件”三层。执行环境需要已经安装 Node.js 和 npm，并且能够访问 Skill 目录使用的网络资源。

`npx skills find` 在 Bash 与 PowerShell 中使用相同的参数。下面用 `python testing` 作为可以直接替换的查询示例；Windows Git Bash 与 WSL 可以直接使用 Bash 版本。

**macOS / Linux Bash，Windows Git Bash / WSL**

```bash
npx skills find "python testing"
```

**Windows PowerShell**

```powershell
npx skills find "python testing"
```

`npx skills find` 命令拆解

| 组成部分 | 作用 | 在本任务中的含义 |
|---|---|---|
| `npx` | npm 提供的包命令执行器。它可以运行项目中已有的命令；本地没有对应命令时，也可能先从网络取得 CLI 包并放入缓存后执行 | 启动 Skills CLI，不需要先进行一次全局 CLI 安装 |
| `skills` | 要执行的 Skills CLI | 连接开放 Agent Skill 目录，提供查找、添加和更新等子命令 |
| `find` | 搜索子命令 | 只查找候选，不把搜索结果安装到当前 Agent |
| `[query]` | 搜索关键词，可以是领域、任务或组合词 | 例如 `"api error handling"`、`"python testing"`；多词查询使用引号更容易看清边界 |
| `[--owner &lt;owner&gt;]` | 可选过滤条件，只搜索指定 GitHub 所有者名下的 Skill | 例如 `--owner anthropics`；不填写时搜索整个目录 |

命令返回的核心对象通常采用 `owner/repo@skill` 形式：`owner` 是 GitHub 用户或组织，`repo` 是仓库，`skill` 是仓库中的具体 Skill。结果还会提供安装量、`skills.sh` 详情链接和类似 `npx skills add owner/repo@skill` 的安装提示。

这里需要区分两件事。`npx` 为了运行 Skills CLI，可能临时取得 CLI 包；`find` 找到的候选 Skill 并不会因此进入项目。只有后续明确执行 `npx skills add <owner/repo@skill>`，才会安装选中的 Skill。

动作追踪中还出现了 `2>&1 | head -30`。它们是 Shell 处理方式，不属于 `skills find`：`2>&1` 把错误输出合并到普通输出，`head -30` 只保留前 30 行。Windows PowerShell 可用 `2>&1 | Select-Object -First 30` 得到对应效果。两种写法都可能截掉排在后面的候选，不能代替完整的候选核验。

原文把 Skills CLI 定义为开放 Agent Skill 生态的包管理器。`find` 负责发现候选，不能替代候选内容审查。原文对 1K 以上安装量给出优先倾向，对 100 以下安装量和 100 以下 GitHub Star 给出谨慎提示；这些阈值是筛选线索，不是安全保证。

翻译版本帮助我们理解流程，命令、参数和作用域仍要回到原始 `SKILL.md` 核对。翻译不会扩大 Skill 的权限，也不会把原文中的全局安装示例自动改成项目级作用域。

| 候选发现验收 | 候选能够定位到具体仓库与 Skill 名称，结果包含用途、安装量或来源、安装命令和详情链接 | 确认报告提供的是可继续核验的 Agent Skill 候选 |

动作追踪记录了安装量、仓库名称和 Skills 详情链接。第二次有 Skill 运行还打开了部分候选详情页，但三次运行都没有形成逐一访问 GitHub 仓库、核对 Star、维护状态、权限和附带脚本的完整记录。因此，报告中的“来源可信度经逐一验证”没有得到充分证明。

候选名称采用 `owner/repo@skill` 形式，只能帮助我们定位对象。采用验收仍要打开对应 Skill 内容，检查它要求读取什么、执行什么、写入哪里，以及附带资源是否超出任务范围。安装量高、排名靠前或仓库星标较多都不是安全保证。

报告还要明确“本次只查找、不安装”。Skill 原文提供了带 `-g -y` 的全局安装示例，本任务只允许给出项目级安装方式，因此三次报告都去掉了全局标志，也没有执行安装。候选通过采用验收后，仍要单独确认作用域和变更范围。

### 2.5 解释对照结果

两组完整配对都显示，有 Skill 路径更快完成并记录了更少或相近的工具调用。这个结果值得记录，但两次下降幅度不同，而且搜索服务、网络和模型决策都会影响耗时，所以不能把它推广为固定提速比例。

两组完整配对的过程指标

| 完整配对 | 无 Skill | 有 Skill | 观察结果 |

| 第 1 组 | 889.226 秒；39 次工具调用；5 次失败；29 次 WebSearch | 481.924 秒；37 次工具调用；0 次失败；1 次 Skill 与 35 次 Bash | 耗时下降 45.80%，工具调用只减少 2 次 |

本组结论的三层证据

| 证据层级 | 本组可以怎么说 | 边界 |
|---|---|---|
| 直接证据 | 三次有 Skill 运行都形成“调用 Skill—Skills CLI 搜索—生成报告”；报告稳定出现 24 至 30 个不同的 `owner/repo@skill`，并给出项目级安装入口 | 能够支持流程规范化和候选类型更对题 |

本项目中，`find-skills` 的核心效果不是替模型决定“哪个候选最好”，而是把模糊选型改造成可重复的发现流程，并让最终报告回答正确的问题。它改善了搜索对象、处理路径和报告可操作性；候选质量与安全性仍需逐一核验。

## 第三章 用 uv 改善依赖修复

![uv 依赖冲突恢复中的声明解析环境同步与重建验证闭环](https://typora-photo1220.oss-cn-beijing.aliyuncs.com/DataAnalysis/Leo/agent-skills-application-practical-intro/2026-07-23/ch03-01-uv-recovery-flow-9bd5df21.png)

`uv` 是 Python 包和项目管理器。这个冲突项目已有 `requirements.txt`，却没有 `pyproject.toml` 和 `uv.lock`，因此实际采用的是 `uv pip compile`、`uv pip sync` 等 pip 兼容接口，而不是以 `pyproject.toml + uv.lock` 为中心的 uv 项目工作流。

两组都解决了依赖冲突。有 Skill 路径的核心变化，是把顶层声明、完整解析结果、环境同步和再次重建分成连续步骤。我们既要检查最终环境能否安装，也要检查维护入口是否清楚、相同起点下的三次重复是否保持一致。

> 📌 **动手实验**：课程项目中的 `02_uv/操作手册.md` 提供了完整操作路径。我们可以按手册自行完成 Skill 加载检查、行动观察台、无 Skill / 有 Skill 对照、恢复基线、重复实验与结果比较。每轮都要从同一初始状态开始，并按手册保留禁止动作与验收边界。

### 3.1 冲突项目边界

冲突项目要求保留 `imports_demo.py` 静态列出的 86 个顶层发行包，并在 Python 3.12 的项目内环境中完成修复。修复不能靠删掉难处理的包，也不能通过新增业务功能或执行 `imports_demo.py` 来改变任务范围。

五类依赖文件的职责边界

| 文件 | 保存内容与维护者 | 是否含传递依赖 | 本项目实际情况 |
|---|---|---|---|
| `requirements.in` | 保存项目要维护的顶层声明，由人或 Agent 修改 | 通常不列传递依赖 | 三次有 Skill 运行都新建该文件；实际文件有 86 项 |
| `requirements.txt` | 在本章有 Skill 路径中由 `uv pip compile` 生成，保存精确解析结果 | 包含顶层与传递依赖 | 三次有 Skill 运行都重写该文件，并用它安装环境 |
| `requirements.lock` | 本项目无 Skill 第一次、第三次把它作为 `uv pip compile -o` 的输出名 | 包含编译出的传递依赖 | 只是 pip 兼容流程中选择的文件名；有 Skill 路径没有生成它 |
| `requirements-locked.txt` | 无 Skill 第二次由 `pip freeze` 生成，记录当次环境中的精确版本 | 包含已安装的传递依赖 | 只在这一次出现，命名和生成方式没有在重复运行中保持一致 |
| `uv.lock` | uv 项目工作流根据 `pyproject.toml` 管理的跨平台锁文件，由 uv 生成和更新 | 包含完整解析关系 | 本项目没有 `pyproject.toml`，六次运行都没有生成或使用 `uv.lock` |

这里最容易混淆的是 `requirements.lock` 与 `uv.lock`。`uv pip compile` 的 `-o` 可以把 requirements 格式结果写成不同文件名；文件名带 `.lock`，不会自动获得 `uv.lock` 的项目语义。本项目有 Skill 路径实际交付的是 `requirements.in + requirements.txt`。

86 这个数字可以由两处实际文件相互核对：`imports_demo.py` 的 `REQUIRED_DISTRIBUTIONS` 有 86 项，最终 `requirements.in` 也有 86 条非注释声明。第三次有 Skill 最终说明曾写成 85 项，但文件内容不支持这个数字，因此本章采用 86，不用最终说明中的口头计数代替文件核对。

### 3.2 读取 uv Skill

`uv` Skill 先按项目现有文件选择工作流。Skill 原文把已有 requirements 文件、手工环境管理且没有 `uv.lock` 的情况归到 pip 兼容接口，并给出 `venv → compile → sync` 的命令组合。原文中“Python 工作始终使用 uv”是这份 Skill 的执行政策，不是 uv 官方对所有项目的普遍要求。

Skill 原文规则、实际动作与文件变化

| Skill 原文规则 | 追踪中的实际动作 | 最终文件或结果变化 | 能支持的结论与边界 |
|---|---|---|---|
| 已有 requirements 且没有 `uv.lock` 时使用 pip 兼容接口 | 三次都先调用 uv Skill，随后使用 `uv pip` 与 `uv venv` | 没有引入 `pyproject.toml` 或 `uv.lock` | 说明实际动作与项目类型匹配；不能据此把 Skill 政策写成通用强制规则 |
| `uv pip compile requirements.in -o requirements.txt` | 前两次按 Python 3.12 编译；第三次增加 `--universal` | 三次都新增 86 项的 `requirements.in`，并生成 `requirements.txt` | 支持“声明与解析结果分离”；第三次的通用解析范围与前两次不同 |
| `uv pip sync requirements.txt` | 前两次都在新环境中同步，并移除环境后再次同步 | 前两次都记录 113 个包再次安装成功 | 支持前两次可重复重建；第三次改用 `uv pip install -r`，不能声称三次都执行了 sync |
| `uv venv` 建立项目环境 | 三次都使用 Python 3.12 新建 `.venv` | 解析结果进入项目内干净环境 | 环境目录是验证载体，不是锁定产物 |
| 使用 uv 的运行与检查入口 | 第三次先遇到 `python -m pip check` 缺少 pip，随后改用 `uv pip check` | 依赖一致性检查正常结束 | 支持检查命令已恢复；不能把前一个失败从工具失败统计中删除 |

### 3.3 重建修复顺序

原始 `requirements.txt` 同时钉住了互不兼容的版本，已暴露 `httpx`、`starlette`、`pydantic`、OpenTelemetry、gRPC/Protocol Buffers 和 `click` 六组依赖链冲突。有 Skill 路径没有逐个保留这些旧版本，而是先从静态清单重建顶层声明，再交给解析器统一计算。

**macOS / Linux Bash，Windows Git Bash / WSL**

```bash
uv pip compile --python-version 3.12 requirements.in -o requirements.txt
```

这条命令在前两次运行中生成面向 Python 3.12 的 `requirements.txt`。两次结果都是 86 个顶层声明解析为 113 个精确包。第三次实际使用了下面的通用编译命令，最终文件有 136 条带环境条件的依赖记录；当前环境安装其中 113 个，因此 136 不能写成当前平台实际安装数量。

```bash
uv pip compile requirements.in -o requirements.txt --python-version 3.12 --universal
```

```bash
uv venv --python 3.12
```

`uv venv` 只负责建立项目环境，不解析完整依赖。环境建立后，前两次运行使用同一份生成文件同步：

```bash
uv pip sync requirements.txt
```

**Windows PowerShell**

```powershell
uv pip compile --python-version 3.12 requirements.in -o requirements.txt
uv pip compile requirements.in -o requirements.txt --python-version 3.12 --universal
uv venv --python 3.12
uv pip sync requirements.txt
```

这组 uv 子命令与参数在两类 Shell 中相同。跨平台差异主要出现在路径、环境变量和删除目录等 Shell 操作，而不在 `compile`、`venv` 与 `sync` 本身。

前两次随后移除 `.venv`，再次执行 `uv venv` 和 `uv pip sync requirements.txt`，都重新安装 113 个包。第三次在通用编译后使用 `uv pip install -r requirements.txt` 完成干净安装，并以 `uv pip check` 验证一致性，但没有留下第二次重建动作。

因此，可重复的主路径是“维护 `requirements.in` → compile 生成 `requirements.txt` → venv 建立环境 → sync 同步 → 删除环境后再次 venv 与 sync”。第三次验证了另一条可安装路径，却不能补足缺失的第二次重建证据。

### 3.4 比较修复效果

三次无 Skill 与三次有 Skill 运行都从内容相同的初始依赖文件开始，运行前工作区也都是干净状态；六次进程都正常完成，并通过 Skill 隔离检查。因此，本章把同序号运行组成三组完整配对，不排除其中任何一次。

三组完整配对的过程指标

| 完整配对 | 无 Skill | 有 Skill | 本组观察 |
|---|---|---|---|
| 第 1 组 | 276.932 秒；47 次工具调用；10 次失败 | 195.652 秒；33 次工具调用；0 次失败；1 次 Skill | 耗时下降 29.35%，工具调用减少 14 次 |
| 第 2 组 | 765.192 秒；44 次工具调用；9 次失败 | 103.562 秒；28 次工具调用；1 次失败；1 次 Skill | 耗时下降 86.47%，工具调用减少 16 次 |
| 第 3 组 | 551.902 秒；53 次工具调用；9 次失败 | 164.606 秒；29 次工具调用；3 次失败；1 次 Skill | 耗时下降 70.17%，工具调用减少 24 次 |

三组有 Skill 运行的耗时、工具调用和失败次数都低于对应的无 Skill 运行。失败统计同时包含预期的初始冲突和过程失误，例如路径空格未引用、临时文件丢失、版本条件被 shell 解释、检查命令不适用等，所以失败次数反映过程阻力，不等同于最终结果质量。

结果质量与流程质量分开判断

| 评价层 | 无 Skill 路径 | 有 Skill 路径 | 结论边界 |
|---|---|---|---|
| 最终结果 | 三次都解决冲突并留下可安装结果 | 三次都解决冲突并保留 86 个顶层发行包 | 不能写成只有 Skill 才能修复 |
| 依赖产物 | 分别留下 `requirements.lock`、`requirements-locked.txt`、`requirements.lock` | 三次都留下 `requirements.in + requirements.txt` | 有 Skill 路径的维护入口更一致 |
| 重建验证 | 都完成新环境安装，但试装和锁定方式不同 | 前两次完成二次 sync；第三次完成干净安装与 check | 第三次验证深度不同，不能说三次都完成二次重建 |
| 过程指标 | 三组中耗时、调用和失败都更高 | 三组对应指标都更低 | 只支持本任务的三组样本，不承诺其他项目获得固定比例 |

结果层面，两组都成功。有 Skill 路径的提升主要体现在文件职责统一、重复运行产物一致，以及本任务三组样本中的过程阻力下降。耗时下降幅度从 29.35% 到 86.47% 相差很大，说明我们可以记录方向一致，不能宣传固定提速。

### 3.5 定位恢复失败

恢复失败要先判断发生在声明、解析、环境还是验收环节。把错误归到正确位置，可以避免为一个环境问题继续改版本，也能避免用一次安装成功掩盖不可重复的声明结果。

失败位置与恢复动作

| 失败位置 | 可观察信号 | 恢复动作 | 恢复判据 |
|---|---|---|---|
| 顶层声明或版本约束 | 解析器返回 `No solution found when resolving dependencies` | 按错误链修改 `requirements.in`，然后重新编译 | 解析器生成新的 `requirements.txt` |
| 一次性命令 | 未引用的 `&gt;=` 被 shell 当作重定向，或临时文件不存在 | 停止扩写长串试装命令，把顶层需求写回声明文件 | 同一编译命令可以重复使用 |
| 环境状态 | 环境不存在，或创建命令发现已有 `.venv` | 确认目标环境后新建，验证重建时先移除旧环境 | 同步只依赖解析结果，不依赖旧环境残留 |
| 检查命令 | `uv run python -m pip check` 返回 `No module named pip` | 在当前 pip 兼容接口中改用 `uv pip check` | 依赖一致性检查正常结束 |
| 产物核对 | 检查了不存在的旧文件，或最终说明中的 85、86、136 项彼此混用 | 分别统计顶层声明、通用解析记录和当前平台安装数 | 顶层发行包以 `requirements.in` 的 86 项为准 |

本章结论的三层证据

| 证据层级 | 本章可以怎么说 | 边界 |
|---|---|---|
| 直接证据 | 三次 Skill 调用后都生成同一组依赖文件；三组过程指标方向一致；两组都修复成功 | 支持本任务中的流程规范化、产物一致和过程改善 |
| 合理关联 | Skill 的 pip 接口、compile、sync 与 venv 规则，和声明/解析分离、二次重建顺序一致 | 规则与动作变化相符，但不能排除模型决策、缓存和环境状态的影响 |
| 没有证据 | Skill 才能解决依赖冲突；所有有 Skill 运行都完成二次 sync；`requirements.txt` 就是 `uv.lock`；其他项目也会固定提速 | 这些说法超出最终文件、动作追踪和三组样本 |

恢复完成的最低证据链是：86 个顶层发行包仍在声明文件，解析器能够生成结果，干净环境能够安装，并且删除环境后还能再次重建。缺少其中一环，就要写明未完成的验证。按照 `02_uv/操作手册.md` 重做时，我们还要分别记录声明数、解析记录数、当前平台安装数和第二次重建结果，避免把不同数字混成一个“包数量”。

## 第四章 用 repomix-explorer 优化仓库接手

![repomix-explorer 从仓库聚合到模式搜索与原文件核验的阅读路径](https://typora-photo1220.oss-cn-beijing.aliyuncs.com/DataAnalysis/Leo/agent-skills-application-practical-intro/2026-07-23/ch04-01-repomix-reading-path-934ccb65.png)

本章项目是一个 Python 3.12 企业工单处理 Agent。它通过命令行接收工单，先执行本地的清洗、分类、路由和工具查询，再调用模型生成回复，最后经过输出守卫返回 JSON。我们先沿源码看清项目本身，再判断 `repomix-explorer` 改变了哪一段仓库探索过程。

仓库接手需要回答四类核心问题：程序从哪里进入，生产对象在哪里完成组装，哪些代码会访问外部服务，测试覆盖到哪里。目录名只能提供候选位置，可靠结论还要连接到配置、符号定义和调用关系。

> 📌 **动手实验**：课程项目中的 `03_repomix_explorer/操作手册.md` 提供了完整操作路径，包括 Skill 加载检查、行动观察台、无 Skill / 有 Skill 提示词、恢复基线、重复运行和比较重点。我们可以按手册自行完成对照；本实验不需要安装 Python 依赖，也不需要运行真实模型。使用 Repomix 的一侧还需按手册核对 Node.js、npm 与网络条件。

### 4.1 看清实际项目架构

项目采用 `src` 布局，交互边界是 CLI，不包含 Web API 或数据库层。`domain` 保存稳定数据结构和规则，`pipeline` 实现处理阶段，`ports` 定义协议，`adapters` 接入模型与审计实现，`tools` 提供六个本地业务工具。

`pyproject.toml` 把 `ticket-agent` 注册到 `ticket_agent.cli:main`，`src/ticket_agent/__main__.py` 也转交给同一个函数。根目录 `main.py` 只读取配置并输出服务是否已配置，不会执行完整工单处理，因此不能仅凭文件名把它认作生产入口。

源码中的实际分层与职责

| 位置 | 源码职责 | 接手时要确认的关系 |
|---|---|---|
| `cli.py`、`io/` | 解析命令行参数，读取工单 JSON 或标准输入，输出结果 JSON | CLI 如何进入应用用例 |
| `bootstrap.py` | `build_application()` 选择具体实现并组装生产对象 | 端口最终绑定到哪个适配器或本地组件 |
| `application.py` | `AgentApplication.handle()` 编排同步工单处理流程和审计阶段 | 数据按什么顺序穿过各处理阶段 |
| `domain/` | 定义工单、分类、路由、工具观察和结果等数据结构，以及优先级和人工复核规则 | 稳定业务对象与规则由谁拥有 |
| `pipeline/` | 实现清洗、分类、路由、工具规划、工具执行、证据整理和输出守卫 | 各阶段的输入、输出与失败处理 |
| `ports/` | 定义 `LanguageModel`、`AuditRecorder` 和业务工具协议 | 核心流程依赖的能力接口 |
| `adapters/` | 实现百炼 OpenAI 兼容模型调用和内存审计记录 | 真实外部调用与测试替身的分界 |
| `tools/` | 注册并执行六个确定性本地工具 | 工具返回本地示例数据，不访问数据库 |
| `tests/`、`scripts/` | 提供单元、契约、离线冒烟测试，以及独立的真实模型连通检查 | 普通验证与真实联网检查不能混为一条路径 |

一张工单进入正式 CLI 后，`read_ticket()` 先把 JSON 转成 `Ticket`，`build_application()` 再装配生产对象，随后 `AgentApplication.handle()` 依次调用清洗、分类、路由、工具规划、工具执行、模型生成和输出守卫，最后由 `present_json()` 输出 `AgentResult`。

```text
工单 JSON 或标准输入 → cli.main() → read_ticket() → build_application() → sanitize → classify → route → plan → execute → BailianOpenAIAdapter.draft_reply() → OutputGuard.guard() → present_json()
```

`bootstrap.py` 默认把 `LanguageModel` 端口绑定到 `BailianOpenAIAdapter`。这个适配器中的 `client.chat.completions.create()` 是完整处理链唯一明确的真实模型联网调用；六个业务工具返回本地确定性数据。`batch_runner.py` 只执行清洗、分类、路由和本地工具，不生成模型回复。

测试边界也由源码明确分开。契约测试向 `BailianOpenAIAdapter` 注入记录型假客户端，离线冒烟测试向组合根注入 `DeterministicLanguageModel`；`scripts/real_model_smoke.py` 才创建真实适配器并检查模型连通性。接手报告若只写“项目依赖 OpenAI SDK”，仍不足以说明哪条路径真正联网。

### 4.2 读取 Skill 原文规则

`repomix-explorer` 的触发条件是理解陌生或较大的仓库、发现跨文件模式和统计仓库规模。原文明确排除已知路径读取、单符号搜索、代码修改、Git 操作、测试、构建和安装。仓库较小、入口已知或问题只涉及一个位置时，直接使用搜索和读取通常更短。

> **【名词解释】****Repomix**：把仓库中的文本内容整理为一个带文件边界的聚合文件，便于统一查看目录、搜索跨文件模式和定向读取相关区段。

原文给出的主流程是“打包仓库—记录输出位置和规模—搜索结构与模式—读取命中区段—提供结论”。这一组动作追踪中的三次有 Skill 运行都先调用 `repomix-explorer`，再调用 Repomix。下面是第三次实际出现的命令形态。

```text
npx repomix@latest --output /tmp/repomix-explorer-with-skill-analysis.xml 2>&1
```

上面是动作追踪中保留的 Linux/macOS 命令原样。学员自行操作时应把聚合文件写入当前系统的临时目录，Windows Git Bash 与 WSL 可以直接使用 Bash 版本。

**macOS / Linux Bash，Windows Git Bash / WSL**

```bash
OUTPUT_FILE="${TMPDIR:-/tmp}/repomix-explorer-with-skill-analysis.xml"
npx repomix@latest --output "$OUTPUT_FILE" 2>&1
```

**Windows PowerShell**

```powershell
$OutputFile = Join-Path ([System.IO.Path]::GetTempPath()) "repomix-explorer-with-skill-analysis.xml"
npx repomix@latest --output $OutputFile 2>&1
```

追踪中 Repomix 命令的组成

| 组成部分 | 实际作用 | 本次出现情况 |
|---|---|---|
| `npx` | 调用 npm 包命令执行器；本地没有对应包时可能从网络取得并缓存 | 三次均用它启动 Repomix |
| `repomix@latest` | 选择当时解析到的最新 Repomix；三次输出均显示 v1.17.0 | 三次均执行一次 |
| `--output &lt;path&gt;` | 把聚合结果写到指定位置，避免在项目根目录新增聚合文件 | 三次分别写入 `/tmp/repomix-with-skill-analysis.xml`、`/tmp/repomix-output.xml`、`/tmp/repomix-explorer-with-skill-analysis.xml` |
| `2&gt;&amp;1` | 把错误输出合并到普通输出，便于动作记录保存完整命令反馈 | 三次命令都包含该重定向 |

三轮都使用默认 XML 输出，没有出现 `--compress`、`--include` 或 `--ignore`。三次打包结果也完全一致：60 个文件、21,651 tokens、89,197 chars。这个结果为搜索建立了相同的聚合检索面，但打包本身仍是一项额外成本。

```text
Total Files: 60 files | Total Tokens: 21,651 tokens | Total Chars: 89,197 chars
```

聚合文件应按原仓库的敏感级别处理。Repomix 的安全检查可以发现部分常见敏感模式，但“没有发现可疑文件”不等于仓库不含秘密，也不能替代权限控制和人工核验。被忽略的文件、二进制文件和配置排除项可能没有进入聚合结果；若启用压缩，结构扫描会更紧凑，也可能省略实现细节。

Skill 原文、实际动作与报告变化

| Skill 原文规则 | 追踪中的实际动作 | 最终报告变化 | 能支持的结论与边界 |
|---|---|---|---|
| 陌生仓库整体理解应触发 Skill | 三次均先调用 `repomix-explorer` | 报告都围绕结构、入口、调用链、依赖和测试组织 | 说明触发条件稳定成立；不能用“调用过”证明答案正确 |
| 先打包仓库并记录输出位置与规模 | 三次各执行一次 Repomix，并得到相同的文件、token 和字符统计 | 有 Skill 报告增加聚合规模和 Repomix 信息 | 说明建立了统一检索面；不能把安全扫描无命中当作无秘密保证 |
| 先看结构，再用模式搜索定位候选 | 三次分别执行 9、4、6 次报告前聚合搜索，目标包括 `main.py`、`pyproject.toml`、`src/` 和 `tests/` | 报告从整体目录进入入口、模块和测试边界 | 三次都复现搜索优先顺序；命中位置仍只是候选 |
| 围绕命中位置定向读取 | 三次分别产生 52、39、39 次聚合文件区段读取 | 报告仍能识别正式入口、组合根、联网点和测试分层 | 减少逐个打开原文件的动作；三轮没有重新打开原文件，不能声称已经完成回源核验 |
| 把观察整理为可行动结论 | 三次都生成中文项目接手报告 | 核心覆盖与无 Skill 报告相当 | Skill 的主要价值是规范探索方法，不是替模型提供仓库答案 |
| 已知路径和单点问题不应触发 | 本次任务要求整体接手，没有进入该排除分支 | 报告没有提供这类任务的效率对照 | 小仓库、已知入口和单符号问题仍应优先直接搜索 |

### 4.3 重建仓库探索过程

两组使用同一任务主体：弄清目录结构、真实入口、核心调用链、模块职责、外部依赖和测试范围，并生成中文接手报告。有 Skill 组只增加“必须使用项目级 `repomix-explorer`”这一项。三组两侧都完整返回且退出码为 0，因此本章只比较这六次完整运行。

无 Skill 三轮先扫描目录，再分别产生 59、58、60 次原文件 `Read`。这种路径能够得到正确报告，但主要依赖逐个打开约 60 个文件，阅读顺序较机械。有 Skill 三轮都稳定复现下面的主链，其中“定向读取”只指读取聚合文件中的相关区段。

```text
调用 repomix-explorer → Repomix 打包 → 搜索聚合文件 → 定向读取聚合文件区段 → 生成项目接手报告
```

三次有 Skill 运行的探索主链

| 运行 | 聚合输出 | 报告前聚合搜索 | 聚合区段 Read | 原文件 Read | 产物 |
|---|---|---|---|---|---|
| 第 1 次 | `/tmp/repomix-with-skill-analysis.xml` | 9 次 | 52 次 | 0 次 | 项目接手报告 |
| 第 2 次 | `/tmp/repomix-output.xml` | 4 次 | 39 次 | 0 次 | 项目接手报告 |
| 第 3 次 | `/tmp/repomix-explorer-with-skill-analysis.xml` | 6 次 | 39 次 | 0 次 | 项目接手报告 |

聚合搜索实际定位了文件树、`main.py`、`pyproject.toml`、`src/ticket_agent/`、`tests/`、`scripts/` 和示例目录。随后进行的 `Read` 仍以聚合文件为对象，只是通过偏移量和读取范围进入相关文件区段。这个动作建立了“全局扫描—候选定位—局部展开”的检索面，但没有独立证明原文件已被重新打开。

仓库接手不能停在聚合文件中的名称匹配。可靠的报告应从搜索命中候选位置，再回到配置和原文件确认符号定义、调用方向与测试替身。这个仓库需要保留下面四条回源路径。

接手报告的四条核心证据链

| 接手结论 | 聚合搜索候选 | 原文件核验 | 报告应写清 |
|---|---|---|---|
| 正式 CLI 入口 | `project.scripts`、`cli.py` | `pyproject.toml` 与 `src/ticket_agent/cli.py` | 注册入口和完整调用链 |
| 生产组合根 | `build_application`、`bootstrap.py` | `src/ticket_agent/bootstrap.py` | 哪些端口在此选择具体实现 |
| 真实模型联网点 | `BailianOpenAIAdapter`、`chat.completions.create` | `src/ticket_agent/adapters/bailian_openai.py` | 联网类、调用方法和配置来源 |
| 测试范围 | `tests/unit`、`tests/contract`、`tests/smoke` | `pyproject.toml`、测试替身与真实连通脚本 | 哪些测试离线，哪条路径才会访问真实服务 |

三份有 Skill 报告仍然得出了与直接阅读相当的核心结论，但动作本身没有证明关键结论经过独立回源。因此，“打包形成聚合检索面”和“回到源码核对结论”必须分成两个动作；后者是报告验收要求，不能写成三轮中已经执行。

### 4.4 比较结果质量与流程质量

本次样本只包含同一仓库、同一接手任务下的三组配对，六次运行都完整返回且退出码为 0。无 Skill 三轮分别产生 59、58、60 次原文件 `Read`；有 Skill 三轮都复现相同探索主链。这个样本可以比较当前任务的结果与过程，不能外推成所有仓库的固定收益。

三轮阅读过程的精确比较

| 配对 | 无 Skill | 有 Skill | 有 Skill 相对变化 |
|---|---|---|---|
| 第 1 轮 | 143.560 秒；64 次调用；Read 59；Bash 4；失败 0 | 183.637 秒；71 次调用；Read 52；Bash 17；失败 2 | 多 40.077 秒（慢 27.92%）；调用多 7；Read 少 7 |
| 第 2 轮 | 176.209 秒；70 次调用；Read 58；Bash 11；失败 1 | 152.539 秒；46 次调用；Read 39；Bash 5；失败 0 | 少 23.670 秒（快 13.43%）；调用少 24；Read 少 19 |
| 第 3 轮 | 165.344 秒；66 次调用；Read 60；Bash 5；失败 0 | 176.220 秒；48 次调用；Read 39；Bash 7；失败 0 | 多 10.876 秒（慢 6.58%）；调用少 18；Read 少 21 |

第一轮有 Skill 的两次失败发生在报告写完后的额外分析，不代表“打包—搜索—聚合区段定向读取—报告”主链没有完成。第二轮无 Skill 的一次失败来自带空格路径未正确引用。失败数仍需保留在逐轮数据中，不能从总结果中删除。

三轮有 Skill 都减少了 `Read` 次数，但耗时表现为一轮更快、两轮更慢，工具调用表现为一轮增加、两轮减少。Repomix 打包和聚合搜索会增加前置成本；仓库较小、入口已知或问题只涉及单个符号时，这项成本可能高于统一聚合带来的收益。

两组最终报告都识别出正式 CLI 入口、生产组合根、真实模型联网点和测试分层，核心结果质量相当。Skill 的主要增益是把探索方法固定为可重复的结构，而不是替模型给出答案。是否节省时间、调用次数或读取量，仍要逐轮判断。

结果质量与流程质量的分项判断

| 评价项 | 本次表现 | 可以得到的结论 |
|---|---|---|
| 报告覆盖 | 两组都覆盖目录、入口、调用链、模块、依赖和测试 | 两组都完成了任务主体 |
| 架构正确性 | 两组都识别出正式 CLI、生产组合根、真实模型联网点和测试分层 | 核心结果质量相当，不能宣称只有 Skill 得到正确答案 |
| 文件读取方式 | 无 Skill 为 59/58/60 次原文件 Read；有 Skill 为 52/39/39 次聚合区段 Read，原文件 Read 为 0 | Skill 改变了阅读组织方式，但回源仍需补充 |
| 工具调用 | 有 Skill 一轮增加 7 次、两轮分别减少 24 和 18 次 | 调用量收益方向不稳定 |
| 工具失败 | 三轮配对分别为 0 对 2、1 对 0、0 对 0 | 失败需要逐轮解释，不能用组名代替判断 |
| 总耗时 | 有 Skill 一轮快 13.43%，两轮分别慢 27.92% 和 6.58% | 不能承诺固定提速 |
| 重复运行稳定性 | 有 Skill 三轮采用“调用—打包—聚合搜索—聚合区段读取—报告”的相同主链 | 探索方法规范化稳定复现，这是本次最明确的流程收益 |

### 4.5 验收接手报告

接手报告的验收对象不是篇幅，而是结论、证据链和边界。报告即使列出了完整目录，只要没有区分正式入口与辅助脚本、离线测试与真实联网路径，就仍然不能支持后续维护。

项目接手报告验收表

| 验收项 | 通过条件 | 不通过信号 |
|---|---|---|
| CLI 入口 | 指出脚本注册位置、入口函数和后续调用链 | 只看到根目录 `main.py` 就认定为正式入口 |
| 生产组合根 | 指出 `build_application()` 及其组装的具体实现 | 只按目录名猜测模块职责 |
| 联网范围 | 定位真实客户端调用，并区分本地工具和测试替身 | 把依赖包存在等同于所有流程都会联网 |
| 测试范围 | 区分单元、契约、离线冒烟和真实连通检查 | 看到适配器测试就认定发送了真实请求 |
| 原文件核验 | 关键结论能够回到配置和源码重新确认 | 只引用聚合结果，无法确认排除项和实现细节 |
| 安全边界 | 把聚合文件按原仓库敏感级别处理 | 把安全扫描无命中当作无秘密保证 |
| 适用条件 | 说明何时值得聚合，何时直接搜索更短 | 把 Skill 当作所有仓库问题的固定前置步骤 |

一份合格报告应让下一位维护者沿着“注册入口—组合根—外部调用—测试替身”重新走通关键路径。聚合结果负责提供全局扫描入口，原文件负责确认最终事实；两者职责分开，才能同时保留探索效率和结论可信度。

## 第五章 Skill 实际应用与课程回顾

![三个 Skill 案例映射到任务选择接入评价与策略调整的课程回顾](https://typora-photo1220.oss-cn-beijing.aliyuncs.com/DataAnalysis/Leo/agent-skills-application-practical-intro/2026-07-23/ch05-01-daily-skill-review-1dccaf9d.png)

前三个案例给出了三类不同结果。第二章 2.5 解释对照结果支持 `find-skills` 的结果与流程均有改善；第三章 3.4 比较修复效果确认 `uv` 的两条路径都解决了冲突，但有 Skill 路径的文件职责和恢复顺序更稳定；第四章 4.4 比较阅读过程确认 `repomix-explorer` 规范了仓库探索方法，最终报告质量相当，效率收益却不稳定。

本章把这些结论收束成一套可迁移的方法：先从平时的工作任务中寻找适合引入 Skill 的对象，再核对 Skill 与任务是否匹配，写清接入边界，分别评价结果和流程，最后按重复任务中的表现调整使用范围。

### 5.1 建立任务清单

任务清单记录的是工作对象、易漏步骤、失败影响和验收条件，不是准备安装的 Skill 名单。步骤会重复、判断容易遗漏、失败后恢复成本较高的任务，更值得进入 Skill 选型；动作单一且路径明确的任务，直接使用普通工具通常更短。

平时的工作任务清单

| 任务类型 | 容易遗漏的环节 | 最低验收条件 | 初步判断 |
|---|---|---|---|
| 能力发现 | 需求拆分、候选身份、来源与采用边界 | 候选属于目标能力，并保留继续核验的入口 | 适合用专用 Skill 组织搜索与核验 |
| 依赖恢复 | 顶层声明、完整解析、环境同步与再次重建 | 真实依赖保留，干净环境能够沿固定产物恢复 | 适合用 Skill 固定恢复顺序 |
| 仓库接手 | 正式入口、生产组装、外部调用与测试边界 | 重要结论能够回指配置和源码 | 大范围探索时更适合引入 Skill |
| 单点读取 | 目标路径已经明确 | 读取指定对象并回答当前问题 | 优先直接搜索或读取 |

每项任务还要补一条失败恢复入口。能力发现需要保留替代关键词与候选核验位置，依赖恢复需要知道失败发生在声明、解析、同步还是检查环节，仓库接手需要保留搜索命中与原文件位置。恢复入口越具体，Skill 越容易把经验转成可重复流程。

任务清单应先于 Skill 选择完成。若任务目标、允许动作和验收条件仍然含糊，我们无法判断某个 Skill 是真正匹配，还是只因为名称相近而被选中。

### 5.2 选择合适 Skill

Skill 选择首先核对任务匹配度，再看流行度或推荐信号。我们需要读清触发条件、排除场景、依赖工具、权限范围、写入对象和预期产物，确认这套工作流解决的正是任务清单中的问题。

Skill 选择核对表

| 核对项 | 需要确认的内容 | 不匹配信号 |
|---|---|---|
| 触发条件 | 当前任务是否属于 Skill 明确覆盖的工作 | 只因名称相近就触发 |
| 排除场景 | 任务是否落在 Skill 明确不处理的范围 | 单点问题却引入完整探索流程 |
| 依赖工具 | 所需命令、网络和运行环境是否可用 | 关键依赖缺失且没有恢复路径 |
| 权限与写入 | 读取、修改、安装和外部访问是否符合任务边界 | Skill 要求的动作超出授权范围 |
| 产物与验收 | Skill 产物能否直接接受当前任务的验收 | 产物形式完整，却没有回答原任务 |
| 规则来源 | 经验性阈值与工具的官方能力分别标记 | 把 Skill 内部建议写成普遍保证 |

中文说明可以帮助我们理解工作流，命令、限制与写入范围仍应回到原 Skill 内容核对。翻译不会扩大权限，也不会改变依赖工具的真实行为。

Skill 中的经验性阈值只表示这套工作流采用了某个判断标准。只有工具本身明确提供的能力才能写成工具事实；任务规模、仓库大小和输入边界变化后，经验阈值也需要重新评价。

### 5.3 接入当前任务

任务提示负责提供具体上下文，Skill 负责补充处理顺序。一次完整接入要写清任务主体、允许动作、禁止动作、目标产物和验收标准，再明确要求使用当前项目中的目标 Skill。

三个案例的接入重点

| 任务 | 任务主体与目标 | 允许与禁止 | 产物与验收 |
|---|---|---|---|
| 能力选型 | 为八类工作寻找开源 Agent Skill | 允许搜索与读取；禁止安装候选 | 报告写清候选身份、来源线索、项目级建议和待核验项 |
| 依赖修复 | 保留真实依赖并恢复 Python 3.12 环境 | 允许调整依赖声明与重建环境；禁止删包绕过冲突和执行业务脚本 | 顶层声明与解析结果职责分开，干净环境能够再次重建 |
| 仓库接手 | 识别入口、组装、外部调用和测试范围 | 允许只读探索与生成报告；禁止修改源码、依赖和配置 | 报告覆盖核心问题，重要结论能够回指原文件 |

这三类接入方式共享同一原则：Skill 不能替代项目上下文，也不能替我们完成最终判断。即使 Skill 已经进入任务，候选是否值得采用、依赖产物是否能够恢复、仓库结论是否可信，仍要由任务验收逐项确认。

接入说明还要保留失败处理。目标 Skill 没有被调用时，当前结果不能计入 Skill 效果；依赖工具不可用时，任务应停在可诊断位置；聚合输出不完整时，仓库结论要回到直接搜索与原文件读取。

### 5.4 复盘双重提升

双轴复盘先判断产物是否更准确、完整、可复核或可复现，再判断工具顺序、失败定位、维护边界和恢复路径是否改善。结果提升与流程提升可以同时成立，也可以只成立其中一项。

三个项目的双轴复盘

| 案例 | 结果评价 | 流程评价 | 证据边界 |
|---|---|---|---|
| `find-skills` | 第二章 2.5 解释对照结果支持结果改善：候选类型更贴近 Agent Skill 选型任务 | 第二章同一节支持流程改善：专用搜索路径更聚焦，完整配对中工具失败更少 | 无 Skill 第二次调用卡住且没有完整结果，不计入任何统计，包括样本数、耗时、工具调用、失败数和比例 |
| `uv` | 第三章 3.4 比较修复效果确认两组都解决了依赖冲突 | 有 Skill 路径分开顶层声明与解析结果，并多次复用编译、同步和重建顺序，职责分离与流程稳定性更好 | 现有结论不支持固定提速或固定减少调用 |
| `repomix-explorer` | 第四章 4.4 比较阅读过程确认两组最终报告质量相当 | 有 Skill 三轮稳定复现“调用 Skill → Repomix 打包 → 聚合搜索 → 定向读取 → 生成报告” | 效率收益不稳定，并且受到任务规模、入口是否明确和问题范围的影响 |

复盘记录至少保留任务输入、使用的 Skill 内容、关键产物、异常项和最终判断。卡住、缺少完整结果或验证深度不同的运行应单独标记，不能为了得到整齐的平均值而强行配对。

双轴结论应写成具体变化。比起笼统地说“Skill 有效”，更准确的表达是“候选类型更对题”“声明与解析职责更清楚”或“探索方法稳定复现，但效率收益不稳定”。

### 5.5 调整使用策略

使用策略由重复任务中的稳定表现决定。结果改善明显、流程也能稳定复现时，可以把 Skill 固化到项目级工作流；结果正确但流程成本增加时，应缩小触发范围；任务不匹配时，则回到通用处理方法。

Skill 使用范围调整

| 观察结果 | 策略动作 | 应用方式 |
|---|---|---|
| 结果改善明显，流程稳定复现 | 固化 | 写入项目级工作流与任务提示模板，并保留验收卡 |
| 结果正确，部分流程更清楚，但额外成本较高 | 缩小范围 | 只在高恢复成本或多步骤任务中触发，保留有价值的检查动作 |
| 收益随任务规模变化 | 增加触发条件 | 大范围探索使用 Skill，已知路径和单点问题直接搜索或读取 |
| 任务目标与 Skill 不匹配 | 停用 | 回到通用方法，不为证明 Skill 有效而改变任务目标 |

策略调整不等于修改 Skill 才算改进。我们也可以保留其中一段有价值的检查顺序，缩小自动触发条件，或只在特定任务规模下使用。范围越清楚，额外步骤越不容易抵消 Skill 带来的流程收益。

任务边界发生变化后，原有结论需要重新进入双轴评价。一个适合大范围仓库探索的 Skill，不会因此自动适合已知文件的一次读取；一个适合重复依赖恢复的工作流，也不代表每次简单装包都要走完整闭环。

### 5.6 三个项目回收

三个项目共同完成了“选择—接入—结果评价—流程评价—调整”的方法回收。它们不是三个工具的排名，而是同一套判断方法在不同任务中的三种结果。

三个项目到应用方法的映射

| 案例 | 选择 | 接入 | 结果与流程评价 | 调整 |
|---|---|---|---|---|
| `find-skills` | 任务需要寻找可安装的 Agent Skill，而非普通工具 | 明确使用项目级 Skill、禁止安装并要求生成选型报告 | 结果与流程均改善，但采用前仍需逐候选核验 | 保留任务拆分、专用搜索与候选核验流程 |
| `uv` | 任务包含声明、解析、同步和重建等重复环节 | 固定真实依赖、禁止删包绕过，并要求留下可重建产物 | 两组都成功；有 Skill 路径的职责分离和流程稳定性更好 | 保留声明、解析、同步与重建的分工 |
| `repomix-explorer` | 任务需要大范围理解陌生仓库和跨文件模式 | 限制为只读探索，要求报告结论回指原文件 | 三轮主链稳定、最终质量相当，效率收益不稳定 | 大范围探索继续使用；小仓库、已知入口或单点问题改用直接搜索 |

这三种结果修正了“只要用了 Skill，任务就一定更好”的判断。Skill 可以同时改善结果与流程，也可以主要改善职责和稳定性，还可能只规范方法而没有稳定效率收益。

课程开始时建立的双轴评价卡在这里完成回收。选择 Skill 之前用它写任务与边界，任务完成后用它验结果、评流程、记异常，再把结论反馈到下一次触发范围。

### 5.7 应用判断收束

最终检查单把整套方法压缩为五项判断。每项都要落到当前任务的产物和过程证据，不能只用“已经调用 Skill”作为回答。

Skill 应用最终检查单

| 判断项 | 通过条件 | 下一动作 |
|---|---|---|
| 任务选择 | 任务包含可复用步骤、易漏判断或较高恢复成本 | 进入 Skill 匹配；否则直接使用普通工具 |
| Skill 接入 | 触发、排除、依赖、权限、产物与任务边界一致 | 写清目标、动作、禁止、产物和验收 |
| 结果评价 | 产物在正确、完整、可复核或可复现方面出现明确改善 | 保留支撑结论的报告、文件和检查结果 |
| 流程评价 | 顺序、定位、维护边界或恢复路径出现明确改善 | 逐项记录收益与额外成本，不单看调用数量 |
| 策略调整 | 重复任务能够确认收益是否稳定 | 按证据固化、缩小范围或停用 Skill |

有 Skill 不等于结果必然更快、调用必然更少或结论必然更正确。Skill 的核心价值，是把成熟的工作方法带进平时的工作任务，并让结果质量或执行流程中的具体变化能够被复核。

下一项平时的工作任务开始前，我们先完成任务清单和 Skill 匹配；任务结束后，再填写双轴评价卡。反复沿着“选择 Skill—接入任务—比较结果—复盘流程—调整使用范围”推进，Skill 才会从一次调用变成可以持续改进的工作方法。
