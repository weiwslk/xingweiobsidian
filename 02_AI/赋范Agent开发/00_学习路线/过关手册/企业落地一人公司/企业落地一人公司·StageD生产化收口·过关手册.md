> 面向「企业落地 / 一人公司」路径 Stage D（评估、驾驭工程与上线验收）。这一阶段的四个节点：D1 给场景服务装评估体检、D2 用 Harness 驾驭工程把 Agent 约束到可控、D3 用项目 AGENTS.md 做一次交付验收、D4 把整套方法复制到第二场景。

## 一、随堂练习

### D1 评估与优化：给你的场景服务装上体检

**练习 1．背出可复现三件套，并说清各挡住什么。**
【参考答案】三件套是：固定时间、每例重置、串行。固定时间把"当前时间"钉成一个常量（记账评估里是 `2026-06-04T12:00:00`），否则"上周三"今天跑和明天跑指向的日期不同、参考答案对不上；每例重置是每条用例跑前 `reset_db(seed=True)` 把账本恢复成同一份种子，防止上一条记的账污染下一条；串行靠 `max_concurrency=1` 强制，因为所有用例共用一个评估库、每条跑前都重置，并发会几条同时重置、同时写导致账本乱。三件套缺一份成绩单就不能拿来做版本回归对比。
【自查要点】能分别说出每件挡住哪种破坏；知道三件套落在 `backend/eval/shared.py`，串行那件落在各套 `run_eval.py` 的 `evaluate(..., max_concurrency=1)`。
<!--src:A; ref:Stage5/05《Agent评估与优化》3.2可复现性; code:backend/eval/shared.py-->

**练习 2．评估器的返回结构是什么？「不适用」这条用例怎么处理，为什么这样设计？**
【参考答案】评估器统一返回三字段 `{"key": 指标名, "score": 分数, "comment": 说明}`。遇到不适用当前用例的评估器返回 `score=None`，LangSmith 聚合时自动跳过、不计入分母。设计上核心集把 13 个评估器合并成一个 `evaluate_all`，只保留 `score` 非 None 的适用指标；否则每条用例会产生 13 条记录、大半是"不适用"占位，看起来刷屏；合并后每条用例只产 1 条记录，查询类只看到工具选择和数据依据几项，记账类才看到金额、余额、轨迹那些。
【自查要点】能写出三字段名；知道 None 是"跳过"不是"0 分"；知道合并的目的是只报适用指标。
<!--src:A; ref:Stage5/05《Agent评估与优化》3.4写评估器; code:backend/eval/core/evaluators.py-->

**练习 3．`budget_alert` 这个指标判 1 需要满足几个条件？为什么收得这么紧？**
【参考答案】两个条件都要满足才算 1：一是 Agent 真调了 `check_budget` 去核实预算，二是最终回答里出现明确的提醒措辞（"超支/超出/接近预算"等）。只查不提醒用户看不到、只喊"超了"却没查等于没核实，缺一即判 0。收紧是因为业务上"超支提醒"这件事必须既有依据（查过）又有结果（说了），任缺一环都不是真闭合的提醒。记账 Agent 优化前这一项是 0.00，是它最严重的短板。
【自查要点】能说出「查预算 + 提醒措辞」两个条件；知道优化前该项 0.00。
<!--src:A; ref:Stage5/05《Agent评估与优化》3.4写评估器; code:backend/eval/core/evaluators.py-->

### D2 Harness 驾驭工程：把 Agent 行为约束到可控

**练习 4．写出八大故障模式清单（编号 + 名称）。**
【参考答案】①循环失控 ②context 溢出 ③cache miss ④tool 错误吞 ⑤状态丢失 ⑥缺权限闸 ⑦缺自动化评审 ⑧成本失控。这张清单是整门驾驭工程课的问题轴，八大核心机制每一个都对应其中某一条。
【自查要点】八条能 30 秒背出；知道机制是照着故障清单一条条解出来的，不是凭空的最佳实践。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part1第五章-->

**练习 5．Prompt Cache 三铁律是哪三条？违反了会怎样？**
【参考答案】三条：运行中不许改 tools 定义、不许中途重载 memory、不许中途重建 system prompt。原理是 toolset 与 system prompt 共同构成前缀缓存的 key，前缀任何改变都会让已缓存的 token 全部作废。典型踩坑是把时间戳、用户名、当前任务写进 system prompt，以为让模型"知道现在在做什么"更好，实际上每轮前缀都不同、缓存全部失效，延迟和费用双双翻倍，长任务里可能多烧数十美元。
【自查要点】三条都能说；能点出"改前缀 = 缓存作废"这个根因；知道对应故障模式③ cache miss。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part2第四章4.2-->

**练习 6．Mini Harness 里 `dispatch_tool` 碰到工具执行报错怎么处理？为什么不能直接抛异常或 `try...except: pass`？**
【参考答案】`dispatch_tool` 既不让主系统崩溃、也不吞掉异常，而是把捕获到的报错包进一个结构化 JSON、形如 `{"error": "具体报错原因"}`，作为工具执行结果原样回传，写进模型的历史上下文。直接抛异常会让 Agent 当场死机、丢掉长程对话；`try...except: pass` 会让模型以为工具成功、基于错误假象继续瞎编。结构化回传后，模型下一轮看到 `error` 字段会像人一样醒悟并自觉改参数重试，这就是它软着陆和自愈的基础，对应解故障模式④ tool 错误吞。
【自查要点】能说出"结构化回传而非抛/吞"；知道两条老路各自的坏处；对应故障④。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part2第二章2.2; code:mini_harness/harness/core.py-->

## 二、误区自查

以下 8 条，读完在心里各判一次"我是不是这么想的"，中招的回对应节点补课。

1. **误区**：评估分数每次都在跳，一定是我优化起了作用或没起作用。→ 大模型本身带随机性，`temperature=0` 也可能因后端路由让分数小幅浮动。要先用可复现三件套把环境噪声摁住，剩下的抖动才是模型自身的。分不清是改动效果还是环境没对齐，成绩单就不能比。
<!--src:A; ref:Stage5/05《Agent评估与优化》3.2可复现性-->

2. **误区**：有唯一正确答案的题（比如算数、余额），用大模型当裁判判对错最稳。→ 反了。大模型判对错要自己把题再算一遍，它本身就可能算错。有唯一答案用规则裁判（字符串比对 / 数值比对），又快又准又零成本；只有主观、开放的输出（措辞得不得体、拒绝解释到不到位）才请 LLM-as-judge。
<!--src:A; ref:Stage5/05《Agent评估与优化》2.8人工标注-->

3. **误区**：成绩单里 Outputs 列就是 Agent 的原始完整回复。→ Outputs 列展示的是 `target` 返回的可评估包（含 `final_answer`、`tool_calls` 等），不是 Agent 原始回复全文。想看它怎么一步步干活，要点进 trace 看调用树，而不是盯着 Outputs 列。
<!--src:A; ref:Stage5/05《Agent评估与优化》3.5跑核心集-->

4. **误区**：面对一份成绩单的低分，直接换个更强更贵的模型就对了。→ 先分"指导不足 vs 能力不足"。相对日期不调工具、记完账不报预算这类，是"模型有能力、只是没被告知该怎么做"，靠写细 prompt 和工具说明就能补，性价比最高、优先做；只有多轮指代这种模型能力天花板才值得换更强的模型。把优化的钱花在刀刃上。
<!--src:A; ref:Stage5/05《Agent评估与优化》4.4三个杠杆各管什么-->

5. **误区**：驾驭工程就是给 prompt 做好组装（scaffolding），把提示词拼漂亮就等于做好了 harness。→ scaffolding 只是 context 装配层的一个子集，属于 harness 的一部分。真正的 harness 必须覆盖 context 装配 + runtime 执行 + 长任务保护三层。判断一个系统是不是完整 harness，看它有没有：循环终止刹车、跨会话进度续传、真机功能验证，三者缺一就不是。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part1第三章3.2-->

6. **误区**：工具函数只要返回 `result.stdout` 就够了，返回码可以不管。→ naive agent 的经典坑：`run_pytest` 只返回 stdout、把 `result.returncode` 丢了，于是即使 pytest 失败（exit code 非 0），Agent 拿到的也只是段字符串，会以为任务成功、继续在错误基础上操作，最后交付一份"通过了但实际没过"的烂代码。工具返回必须含布尔成败标记。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part1第五章5.1-->

7. **误区**：父 Agent 上限 50 步、子 Agent 上限 50 步，最坏也就 50 + 50 = 100 步。→ 父子迭代步数是乘法不是加法。1 个父派 5 个子、每个子上限也 50 步，最坏是 250 步；父子都 50 就是 50 × 50 = 2500 步。这是 Manus 早期版本的真实教训。子 Agent 必须有独立且比父更小的步数上限（推荐父 50、子 10）、结果长度上限、成本上限三道防线。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part2第七章7.2-->

8. **误区**：上线验收让 Agent 帮我把 AGENTS.md 的验证标准逐条打勾就行，省事。→ 验收是交付前人签字的最后一道环节，通过/不通过的判定和签字只能你自己来。Agent 可以帮你把证据摆齐（接口响应、容器起停日志、评估数值、约束用例），但"打勾"这个动作是深潜专属、要关掉 Agent 代做的。
<!--src:A; ref:business-landing#D3-->

## 三、迁移挑战

**迁移 1．你选的是运维场景（ff-sre-incidentops），不是记账。课件的评估四套是围绕记账 Agent 的，你怎么把这套评估搬到运维服务上？**
【参考答案】骨架原样复用，只换业务件。评估模板是一份可复现的 shared 公共层 + 一套 `cases.csv`（题库）+ `create_dataset.py`（导入）+ `evaluators.py`（评估器）+ `run_eval.py`（跑分）的四件套结构，加一个评估驱动优化的飞轮。搬到运维场景要做三件替换：① 题库 `cases.csv` 换成真实告警 / 事故用例，参考答案换成"该聚合成哪个事故、该给什么处置建议"；② 评估器换成运维关心的判分（是否调对只读诊断命令而非误调危险命令、事故定位是否基于真实日志而非编造、处置建议是否可执行）；③ 可复现三件套照旧（固定时间、每例重置到同一份告警快照、`max_concurrency=1` 串行）。第一章那张"特殊评估角度 × Agent 类型"表告诉你，运维这类 Agent 要额外挑"外部系统状态变更评估""用户确认与副作用控制评估"叠加到通用七类上。
【自查要点】能说出四件套骨架不变、只换题库+评估器+参考答案；知道运维要叠加"副作用控制/状态变更"等特殊角度；可复现三件套与场景无关。
<!--src:A; ref:Stage5/05《Agent评估与优化》5.5下一步往哪走; pack:agent-evaluation-pack-->

**迁移 2．公司数据不能出内网，不让用 LangSmith。你怎么给场景服务做评估？**
【参考答案】真正值钱的是评估方法论（题库 + 多维评估器 + 可复现环境 + 多维成绩单 + 优化飞轮），LangSmith 只是承载它的平台，换掉它方法论一字不变。有两条路。第一条换自托管开源平台，含 Langfuse（MIT、自托管一等公民）、Arize Phoenix（OpenTelemetry 原生、自带评估指标库）、Opik（Apache 2.0），私有化部署在公司服务器上，数据全程不出内网。第二条纯自建轻量 harness，即 `cases.csv` + `evaluators.py`（返回 `key/score/comment`）+ 一个 run 脚本（跑 Agent、逐条打分、汇总各指标均分），结果存 CSV 或写库。第二条最轻，特别适合塞进 CI：每次改完自动跑一遍题库，分数低于阈值就卡住合并，把评估变成回归门禁。要观测面板和人工标注队列就选自托管平台，只要 CI 里跑个回归门禁纯 Python harness 最省事。
【自查要点】能说出"方法论与平台解耦"；能各举一条自托管平台和纯自建路子；知道纯自建能塞进 CI 当回归门禁。
<!--src:A; ref:Stage5/05《Agent评估与优化》5.4不用LangSmith怎么做内部评估; pack:agent-evaluation-pack-->

## 四、排错挑战

**场景**：你给选定场景服务加了 Harness 驾驭约束，用「记完账必须调 check_budget 报预算」这条规则加进 system prompt。跑起来后发现服务在某些请求上迟迟不返回、token 疯涨，账单吓人。翻 LangSmith 的 trace 瀑布图，看到同一句"已记账、预算正常"配着 `check_budget` 调用一遍遍转个不停。

下面是加规则的 prompt 片段（有问题的版本）：

```text
# system prompt 工作规范（有问题的版本）
- 记完一笔支出后，必须调 check_budget 看预算，near/over 就提醒用户。
```

【症状】服务对部分请求不返回、耗时和 token 异常增长；trace 瀑布图里 `check_budget` 被同一轮反复调用，Agent 一边给出最终回答、一边又回头再调工具，陷在原地空转（对应八大故障模式①循环失控）。

【根因】规则只说了"必须调 check_budget"，没说"调几次、调过要不要停"。模型每轮都读到"必须调"这条硬要求，于是给完回答后又觉得还得再调一次，卡进"回答，再调，再回答"的回环出不来。这不是模型坏了，是驾驭约束写得不封口，缺了终止条件。

【修法】两条一起上：① 把 prompt 收紧成有终止条件的版本，即"记完一笔支出后调一次 check_budget 看预算（只调一次，调过别再调），near/over 就提醒用户，否则正常回答，不要重复调用工具"；② 在 Agent Loop 外围保留硬刹车兜底：`while steps < config.max_steps`（课件默认 `max_steps=50`）+ Token Budget（`BudgetGuard`，超上限触发优雅终止），即使某次 prompt 又没封住，也不会无限烧钱。改完重跑评估，用 Comparison 并排比，确认这一项修好、且原本满分的指标没被改坏。

```text
# system prompt 工作规范（修好的版本）
- 记完一笔支出后，调一次 check_budget 看预算（只调一次，调过别再调），
  near/over 就提醒用户，否则正常回答——不要重复调用工具。
```

## 五、面试自测

10 题，每题闭卷答完再看要点；每题带一层追问，追问答不上说明这块还没吃透。

**面试 1．请解释「Agent = Model + Harness」这个公式，并说清 Harness 到底在解什么问题。**
【考察点】对驾驭工程定位的理解，即差距的根源在 harness 层而非模型。
【答题要点】Model 是引擎，Harness 是底盘变速箱刹车方向盘；引擎再强，没底盘刹车跑不远。Harness 系统性地应对 naive agent 的八大故障模式（循环失控、context 溢出、cache miss、tool 错误吞、状态丢失、缺权限闸、缺自动化评审、成本失控）。有硬数据：同模型只改 harness，Terminal Bench 2.0 从 52.8% 提到 66.5%，+13.7 个百分点，说明 harness 是可量化的工程变量，不是玄学。
【追问】那 harness 是不是就是几十年前的 feedback control 换个名字？→ 不是。feedback control 没人能给你看 +13.7pp 的 benchmark 曲线，也没有公司敢说用它写了约百万行零人工代码；它是一个已经能拉出硬数据的新工程学科，不是换皮。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part1第一章/第二章-->

**面试 2．评估一个 Agent 为什么比测传统程序难？**
【考察点】对"Agent 评估难在哪"的系统认识。
【答题要点】传统程序有标准答案，输入 2 加 3 断言必须返回 5，用 `==` 就能判。Agent 不一样：输出是自然语言 + 一串调工具的动作，同一问题有多种都算对的答法，没法简单比对；它分多步走，中间调错工具、漏步、绕路，哪怕最后蒙对过程也是坏的，要看清就得记完整轨迹；大模型带随机性，今天对明天可能错；它会真删数据改状态，越界就是实打实破坏；多轮里还得记上文；每改一次 prompt 或换模型都可能"修好 A 弄坏 B"。所以"凭感觉觉得它还行"靠不住，需要一套评估角度加一个能记录、批量打分、版本对比的平台。
【追问】那"看清过程"具体靠什么？→ 靠 trace（完整执行轨迹）。过程轨迹评估要看有没有漏步、绕路、重复、死循环，这些判断的原始数据全在调用树里；没有 trace，轨迹无从评起。
<!--src:A; ref:Stage5/05《Agent评估与优化》开篇/1.3过程轨迹评估-->

**面试 3．通用七类评估角度是哪七类？记账 Agent 的四套评估分别回收了哪几类？**
【考察点】评估认知地图 + 落地映射。
【答题要点】通用七类：1.1 任务结果、1.2 工具与动作、1.3 过程轨迹、1.4 依据与状态一致性、1.5 多轮交互与状态保持、1.6 规则安全与权限、1.7 抗扰稳定性与回归稳定性。四套映射：核心集回收 1.1/1.2/1.3/1.4；多轮集回收 1.5；安全集回收 1.6；稳定集回收 1.7 的抗扰部分，回归部分靠第四章优化前后的 Comparison 并排对比。
【追问】1.7 里"抗扰"和"回归"有什么区别？→ 抗扰看 Agent 扛不扛得住模糊 / 异常 / 工具失败等奇怪输入；回归看每次改 prompt、换模型后会不会"修好 A 弄坏 B"，靠 Experiment 版本对比来测。
<!--src:A; ref:Stage5/05《Agent评估与优化》第一章/5.1七类覆盖度自检-->

**面试 4．LangSmith 四大功能块各管什么？分别承接哪类评估？**
【考察点】平台四块与评估角度的对应。
【答题要点】Tracing 记录单次运行完整轨迹，是过程轨迹评估的数据来源；Datasets & Experiments 用题库批量打分出成绩单，承接任务结果 / 工具动作 / 依据等的批量量化；Comparison，把多个版本成绩单并排比，承接抗扰稳定性与回归稳定性评估；Annotation Queues，人工逐条打分校准机器裁判，给自动评分做人工对齐。
【追问】接入 LangSmith 要改多少业务代码？→ 几乎不改。补四个环境变量（`LANGSMITH_TRACING` / `LANGSMITH_API_KEY` / `LANGSMITH_PROJECT` / `LANGSMITH_ENDPOINT`）+ 在业务入口加一行 `@traceable` 装饰器就够了，业务逻辑一字未动。
<!--src:A; ref:Stage5/05《Agent评估与优化》2.1/2.3-->

**面试 5．记账 Agent 优化前的低分主要集中在哪几块？三个杠杆各修哪一类？**
【考察点】评估驱动优化的定位与选杠杆能力。
【答题要点】短板集中三块：① 该用工具时不用、该走的流程没走（相对日期不调 `resolve_date` 导致 date_correct 0.20、记完账不调 `check_budget` 导致 budget_alert 0.00）；② 拿到工具结果不如实复述（data_grounded 0.25、format_valid 0.40）；③ 多轮指代和安全边界（context_resolved 0.17、dangerous_blocked 0.50）。三杠杆：写细 system prompt + 写清工具说明（docstring）修"指导不足"，性价比最高优先做；换更强的模型（coder-flash 换成 deepseek-v4-pro）修"能力不足"，最典型是多轮指代 context_resolved 从 0.17 拉到 1.00。
【追问】参数抽取（金额、账户、余额）为什么不在优化靶子里？→ 因为它本来就满分。优化只打有提升空间的低分项，参数抽取模型本来就做得对，动它没意义；而且回归时要确认这些原本满分的项优化后依然满分，没被改坏。
<!--src:A; ref:Stage5/05《Agent评估与优化》4.2定位低分/4.3三杠杆-->

**面试 6．「指导不足」和「能力不足」怎么分？为什么这个区分值钱？**
【考察点】优化决策的核心判据。
【答题要点】指导不足指模型有能力、只是没被告知该怎么做，靠写清 prompt 和工具说明就能补，便宜快；而能力不足指提示词再细、模型也补不动（比如跨轮记忆、实体定位），得换更强的模型，贵但能突破上限。值钱是因为它让你分得清哪些花小钱能修、哪些必须花大钱换模型；正确顺序是先想能不能靠 prompt 和工具说明补，补不动的、属于能力天花板的再换模型，把钱花在刀刃上。
【追问】举一个"再怎么写 prompt 也补不动"的例子。→ 多轮指代 context_resolved。用 coder-flash 时怎么写 prompt，它在"把刚才那笔改成…"这种跨轮指代上还是会找错记录甚至反复查工具空转，只有换上跨轮记忆更强的模型才真正补上。
<!--src:A; ref:Stage5/05《Agent评估与优化》4.3/4.4-->

**面试 7．驾驭工程的三支柱是什么？各回答什么核心问题？**
【考察点】评价 harness 机制的坐标系。
【答题要点】三支柱：Context Engineering（Agent 能看见什么信息、是否准确精简）、Architectural Constraints（Agent 能做什么、不能做什么、动作空间边界在哪）、Garbage Collection（Agent 能跑多久、成本和资源怎么回收）。判断规则：一个机制在整理输入信息就归第一柱、在约束能力或交互边界就归第二柱、在清理过期状态 / 限成本 / 回收资源就归第三柱。
【追问】Permission Gate（权限闸）主要落在哪一柱？→ Architectural Constraints。危险操作拦截是在约束 Agent 的动作空间边界，属架构约束这一柱。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part1第七章-->

**面试 8．Verification Loop（验证闭环）解决什么？它和「工具层结构化错误回传」的区别在哪？**
【考察点】对"真机验证 vs 工具错误显性化"两层的区分。
【答题要点】Verification Loop 解决的是"LLM 自评不可信"，做法是每个任务完成后用 pytest / Playwright 这类外部工具真机验证功能，`verify_by_pytest` 里 `passed` 和 `exit_code` 来自 subprocess 真实返回码，LLM 无法伪造；验证失败就回退重做，通过才标 `passed=True`。区别：结构化错误回传是工具调用本身出错时、由工具执行层确保错误不被吞掉；Verification Loop 是工具调用成功之后、由独立验证工具确保结果本身正确。一个管"错误别丢"，一个管"结果是真对"。
【追问】为什么不能让 Agent 自己说"我测过了、通过了"？→ 一段代码只有被真实执行过才算被验证过，LLM 的自我确认没有验证效力，会陷入自评的循环论证。测试是唯一的真相来源。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part2第六章-->

**面试 9．Mini Harness 的 E2E 实测里，Full Harness 相对 Baseline 多花了多少 token 和耗时？这些成本换来了什么？**
【考察点】对 harness 真实代价的诚实认知。
【答题要点】实测：Baseline 单轮 1104 tokens、1 步、35.45 秒；Full Harness 15053 tokens、7 步、94.02 秒，约合 13.6 倍 tokens、2.65 倍耗时（本次成本约 $0.0697，低于 $0.50 预算上限，budget 未触发）。这不是 harness 效率低，是它的成本结构：13 倍 tokens 换来 Baseline 永远买不到的三性，即可观察性（progress.md 落盘 7 条记录、每步可追溯）、可干预性（Permission Gate 就绪，危险命令执行前被拦）、可控性（Token Budget 守住上限、异常时优雅终止不无限烧钱）。凡是需要追溯、拦截、兜底的任务，这个成本就是必要的。
【追问】那是不是所有任务都该上 harness？→ 不是。成本直觉建立后要判断"这个任务值不值得上 harness"。harness 会随模型变强而 go stale，harness 是工具不是信仰，只在需要三性的任务上用。
<!--src:A; ref:Stage4/07《Harness Engineering驾驭工程实战》Part2第十章/第十一章-->

**面试 10．上线验收时，AGENTS.md「部署完成的验证标准」怎么用？为什么这一步必须你亲自签字？（关掉 Agent 代做）**
【考察点】交付验收的人签字纪律。
【答题要点】把选定场景项目 AGENTS.md 的「部署完成的验证标准」逐条列出，为每条准备可核对的证据（含接口响应、容器起停日志、评估指标、约束用例），你自己逐项核对并逐项打勾签字，缺项写"本场景不适用及原因"。报告还要附 D1 评估指标实测值 + D2 驾驭约束验证结论。必须亲自签字，是因为验收是交付前人签字的最后一道环节，Agent 可以把证据摆齐，但"通过 / 不通过"的判定和签字只能你来，这是深潜专属、要关掉 Agent 代做的。
【追问】以 ff-sre-incidentops 为例，说一条你会亲手 curl 核对的健康检查。→ `curl -fsS` 后端 `/api/health`（端口 8016）应返回 `{"status":"ok","product":"FF-SRE 智能运维事故管理平台"}`。
