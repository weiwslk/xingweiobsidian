## 一、随堂练习（动手小题）

### D1 · Agent Skills 详解：原理到从零开发
> 来源讲次：《大模型 Agent Skills 基础入门》第一至四部分 /《大模型 Agent Skills 设计实战》第二至九章

**练习 D1-1｜一句话说清 Skill 是什么，再说清它的三大特性**
课件给 Skill 下了一个一句话定义，还提炼了贯穿全课的三个关键词。请把定义和三大特性都写出来，并各配一句话解释。

- 【参考答案】
  - 定义：**Skill 是一个可被 Agent 在运行时发现、理解、调用和组合的能力模块**（四个动词构成完整生命周期）。
  - 三大特性：**可发现**（Agent 能知道这个 Skill 适合什么任务，靠清晰的 description 被路由识别）、**可执行**（进入后不是自由发挥，有结构化 Workflow 支撑）、**可复用**（同一份能力跨场景、跨任务、跨时间反复使用和优化）。
- 【自查要点】记住课件那句总结：Skill 不是"更长的 Prompt"，而是"可发现、可执行、可复用的能力模块"。后面所有内容都围绕这三个词展开。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 基础入门》1.2 核心定义 / 1.3 三大特性-->

**练习 D1-2｜三种技能结构对号入座**
课件用三个真实案例讲了三种复杂度的 Skill 结构。请填出每种结构的代表案例和文件组成。

- 【参考答案】
  - 简单技能：`commit-message-generator`，**仅 SKILL.md**、无外部依赖、3-5 步线性流程。
  - 多步骤工作流技能：`test-driven-development`，**仍是仅 SKILL.md**，但 Workflow 有 5-10 步、含分支逻辑。
  - 资源依赖型技能：`lesson-interaction-architect`，**SKILL.md + 同级资源目录**（scripts/、templates/ 等），10+ 步、需调脚本和模板。
- 【自查要点】关键区分：前两种都只有一个 SKILL.md，差别在 Workflow 的复杂度；只有第三种才需要外置资源目录。这体现"简单优先、按需复杂"的设计哲学，不是所有 Skill 都要塞满目录。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 基础入门》1.5 三种技能结构对比-->

**练习 D1-3｜写出边界四问（动笔前必答）**
能力包 `agent-skills-authoring-pack` 要求：拿到"写个 Skill"的需求，动笔写 SKILL.md 之前先答四个问题。请把这四问默出来，并标出最常被漏的那一问。

- 【参考答案】
  1. 这个 Skill 解决的"重复出现的问题"是什么？（一句话，说不清就还不该做成 Skill）
  2. 哪些用户请求"应该"触发它？（列 2-3 条自然口语）
  3. 哪些"相邻"请求"不应该"触发它？（**这条最常被漏，却是防误触发的关键**）
  4. 对使用者来说，什么算"成功"？（可验证的成功标准，不是"做得好"这种空话）
- 【自查要点】第 3 问是重点：只列"应该触发"、不列"不应该触发的相邻请求"，description 天然会变宽泛，后患就是触发污染。成功标准也别写"生成高质量结果"这种空话，要写成"摘要覆盖核心观点/关键数据/结论三部分"这类可检查项。
<!--src:A; ref:zero-to-builder#D1 pack:agent-skills-authoring-pack（定边界 skill-boundary-scoping）-->

**练习 D1-4｜用 SRP 三测试判一个 Skill 该不该拆**
课件给了三个交叉验证的测试来判断职责是否单一。请写出三个测试，并用 `ai-dev-assistant` 走一遍，得出结论。

- 【参考答案】
  - 一句话描述测试：用一句话描述功能，需要"和/或/以及"等连接词就不单一。
  - 变化原因测试：列出会导致它需要修改的原因，超过一个就不单一。
  - 调用场景测试：列出用户会在什么场景调它，场景之间没有强关联就不单一。
  - 走 `ai-dev-assistant`：它是"创建项目**和**生成文档**以及**运行测试"，一句话描述挂了；模板结构变、文档规范变、测试框架升级是三个变化原因；三个调用场景相互独立。三测试全挂 → 拆成 `project-init` / `doc-generator` / `test-runner` 三个 Skill。
- 【自查要点】三个测试任一不过就要拆。记住课件那句：**宁可多几个小 Skill，也不要一个大而全的 Skill**。别怕"Skill 数量爆炸"，合理拆分反而让系统更清晰。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 设计实战》3.1 单一职责原则 SRP-->

### D2 · 顶尖 Skills 实战：Spec-Kit 与 Superpowers（支线）
> 来源讲次：《顶尖 Skills 实战》Lesson 10 Spec-Kit 入门实战 / Lesson 12 Superpowers 基础入门·TDD 驱动开发

**练习 D2-1｜走一遍 Spec-Kit 的规范驱动流程**
D2 的过关物是用 Spec-Kit 把一个小需求拆成三件套。请写出这条规范驱动流程的关键阶段，并说明它和"直接让 Agent 写代码"的根本差别。

- 【参考答案】流程按 **specify（写规范）→ clarify（澄清）→ plan（做计划）→ tasks（拆任务）** 推进，产出 spec / plan / tasks 三件套且互相一致。根本差别是 **SDD（规范驱动开发）先规格、后代码**：先把"要做成什么样"定清楚，再让 Agent 照规范实现，而不是一上来就写代码、边写边猜需求。
- 【自查要点】过关标准是三件套齐全且互相一致（spec 里的要求在 plan 和 tasks 里都能对上）。Spec-Kit 是从 OpenSpec 演进来的 SDD 框架，重点是把需求收敛在规范里，减少返工。
<!--src:A; ref:zero-to-builder#D2 讲次《顶尖 Skills 实战》Lesson 10 Spec-Kit 入门实战-->

**练习 D2-2｜说清 Superpowers TDD 的红绿重构**
Superpowers 是以 TDD 为核心的规范驱动开发方法论。请说清 TDD 的核心节奏，以及"测试先行"为什么能约束 Agent。

- 【参考答案】核心节奏是 **红→绿→重构**：先写测试并确认它失败（红灯，证明测试有效）→ 写恰好能让测试通过的最小代码（绿灯）→ 在测试保护下重构提升代码质量。"测试先行"约束 Agent 是因为：绝对不许在写测试之前先写实现代码，每一步都有明确的通过/失败断言，Agent 无法跳过验证直接声称"应该能跑"。
- 【自查要点】课件的 NanoClaw Dashboard 起步项目就是靠一套 TDD 测试（面板状态机配套 42 个测试）驱动出来的。红灯这一步不能省：没见过测试失败，就不知道测试到底测没测到东西。
<!--src:A; ref:zero-to-builder#D2 讲次《顶尖 Skills 实战》Lesson 12 Superpowers 基础入门·TDD 驱动开发-->

## 二、误区自查（照镜子）

> 读法：如果你心里认同左边那句 X，说明你还没真正掌握 Y，去回看 Z。

1. **如果你以为「Skill 就是把 Prompt 写长一点、写详细一点」** → 说明你还没掌握 Skill 与 Prompt 的本质区别。Skill 是可发现、可执行、可复用的能力模块，Prompt 是散在对话历史里的一次性指令。回看 zero-to-builder#D1《大模型 Agent Skills 基础入门》1.4 Skill vs Prompt。

2. **如果你以为「给 Agent 的信息越多越好，把官方文档全贴进 SKILL.md 最省事」** → 说明你正在犯 `encyclopedia-translator`（复制粘贴文档）的错。2847 行文档只会让 Agent 迷失、执行变慢，关键执行步骤被淹没。回看 zero-to-builder#D1《设计实战》2.4 案例 3 与 3.3 信息精炼原则。

3. **如果你以为「一个全能开发助手 Skill 最方便，什么都能干」** → 说明你正在犯 `ai-dev-assistant`（万能瑞士军刀）的错。描述过宽会让 Agent 几乎任何请求都误触发它，还越改越难维护。回看 zero-to-builder#D1《设计实战》2.2 案例 1 与 3.1 单一职责原则。

4. **如果你以为「触发不准，那就去改 Skill 的执行流程」** → 说明你找错了根因。触发不准几乎都出在 frontmatter 的 description 过宽、缺正反示例约束，改执行逻辑是南辕北辙。回看 zero-to-builder#D1 能力包"触发准确性排障"与《设计实战》第 8 章。

5. **如果你以为「SKILL.md 写完、能跑起来，这个 Skill 就做完了」** → 说明你还没接受课件最重要的那句：创建只完成了 20%。触发准不准、输出稳不稳、要靠评估暴露、靠迭代解决。回看 zero-to-builder#D1《设计实战》第 9 章核心认知 1。

6. **如果你以为「description 只要把能做的事写清楚就够了」** → 说明你漏了负向触发器。好的 description 必须写明"不适用于 X（防误触）"，只写正向会导致触发污染。回看 zero-to-builder#D1 能力包坏设计红线与《基础入门》4.3 路由瘫痪。

## 三、迁移挑战（换个场景用同样方法）

**迁移挑战 1｜把"你整理周报的方法"做成一个合格的 Skill**
课件教的是通用方法，现在拿你自己的真实重复任务练手：把"我每周整理周报的方法"做成一个 Skill。要求先答边界四问，再用 SRP 三测试自检，最后写出 frontmatter（name + description，description 要带负向触发器）。

- 【怎么算过关】① 四问都能一句话答清，尤其第 3 问要列出 2-3 个"不该触发的相邻请求"（比如"写日报""做 PPT 汇报""分析周报数据"）；② name 用 kebab-case（如 `weekly-report-writer`）；③ description 里既有正向触发场景，又有一句"不适用于……（防误触）"；④ 用一句无连接词的话能描述它的职责。能做到这四点，说明你把"定边界优先"真正用起来了。
<!--src:A; ref:zero-to-builder#D1 pack:agent-skills-authoring-pack（定边界 / 坏设计红线）-->

**迁移挑战 2｜给一个新需求选对设计范式**
课件给了 7 种设计范式和一张选型判断表。现在来了三个需求，请各自判断主导范式并说明理由：① 把 Markdown 批量转成带固定格式的 PDF；② 在一个陌生代码库里定位一个偶发 Bug；③ 帮用户从模糊想法一步步敲定一个落地页的配色和布局。

- 【怎么算过关】能按选型判断表从上到下答"第一个是"就选：① 操作确定、工具链固定 → **Operator**（工具链封装）；② 环境不确定、要先侦察再行动、证据驱动 → **Scout**（环境不确定任务）；③ 需求模糊、有主观判断、要多轮确认 → **Partner**（交互式任务）。能说清"为什么不是别的范式"（比如②不是 Operator，因为一开始根本不知道 Bug 在哪，不能当确定性流程做）就到位了。核心 4 种范式覆盖约 85% 的日常场景，别一上来就升级到进阶范式。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 设计实战》4.2-4.5 四种核心范式 / 4.10 范式选型决策树-->

## 四、排错挑战（给你一份带病的 SKILL.md，修好它）

一位同学写了下面这份 `doc-helper` 的 SKILL.md，他反馈：**「装上之后特别爱乱触发，用户只是让我翻译一段文字、或者只想读一下文档原文，它也跳出来要做摘要；而且 Agent 一进来就先输出一大段代码和文档，半天不干正事。」** 请找出问题并修好。

```yaml
---
name: doc-helper
description: 一个处理文档的强大助手，能帮你搞定各种和文档、文本、资料相关的所有任务
---

# 文档助手

## Workflow
1. 用下面这段完整代码提取文本（把 pdfplumber 的完整用法贴在这）：
   ```python
   import pdfplumber
   def extract(path):
       text = ""
       with pdfplumber.open(path) as pdf:
           for page in pdf.pages:
               text += page.extract_text() or ""
       # ……此处省略 200 行各种格式的解析、清洗、分块示例代码
       return text
   ```
2. 参考下面从 Stripe / Twilio 官方文档复制来的 2000 行说明，决定怎么处理……
3. 生成摘要
```

- 【症状】① 该触发时之外也乱触发：翻译、纯读取原文都会误触发这个摘要 Skill；② Agent 进来先输出大段代码和文档、不直接干活，长文档处理还特别慢。本质是触发面失控 + SKILL.md 严重超载。
- 【根因】两处坏设计叠加：其一，**description 过于宽泛、且完全没有负向触发器**（"各种和文档相关的所有任务"），这正是触发污染的根因，属于五维度里判 P0 的触发质量问题；其二，把 200 行提取代码和 2000 行第三方文档**直接嵌进了 SKILL.md**，同时踩中 `code-bomb-deployer`（厨房水槽，违反关注点分离）和 `encyclopedia-translator`（复制粘贴文档，违反信息精炼）两个反面案例；SKILL.md 是指挥官不是士兵，代码该进 scripts/、文档该进 references/。
- 【修法】
  ```yaml
  ---
  name: doc-summarizer
  description: 从长文档中提取结构化摘要。用户明确要求"总结/摘要/提炼重点"，且输入是文档、长文本、报告或 PDF/Word/Markdown 时触发。不适用于：全文翻译、润色改写、文档问答、纯读取原文、复杂决策分析（防误触）。
  ---

  # 文档摘要生成器

  ## Workflow
  1. 验证输入：检查文档格式是否支持（PDF/DOCX/MD）
  2. 提取文本：调用 scripts/extract_text.py
  3. 分块处理：文档 >5000 字时调用 scripts/chunk_document.py
  4. 生成摘要：按 references/summarization-strategies.md 的策略生成
  5. 格式化输出：套用 assets/summary-template.md
  6. 验证完整性：摘要长度为原文 10-15%，且含"核心观点/关键数据/结论"三部分

  ## Validation
  - 若关键章节未覆盖 → 重新生成对应部分
  ```
  改动要点：收窄 name 与 description 并补上负向触发器（治乱触发）；把代码搬进 `scripts/`、把长文档搬进 `references/`、把输出模板搬进 `assets/`（治超载）；SKILL.md 只留"什么时候调哪个脚本"和验证标准，控制在 60-100 行。
- 【一句话总结】触发乱 → 根因在 description，加负向触发器；SKILL.md 又臭又长 → 代码进 scripts/、文档进 references/、模板进 assets/，主文件只当指挥官。

## 五、面试自测（本阶段技术点常问题）

> 每题给：考察点 · 答题要点 · 一层追问。答案已写全，可自包含背诵。
> 说明：以下题目按 2026 年 AI 应用 / Agent 开发岗真实高频方向校准，考点集中在 Skill 触发机制、三条设计原则、七种范式、五维度评估、Skill 与 FC/MCP 的边界。

**面试 1｜Agent 是怎么决定要不要调用某个 Skill 的？完整流程是什么？**
- 考察点：对 Skill 调用/路由机制的整体理解。
- 答题要点：课件的五步决策流程是**识别任务 → 判断能力边界 → 匹配 Skill → 执行 Skill → 整合输出**。匹配那一步靠语义匹配度（description 与请求的相似度 + 关键词）、能力边界匹配、优先级规则三个依据从多个候选里筛出最合适的一个。任务很简单（如"什么是 Python"）时会在第二步判定不需要 Skill，直接回答。
- 追问：「这套机制里，决定一个 Skill 能不能被选中的最关键字段是哪个？」→ frontmatter 里的 **description**，它是路由系统的入口，决定 Skill 能否被发现和匹配。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 基础入门》2.1 五步决策 / 2.2 路由决策-->

**面试 2｜什么是渐进式信息披露（Progressive Disclosure）？它为什么高效？**
- 考察点：Skill 系统的 Token 经济学。
- 答题要点：系统分三层按需加载：空闲/无关时只加载所有 Skill 的**元数据**（name+description，约每技能 100 Token）维持全局可见；匹配到任务才读完整 **SKILL.md**（约 3000 Token）；执行到特定步骤才加载 **references/** 里的大文档（10000+ Token）。这种"压缩与解压"机制让 Agent 能"知道"数百个技能存在，却只在需要时才"学习"具体细节，极大优化资源消耗。
- 追问：「所以简单 Skill 和复杂 Skill 在这套机制下有什么结构差异？」→ 简单 Skill 逻辑单一、所有内容都在 SKILL.md；复杂 Skill 才把知识拆进 references/、把脚本拆进 scripts/，正是渐进式披露的体现。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 基础入门》2.1.3 Token 经济学-->

**面试 3｜Skill、Function Calling、MCP 三者有什么区别？分别什么时候用？**
- 考察点：三种能力扩展方式的边界与选型。
- 答题要点：**Function Calling** 是代码级函数调用，本质是函数签名+实现，确定性高，适合金融交易、数据库操作这类要精确控制的场景；**MCP** 是协议级能力接入，标准化协议，适合跨平台、跨系统集成（"一次实现，到处使用"）；**Agent Skills** 是语义级能力模块，本质是结构化提示词+资源，用 Markdown 写、门槛低，适合复杂工作流、快速迭代、非技术人员参与的场景。三者不互斥：高层工作流用 Skill、底层精确操作用 FC、跨平台能力用 MCP。
- 追问：「一个金融风控要审贷款，为什么不能用 Skill 而要用 Function Calling？」→ 因为这类场景不能接受任何不确定性，Skill 的灵活性反而是劣势，你要的是"精确执行指令"而非"灵活理解意图"，FC 的确定性执行（相同输入→相同输出）才是刚需。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 基础入门》4.2 Skills vs FC vs MCP-->

**面试 4｜Skill 设计有三大坏味道，分别是什么？各对应什么正面原则？**
- 考察点：从反面案例提炼设计原则的能力。
- 答题要点：① **万能瑞士军刀**（`ai-dev-assistant`，职责不清、触发混乱）→ 对应**单一职责原则 SRP**，一个 Skill 只做一件事；② **厨房水槽**（`code-bomb-deployer`，代码配置文档全塞进一个文件、结构混乱）→ 对应**关注点分离 SoC**，SKILL.md 只写执行流程，代码进独立文件、配置进环境变量或模板；③ **复制粘贴文档 / 百科全书**（`encyclopedia-translator`，信息过载、Agent 迷失）→ 对应**信息精炼原则**，只保留执行必需信息、背景知识用链接引用。
- 追问：「三条原则冲突时谁优先？为什么？」→ **SRP 优先级最高**。职责边界是设计的基础，边界错了，后面整理结构、压缩内容都只是把一个方向错误的东西整理得更漂亮。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 设计实战》第 2 章反面案例 / 3.4 规则优先级-->

**面试 5｜一份设计良好的 Skill 是三层架构，请说清每一层的职责和体量。**
- 考察点：三层架构与"SKILL.md 是指挥官"的认知。
- 答题要点：**路由层**（frontmatter）放 name、description，负责触发匹配，通常 3-5 行；**控制层**（SKILL.md 正文）放 Goal、Workflow、决策树、Constraints、Validation，负责决策和流程，60-100 行；**执行层**（scripts/ + references/ + assets/）放具体操作、领域知识、模板，体量不限、按需扩展。三层关系：路由层决定"要不要激活"，控制层决定"怎么做决策"，执行层负责"具体怎么做"。
- 追问：「如果发现自己在 SKILL.md 里写了大量代码，说明什么？」→ 说明混淆了控制层和执行层的职责，代码应该外置到 scripts/，SKILL.md 只说明"调哪个脚本、传什么参数"。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 设计实战》2.6 三层架构 / 第 9 章核心认知 3-->

**面试 6｜写 description 时，一个新手最容易踩的坑是什么？怎么写才对？**
- 考察点：触发质量与负向触发器意识。
- 答题要点：最容易踩的坑是在 description 里写一部"小长篇小说"、或写得过于宽泛（如"处理所有文档相关任务"），导致路由瘫痪、触发污染。正确做法：用清晰动词开头，说明核心能力和适用场景，**并明确写出负向触发器**（如"绝对严禁用于纯文本或代码仓库扫描（防误触）"）。只列正向、不列负向的相邻场景，是误触发的头号根因。
- 追问：「两个 Skill 抢同一句话反复横跳（路由震荡）怎么办？」→ 不要两边都拼命加词内卷，应重写各自描述划清边界，让语义域更弱的一方"让渡"、写明"不适用于 X"。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 基础入门》4.3 常见风险 + 能力包触发排障-->

**面试 7｜七种设计范式里，核心的四种是什么？怎么快速选型？**
- 考察点：范式认知与选型判断表。
- 答题要点：核心四种是 **Operator（工具链封装，35%）、Scout（环境不确定任务，25%）、Partner（交互式任务，20%）、Navigator（路由和查找，15%）**，覆盖约 85% 的日常场景。选型用判断表从上到下问四个问题，第一个回答"是"的即为主导范式：操作是否确定？→ Operator；环境是否不确定？→ Scout；是否需要人工确认？→ Partner；是否需要条件路由？→ Navigator。进阶三种（Philosopher/Architect/Orchestrator 各约 5%）只在核心范式确实不够时才升级。
- 追问：「范式可以混合吗？」→ 可以，但必须有唯一的**主导范式**。比如一个 Operator 范式的 Skill 可以在某步引入 Partner 的人工确认机制，但整体仍以 Operator 为主，避免过度设计。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 设计实战》4.1 范式频率 / 4.10 选型判断表-->

**面试 8｜Skill 的五维度质量评估体系是哪五维？综合分怎么用？**
- 考察点：五维度验收标准。
- 答题要点：五维是 **触发质量、路由质量、上下文效率、复用与确定性、验证强度**，每维 1-5 分、合计 25 分。关键：**看最低维度定改进优先级，不看综合分**。某一维低于 3 分就是基础可用性缺陷、要优先修。上下文效率一维里，SKILL.md 控制在 60-150 行给 4-5 分、150-300 行给 3 分、超 500 行只有 1-2 分。
- 追问：「课件里 document-summarizer v1 实测哪一维最低？说明什么？」→ 触发质量最低（2.5/5，误触发率 40%、漏触发率 20%），说明 v1→v2 的首要改进方向是触发准确性（P0），而不是大家容易先想到的性能。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 设计实战》第 7 章五维度 + 能力包 quality-rubric-->

**面试 9｜有人说"Skill 用着用着会自己变聪明、自动进化"，对吗？**
- 考察点：破除"自动进化"迷思。
- 答题要点：不对。Skill 本质是一份可执行的流程规范，不是会自我训练的生命体。所谓"自主进化"其实是三层组合：**遥测采集**（记录触发/失败/输出质量，自动化程度高）、**定期复盘**（从数据里找模式，半自动）、**实际升级**（改结构/脚本/策略，靠人工判断、自动化程度低）。能自动的只是前一层半，真正决定质量跃迁的是第三层人工升级。正确路径是"先评估、再升级；先定位问题、再改动"。
- 追问：「为什么必须先评估再进化？」→ 没有评估就不知道问题在哪，不知道问题就无法排优先级，没有优先级优化就沦为"到处补丁"，时间全耗在次要问题上。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 设计实战》第 6 章自主进化真相-->

**面试 10｜在一个真实 Agent 系统里，一份写好的 SKILL.md 是怎么被"用起来"的？**
- 考察点：从设计到运行的落地链路（mini-OpenClaw 收口）。
- 答题要点：链路四环——① SKILL.md 用 YAML frontmatter 开头（name+description 必填）；② 系统启动时 `skills_scanner` 扫描 skills/ 目录、解析 frontmatter，生成一份技能快照 `SKILLS_SNAPSHOT.md`（**只提取 name+description，不塞全文**，体现信息精炼）；③ `prompt_builder` 把快照注入 System Prompt 的**最前面**，让 LLM 每次处理消息前最先感知"我有哪些技能可用"，大幅提升触发准确率；④ 新增技能只需三个动作：创建目录、写 SKILL.md、重启后端，无需改代码。
- 追问：「为什么快照只放 name+description、而不是整份 SKILL.md？」→ 这是关注点分离：快照负责"发现"（让 Agent 知道有哪些技能），完整 SKILL.md 负责"执行指导"（用时再按路径 read_file 读），两者职责不重叠，也避免上下文膨胀。
<!--src:A; ref:zero-to-builder#D1 讲次《大模型 Agent Skills 设计实战》第 10 章 mini-OpenClaw 落地-->

## 六、模拟面试官指令（可直接粘贴给 Agent）

> 把下面整段复制给任意 Agent，让它当考官考你。请**只做考官、不做辅导**。

```
请你扮演一名技术面试官，围绕「Agent Skills 的原理、设计与评估」这一阶段考我。规则如下：

【角色纪律】请只做考官、不做辅导。在我明确说「结束，请点评」之前，你不要讲解知识点、不要给正确答案、不要提示思路。我答错也只说「记录了，下一题」，不纠正。

【题库范围】只问以下方向，且尽量贴近真实岗位：
1. Skill 基础：一句话定义、可发现/可执行/可复用三大特性、Skill vs Prompt 的本质区别。
2. 调用机制：五步决策流程、路由靠什么匹配、渐进式信息披露与 Token 经济学。
3. 三大坏味道与三条原则：万能瑞士军刀/厨房水槽/复制粘贴文档，对应 SRP/SoC/信息精炼，冲突时谁优先。
4. 结构与范式：三层架构（路由层/控制层/执行层）、七种范式里核心四种与选型判断表。
5. 质量与评估：五维度评估体系、看最低维定优先级、破除「自动进化」迷思。
6. 边界与触发：边界四问、description 的负向触发器、触发不准的根因与修法。

【流程】
- 先出 6 道题，一次一题，等我回答完再出下一题。
- 每道题我答完后，你追问一层（更深或更具体的一个小问题），再进入下一题。
- 如果我答「不会」，记录后直接下一题，不要讲解。

【结束点评】当我说「结束，请点评」时，你再一次性给出：每道题我的表现评价（答对/部分/未答）、暴露的薄弱点、以及建议我回看 Stage D 的哪个环节（D1 Skill 原理与从零开发 / D2 顶尖 Skill 工作流）。

现在，请出第 1 题。
```

## 七、能力自评表

> 对每个技能点，诚实勾选你现在处于哪一档。三档标准：**能跟做**（照着课件 / Agent 能做出来）< **能独立做**（关掉教程、自己从零做对）< **能教别人**（能讲清为什么这么做、能纠别人的错）。

| 技能点 | 能跟做 | 能独立做 | 能教别人 |
|---|---|---|---|
| 一句话说清 Skill 定义与三大特性 | ☐ | ☐ | ☐ |
| 区分三种技能结构（简单 / 多步骤 / 资源依赖型） | ☐ | ☐ | ☐ |
| 讲清 Skill 与 Prompt、FC、MCP 的本质区别与选型 | ☐ | ☐ | ☐ |
| 说清五步调用流程与渐进式信息披露 | ☐ | ☐ | ☐ |
| 动笔前答清边界四问（尤其不该触发的相邻请求） | ☐ | ☐ | ☐ |
| 用 SRP 三测试判断一个 Skill 该不该拆 | ☐ | ☐ | ☐ |
| 说清三大坏味道及对应的 SRP/SoC/信息精炼 | ☐ | ☐ | ☐ |
| 讲清三层架构、把内容归对层 | ☐ | ☐ | ☐ |
| 从七种范式里为新需求选出主导范式 | ☐ | ☐ | ☐ |
| 写出带负向触发器的 description | ☐ | ☐ | ☐ |
| 用五维度给一个 Skill 打分、按最低维定优先级 | ☐ | ☐ | ☐ |
| 定位触发不准的根因并只改 description 修好 | ☐ | ☐ | ☐ |
| （D2）走一遍 Spec-Kit specify→clarify→plan→tasks | ☐ | ☐ | ☐ |

## 八、落地对照（学完这阶段能接的真实小活）

> 都是这阶段能力就能接的入门级活儿，描述自包含。它们是你作品集和「超级个体」现金流的一部分。

1. **帮别人把一段重复工作方法沉淀成一个可用的 Skill。**
   很多人有固定套路（写周报、整理会议纪要、给素材配标题）却每次都要重新教一遍 AI。你会答边界四问、会用 SRP 判拆、会写带负向触发器的 description，正好能把这类隐性方法做成一个 SKILL.md 交付给对方。

2. **给别人已有的一堆烂 Skill 做一次"体检"。**
   拿五维度评估体系给对方的 Skill 逐个打分，指出最低维、给出改进优先级（比如"你这个触发质量只有 2 分，先加负向触发器"）。这是一单轻量但很值钱的"Skill 质检"服务。

3. **专治"Skill 装了却乱触发 / 不触发"。**
   你懂触发不准的根因在 description、懂用 should / should-not 用例集把"我觉得不准"变成"数据证明不准"。帮人排掉触发污染、修好 description，是一类很具体的排障小活。

4. **给小团队搭一套"文件即配置"的轻量 Skill 目录。**
   照 mini-OpenClaw 那套思路：让团队把常用技能各写一份 SKILL.md 放进目录，新增技能只要创建目录、写文件、重启即可。你帮他们把规范和目录立起来，团队就有了可自助扩展的 Agent 能力库。

5. **用 Spec-Kit 帮人把一个模糊需求拆成规范三件套。**
   拿 D2 学的规范驱动流程（specify→clarify→plan→tasks），帮不会拆需求的人把一个想法整理成 spec / plan / tasks，交付一份可直接指挥 Agent 落地的规范文档。
