## 一、随堂练习（动手小题）

### A1 · Claude Code 架构源码解析
> 来源讲次：《Claude Code 架构源码解析》Part 2《能力与安全边界》第 3、5、9 章

**练习 A1-1｜徒手画出五层架构地图**
课件把这份泄露快照的 51 万行代码归纳成一张五层地图，让你能徒手画出来。请从下往上写出这五层的名字和各自一句话职责。

- 【参考答案】L1 信息收集（汇聚用户输入、对话上下文、记忆）→ L2 推理决策（约 1.6% 的核心，调用模型做判断）→ L3 工具执行（把决策落地成对四十多个工具的统一调度）→ L4 扩展能力（Skill / MCP / Hook 三个正交扩展口）→ L5 安全约束（一道四层管线，决定哪些动作真能执行）。
- 【自查要点】课件明确交代「五层、L1 到 L5」是本课为了教学做的归纳，不是源码里的官方分层，源码里没有一个叫 Layer 3 的目录。答题时要能主动点破这一点，别把教学抽象当成官方术语。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 第3章 五层架构地图-->

**练习 A1-2｜说清工业版凭什么不信 `stop_reason`**
你的三十行朴素 Agent 里有一句 `if decision["stop_reason"] == "tool_use"`，完全信任模型说要调工具。真实源码 `query.ts:554` 那行注释怎么写的？工业版改成怎么判断要不要调工具？

- 【参考答案】`query.ts:554` 原文是 `// Note: stop_reason === 'tool_use' is unreliable -- it's not always set correctly.`（`stop_reason` 等于 `tool_use` 不可信，它不总被正确设置）。工业版不信这个字段，转而结构化地检查模型返回内容里到底有没有真实的 `tool_use` 块（`query.ts:130` 那句 `content => content.type === 'tool_use'` 就是在响应内容里逐块过滤）。
- 【自查要点】在流式场景下 `stop_reason` 可能没被正确赋值，无脑信它会出现两种崩法：该调工具时没调（任务卡住），或把幻觉出来的假工具调用当真去执行。判据要落到「响应内容里是否真实存在 `tool_use` 结构块」，`stop_reason` 只当辅助信号。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 第4章 QueryLoop 深拆-->

**练习 A1-3｜把 L5 安全约束的四件套背出来**
课件用「四层管线 + 五层权限 + 三平台沙箱 + 断路器」回答「凭什么敢让 Agent 动手」。请把这四块各自的关键数字或名字写全。

- 【参考答案】
  - 四层安全管线：静态规则 → 白名单 → LLM 分类器 → 人类确认，是「管线」不是「替代」，逐层过滤，任一层判危险都拦下。
  - 五层配置来源优先级（`SETTING_SOURCES`，从低到高）：`userSettings` < `projectSettings` < `localSettings` < `flagSettings` < `policySettings`；靠后覆盖靠前，企业策略 `policySettings` 在最外层谁也覆盖不了。规则行为 `PermissionBehavior` 只有 `allow` / `deny` / `ask` 三个值，评估遵循 `deny > ask > allow`。
  - 三平台沙箱：macOS、Linux、WSL2，**不是原生 Windows**。
  - 断路器 `DENIAL_LIMITS`：连续被拒 3 次或累计被拒 20 次自动跳闸停机（`{ maxConsecutive: 3, maxTotal: 20 }`）。
- 【自查要点】常见错答是「三平台沙箱包括 Windows」——原生 Windows 无沙箱，要用得走 WSL2。这一整套约束的立意是「不是因为信任 AI，而是因为不信任 AI，所以建了一整套约束工程」。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 第9章 约束行为（安全）-->

### A2 · OpenAI Codex 快速入门实战
> 来源讲次：《OpenAI Codex 快速入门实战（上）》第 3、5、8、9 章

**练习 A2-1｜Codex 三档权限各是什么，什么时候用哪档**
Codex 在「请求批准」设置里给了三档权限。写出三档的名字和各自行为，并说出你接一个陌生仓库、需要联网时该选哪档。

- 【参考答案】三档是：**请求批准**（编辑工作区外文件、要联网时都停下来问你）、**替我审批**（只对它判断有风险的操作请示，其余自己做）、**完全访问权限**（不受限地联网、读写本机文件，基本不再问）。接陌生仓库或涉及联网时，选「请求批准」或「替我审批」更稳妥；日常熟练后大部分人切「完全访问权限」图流畅。
- 【自查要点】三档对应的是「自主性」和「安全」之间的取舍。刚上手先保持「请求批准」，亲眼看几次它来请示是什么样，心里有数再放权。
<!--src:A; ref:《OpenAI Codex 快速入门实战（上）》3.6 配置 Codex 的权限-->

**练习 A2-2｜计划模式什么时候用；AGENTS.md 和全局自定义指令怎么分工**
① 待办清单这种小活要不要开计划模式？点餐系统这种有前后台带数据库的活呢？② `AGENTS.md` 和 Codex 的「自定义指令」分别管到哪一层？

- 【参考答案】① 小活（如待办清单）直接说就行，用不着计划模式；有前台、后台、数据库的复杂活（如点餐系统）先让它把「打算分几步怎么做」列成计划给你过目，确认了再动手，能少走弯路。② `AGENTS.md` 放在项目根目录，是**单个项目**的规则，跟着项目走；「自定义指令」是**所有项目都遵守**的个人长期偏好，跟着你这个人走，落到本机就是一份全局的 `~/.codex/AGENTS.md`。
- 【自查要点】AGENTS.md 一份典型内容含：项目说明、安装与启动、测试命令、代码规范、安全与限制（哪些文件别动）、提交规范。它的价值是让 Codex「少问、少猜、少乱改」，不用每次新开会话重新交代一遍。
<!--src:A; ref:《OpenAI Codex 快速入门实战（上）》第5章 计划模式 / 第8章 AGENTS.md-->

**练习 A2-3｜Codex 两种多 Agent 并行有什么本质区别**
课件演示了「单会话内并行」和「多会话 + worktree 并行」两种。写出各自并行的是什么、单会话最多能拉起几个子智能体、为什么写入并行要请出 worktree。

- 【参考答案】单会话内最多能同时拉起 **8 个并行 SubAgent**，但它们的并行主要发生在**思考和调研**这一段（多以只读模式做代码调研），真正落笔改代码的还是主 agent（supervisor）一个人。多会话 + worktree 才是**写入并行**：不加 worktree，A、B 都改 `main.py` 会互相覆盖或冲突；worktree 为同一仓库开出多份相互独立、各挂不同分支的工作目录，让多个 agent 同时改同一项目却互不踩脚。合并时最好一个一个合、每合一个跑一次测试。
- 【自查要点】主 agent 分派、子 agent 并行、主 agent 汇总，这套叫 supervisor 协作模式，OpenAI 官方说法是「subagent workflows」。worktree 解决的是「并行写入互相覆盖」，但并不能消除「最终合并时的冲突」，所以一个 worktree 对应一个清晰功能最稳。
<!--src:A; ref:《OpenAI Codex 快速入门实战（上）》第9章 多 Agent 并行干活-->

### A3 · 安装课程全家桶
> 来源讲次：《赋范 Skills 全家桶 · 使用说明》+ 各课时随课能力包

**练习 A3-1｜全家桶怎么装，双流派各装到哪**
写出用户级安装与项目级安装的命令，以及 Windows 手动安装时 Claude Code 版和 Codex 版各复制进哪个目录。

- 【参考答案】解压后进入解压目录执行 `./install.sh` 装到用户级（全局生效），或 `./install.sh --project` 只装到当前项目。Windows 手动装：`Claude Code 版/` 下所有文件夹复制进 `%USERPROFILE%\.claude\skills\`，`Codex 版/` 复制进 `%USERPROFILE%\.agents\skills\`。装完**重启 Claude Code / Codex 会话**即生效，正常提问自动触发，无需手动调用。

**练习 A3-2｜怎么验收全家桶真的装上了**
对照 A3 的验收标准，写出一条能证明「Agent 已经按课程能力包方法答题」的检验动作。

**练习 A3-3｜装完 Agent 没识别到能力包怎么办**
你把包放好了，但 Agent 答题时完全没有课程包的味道。按 A3 的常见问题，先排查哪两件事？

- 【参考答案】① 确认能力包确实放进了 Agent 的 `skills` 目录（Claude Code 版进 `.claude/skills/`，Codex 版进 `.agents/skills/`）；② **重启会话**再让它列出新增领域。两件事都做了还不行，再逐个方向确认包是否解压完整。

## 二、误区自查（照镜子）

> 读法：如果你心里认同左边那句 X，说明你还没真正掌握 Y，去回看 Z。

1. **如果你以为「Agent 不就是个带工具的 while 循环，三十行够了，大厂在过度工程」** → 说明你还没体会「够跑」和「敢用」之间差的那五十一万行。课件用代码归类估算给出：约 1.6% 在调模型做决策，约 98.4% 是权限、上下文、工具路由、错误恢复这类确定性运营基建。回看 engineer-transform#A1 的三十行朴素 Agent 与四个致命问题。

2. **如果你以为「模型回你『我是 DeepSeek』就说明路由配对了」** → 说明你还没建立「能对话不等于能验证」的习惯。模型自报身份不是路由证据，真正的证据要去三处外部找：cc-switch 当前 provider 状态、DeepSeek 控制台调用记录、CCR 日志。回看 engineer-transform#A1 的路由验证闭环。

3. **如果你以为「权限判断就是 `isReadOnly` 一个布尔，只读放行、非只读拦截」** → 说明你把权限想简单了。工具能不能跑要走一条链式决策，PreToolUse Hook 可以改写参数或直接否决，之后才进入权限裁决，遵循 `deny > ask > allow`。回看 engineer-transform#A1 的「权限不是布尔，是决策链」。

4. **如果你以为「让 Agent 帮我把 A1 的架构图画了、agent loop 讲了，也算过关」** → 说明你还没意识到 A1 的这道深潜关是闭卷、不许 Agent 代做。关掉 Agent 与全家桶独立画出四环并标注工具调用与上下文裁剪点，才拿得到阶段徽章。回看 engineer-transform#A1 的深潜验收说明。

5. **如果你以为「Codex 就是个更强的代码补全」** → 说明你还停在 2021 年那个旧 Codex 的印象里。今天的 Codex 是 2025 年重启命名的、能自己接任务拆步骤调工具干到完成的编程 agent，和旧模型没有技术传承。回看 engineer-transform#A2 的「此 Codex 非彼 Codex」。

6. **如果你以为「装完全家桶，Agent 就自动会用课程包了」** → 说明你漏了「重启会话」这一步。能力包在会话启动时加载，放对目录也要重启会话才识别得到，之后还得用一个 LangChain 中间件问题验一验它是不是真按课程包方法答。回看 engineer-transform#A3 的安装与验收。

## 三、迁移挑战（换个场景用同样方法）

**迁移挑战 1｜把「吃透任意开源项目」的方法搬到另一个陌生项目**
A1 课件给了一段通用提示词，用「规模与分层 → 主干一线 → 核心契约 → 扩展点 → 约束与安全 → 可迁移设计模式」六个阶段拆开一个陌生大型开源项目。请你挑一个自己没读过的开源项目（比如某个 Web 框架或 CLI 工具），不通读全部代码，只用这套六阶段方法产出一张分层地图。

- 【怎么算过关】① 每个阶段产出后停下、不一口气全做；② 每条断言都贴上证据色标（源码 `file:line` 实测 / 行为 / 文档 / 推断 / 待核验），对「内部如何实现」的描述默认先进「待核验」；③ 你自己起的归纳命名（比如「L3 层」）必须显式声明「这是教学归纳，非项目官方术语」；④ 查不到证据就写「未找到」，绝不用合理猜测去填 `file:line`。
- 【提示】这套方法的价值不在让 AI 替你读项目，恰恰是逼你带着尖锐问题进场、把每条结论钉在可核实的源码与行为上。你在 Claude Code 上跑第 1 阶段得到的，就是那张五层地图。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 通用提示词-->

**迁移挑战 2｜把路由验证闭环搬到你自己的模型网关**
A1 教你「用三处外部证据证明请求真到目标模型」。假设你在公司搭了一个自研模型网关，怎么迁移这套闭环去验证「客户端发的请求确实路由到了你以为的那个后端模型」？只描述验证动作，不用真跑。

- 【怎么算过关】能指出：不看模型自报身份，转而凑齐至少两三处独立外部证据：网关侧的转发日志（这次请求打到了哪个后端）、目标模型服务商控制台的调用记录（时间戳与用量对得上）、以及一个能区分模型的探针问题（不同模型回答特征不同）。能说清「为什么不能只信模型自己说它是谁」= 因为它可能按提示词猜、也可能被错误路由后仍能正常回复。
- 【提示】这正是「能对话不等于能验证」从 Claude Code 场景迁移到任意 API 网关的通用形态。

## 四、排错挑战（给你一段带病的配置，修好它）

一位同学按课件走 CCR（Claude Code Router）路线，把 cc-haha 接 DeepSeek 的 Anthropic 兼容端点。他反馈：**「`ccr` 启动没报任何错，看起来一切正常，但对话时请求根本到不了 DeepSeek，模型也不响应。」** 下面是他写进 `~/.claude-code-router/config.json` 的内容，请找出问题并修好。

```json
{
  "Providers": [
    {
      "name": "deepseek-anthropic",
      "api_base_url": "https://api.deepseek.com/anthropic",
      "api_key": "sk-your-deepseek-key",
      "models": ["deepseek-v4-pro", "deepseek-v4-flash"],
      "transformer": {
        "use": ["anthropic"]
      }
    }
  ],
  "Router": {
    "default": "deepseek-anthropic,deepseek-v4-pro"
  }
}
```

- 【症状】`ccr` 启动不报错、进程正常，客户端界面看着也没异常，但请求既不报错也不路由，根本到不了 DeepSeek，模型无响应。
- 【根因】`transformer` 的 `use` 写成了小写的 `"anthropic"`。CCR 的 transformer 名称**大小写敏感**：Anthropic 兼容端点对应的正确名称是大写 A 的 `"Anthropic"`。写错大小写会导致 Anthropic 端点路由**静默失效**——既不报错、也不路由，启动后看起来一切正常，请求却送不出去。（对照记忆：只有 OpenAI 兼容端点那条路线用的才是小写 `"deepseek"`。）
- 【修法】把 `"use": ["anthropic"]` 改成 `"use": ["Anthropic"]`：
  ```json
  "transformer": {
    "use": ["Anthropic"]
  }
  ```
  改完顺手核对两处：模型 ID 用当前的 `deepseek-v4-pro` / `deepseek-v4-flash`（旧 ID `deepseek-chat` / `deepseek-reasoner` / `deepseek-v3.2` 于 2026-07-24 废弃），真实 Key 只写在这份不进 Git 的配置里。修完再用路由验证闭环凑三处外部证据确认请求真到了 DeepSeek。
- 【一句话总结】这类「不报错但不生效」的静默故障最坑，排查口诀是：先分层判断断在 provider 配置 / CCR / DeepSeek 哪一层，再逐字核对大小写敏感的字段。

## 五、面试自测（本阶段技术点常问题）

> 每题给：考察点 · 答题要点 · 一层追问。答案已写全，可自包含背诵。

**面试 1｜Claude Code 的 agent loop 靠什么结构驱动？为什么用这个结构？**
- 考察点：对工业级 agent loop 执行体的理解。
- 答题要点：核心循环在 `query.ts`（约 1729 行），驱动结构是 `async function*`，即异步生成器（AsyncGenerator）。用它是因为 Agent 每轮循环天然就是这个形态：执行一个工具、把结果 `yield` 出去、暂停，等下一轮被唤醒继续。普通函数「调一次返回一次就结束」，生成器能跑到一半停下来交出当前结果、等外部叫它再往下跑。
- 追问：「工业版循环的退出为什么不能只判一个停止条件？」→ 源码里有多个语义不同的退出 reason，本课选讲五个代表：`completed`（正常完成）、`max_turns`（到轮次上限）、`model_error`（模型调用出错，触发分阶段回退）、`prompt_too_long`（超上下文窗口，触发压缩）、`stop_hook_prevented`（Hook 阻断，把 stderr 喂回模型换方案）。朴素版只有一个出口，出错就崩、超窗就静默失败。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 第4章 QueryLoop-->

**面试 2｜为什么说模型返回的 `stop_reason` 不可信？工业级 Agent 怎么处理？**
- 考察点：用工程手段兜住模型输出的不确定性。
- 答题要点：源码 `query.ts:554` 有一行注释直言 `stop_reason === 'tool_use' is unreliable`——在流式输出时这个字段可能没被正确赋值。无脑信它会两种崩：该调工具时没调（任务卡住），或把幻觉出的假工具调用当真执行。工业版不看这个字段，改成结构化检查响应内容里是否真实存在 `tool_use` 块（`content.type === 'tool_use'`），`stop_reason` 只当辅助信号。
- 追问：「这一个细节体现了课件那个 1.6% / 98.4% 的什么含义？」→ 模型本身没变聪明，是工程层用结构校验兜住了模型输出的不确定性，这正是那 98.4% 确定性运营基建的典型样本。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 4.2 stop_reason 不可信-->

**面试 3｜那份泄露快照约 51 万行代码，大部分在干什么？这个比例怎么讲才严谨？**
- 考察点：对「工业级 Agent 里代码到底花在哪」的判断，以及引用数据的严谨度。
- 答题要点：社区对快照做过代码归类估算：真正调模型做决策的逻辑约 1.6%，其余约 98.4% 是确定性运营基建（权限控制、上下文管理、工具路由、错误恢复）。讲这个比例必须带三个限定：① 来源是社区分析、经一篇 arXiv 论文（VILA-Lab《Dive into Claude Code》）收录引述，不是 Anthropic 官方数据；② 口径是「AI 决策逻辑 vs 确定性运营基建」，不是「扩展能力 vs 约束行为」的精确切割；③ 论点站得住（绝大多数代码在约束和支撑 AI），但精确小数别当圣经报出去。
- 追问：「那这份快照的版本和规模是多少？」→ 版本 `v2.1.88`，实测 512,664 行代码、1884 个文件（来自泄露的 source map 反向还原）。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 第1、3章-->

**面试 4｜Skill、MCP、Hook 三个扩展机制怎么快速选型？**
- 考察点：对 Agent 扩展点的正交理解。
- 答题要点：一句口诀 know / do / intercept。想让 Agent **多懂点什么（know）**，加知识、加固定工作方式，用 Skill（配置即 prompt）；想让 Agent **多能干点什么（do）**，接外部服务、外部工具，用 MCP（协议即工具）；想在 Agent **做事的关键点插手（intercept）**，拦截、审计、改写它的行为，用 Hook（事件即拦截）。三个诉求正交，不重叠也不遗漏。know / do / intercept 是教学归纳，不是源码官方术语。
- 追问：「Hook 到底有多少个生命周期事件点？」→ 源码 `HOOK_EVENTS` 常量实测是 27 个（如 `PreToolUse`、`PostToolUse`、`Stop`、`SessionStart`、`SessionEnd`、`PreCompact` 等），本课只选讲最常用的子集（以 `PreToolUse` 为代表），不是网上有些资料说的 10 个。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 6.4 三正交选型-->

**面试 5｜为什么说 Claude Code 的安全是「管线」而不是「替代」？**
- 考察点：多层安全防线的设计取舍。
- 答题要点：四层（静态规则 / 白名单 / LLM 分类器 / 人类确认）是串联逐层过滤、各司其职，命令必须每层都走一遍，任一层判危险就拦下，前一层放行绝不等于最终放行；「替代」则是只留一个最强检查。选管线有三个理由：① 各层成本能力天差地别，把便宜的静态规则放前面先筛掉绝大多数明显安全/危险的命令，只让极少数模糊的升级到又慢又贵的 LLM 层；② 各层互补不冗余，静态规则揪固定攻击模式、白名单快速放行、LLM 补语义灰色地带、人类兜最后一档，删任何一层都会漏一类风险；③ 前层不否决后层，评估遵循 `deny > ask > allow`，后面任意一层给出 `deny`，前面再多 `allow` 也救不回来。
- 追问：「那个 LLM 分类器是不是一个独立的第二个 AI？」→ 要精确划界：它是独立的检查通道，但独立通道不等于独立模型，别把它讲成「另起一个大模型全量审查每条命令」。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 9.2 四层安全管线-->

**面试 6｜Claude Code 的权限优先级体系是怎么设计的？**
- 考察点：配置来源优先级 + 规则行为两个维度。
- 答题要点：由两个正交维度组成。配置来源优先级（`SETTING_SOURCES`，从低到高）：`userSettings` < `projectSettings` < `localSettings` < `flagSettings` < `policySettings`，靠后覆盖靠前，企业统一下发的 `policySettings` 在最外层、开发者改不动。规则行为 `PermissionBehavior` 只有 `allow` / `deny` / `ask` 三个值，评估遵循 `deny > ask > allow`。合起来一句话：最高优先级来源里的最严格规则永远赢，这是「安全优先」在权限设计上的落地。
- 追问：「真实 Key 按课件只能放哪三个地方？」→ cc-switch 的本地配置、`.claude/settings.local.json`（已进 `.gitignore`）、或 shell profile（`.zshrc` / `.bashrc`）；绝不写进 `CLAUDE.md`、`settings.json`、截图或公开仓库。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 9.4 五层权限优先级-->

**面试 7｜Claude Code 的沙箱支持哪几个平台？断路器防的是哪一类风险？**
- 考察点：安全能力的平台边界与失控保护。
- 答题要点：沙箱支持三个平台，即 macOS、Linux、WSL2，**不是原生 Windows**；原生 Windows 上没有沙箱隔离，要用得走 WSL2（本质还是 Linux 内核）。断路器防的不是单条危险命令，而是「Agent 一直在试探边界」这类风险：源码常量 `DENIAL_LIMITS` 实测 `{ maxConsecutive: 3, maxTotal: 20 }`，一个 Agent 连续被拒 3 次或累计被拒 20 次就自动跳闸停机。
- 追问：「静态规则层为什么能是零成本、微秒级？」→ 它靠预写死的模式匹配识别已知危险（命令替换注入、危险变量等），不调模型、不做 I/O，所以又快又便宜，专门负责先筛掉绝大多数明显命令。
<!--src:A; ref:《Claude Code 架构源码解析》Part2 9.5 三平台沙箱 / 9.6 断路器-->

**面试 8｜现在的 Codex 和 2021 年那个 Codex 是一回事吗？它今天跑什么模型？**
- 考察点：对 Codex 身份的准确认知。
- 答题要点：不是一回事，同名不同物、没有技术传承。2021 年 6 月那个 Codex 是代码补全模型、当过 GitHub Copilot 早期引擎，2023 年 3 月被弃用；2025 年 5 月 OpenAI 把「Codex」这名字重新用在一套全新的、能自己干活的编程 agent 上。今天 Codex App 默认跑 GPT-5.5。
- 追问：「有没有一个叫 GPT-5.5-Codex 的单独型号？」→ 没有。带 `-Codex` 后缀的命名到 GPT-5.3-Codex 那一代就停了，之后的 GPT-5.4、GPT-5.5 都是直接用通用模型，模型菜单里看到的就是 GPT-5.5、GPT-5.4 这些通用型号。
<!--src:A; ref:《OpenAI Codex 快速入门实战（上）》第1章 先认识 Codex-->

**面试 9｜Codex 的三档权限和计划模式分别解决什么问题？**
- 考察点：Codex 工作流里的受控执行。
- 答题要点：三档权限（请求批准 / 替我审批 / 完全访问权限）解决的是「给 Agent 多大自主权」，在自主性和安全之间取舍，接陌生仓库或联网时收紧、日常熟练后放开。计划模式解决的是「复杂任务一上来就动手容易跑偏」：让它收到需求后先不写代码，把「分几步怎么做」列成计划给你过目，确认了再实施；小活直接说就行，多约束、易返工的活不许跳过计划直接干。
- 追问：「Codex 按什么计费，哪些操作特别费额度？」→ 从 2026 年 4 月起按 token 用量计费（不再按消息条数），生图约是普通文字任务的 3 到 5 倍，电脑操控每步都要截图喂进去、步数一多涨得猛，多个 agent 同时干各自独立计费；额度按每 5 小时滚动窗口恢复。
<!--src:A; ref:《OpenAI Codex 快速入门实战（上）》3.6 权限 / 第5章 计划模式-->

**面试 10｜Codex 里让多个 Agent 协作，思考并行和写入并行有什么区别？**
- 考察点：多 Agent 协作的两种形态与工程约束。
- 答题要点：单会话内最多拉起 8 个并行 SubAgent，但并行主要发生在思考和调研段（多以只读模式做代码调研），真正落笔改代码的还是主 agent 一个人，这叫 supervisor 协作模式（官方说法 subagent workflows），适合需求复杂、要先读代码理清方案的场景。要写入并行，得开多个会话、每个挂一棵 worktree（Git 的多工作目录机制），让多个 agent 同时改同一项目却互不覆盖文件；合并回主分支时逐个合、每合一个跑测试，避免出 bug 难定位。
- 追问：「worktree 能消除合并冲突吗？」→ 不能。worktree 解决的是「并行写入互相覆盖」，并不能消除「最终合并时的冲突」，所以一个 worktree 对应一个清晰功能、别让不同 agent 改同一批文件最稳。
<!--src:A; ref:《OpenAI Codex 快速入门实战（上）》第9章 多 Agent 并行-->

## 八、落地对照（学完这阶段能接的真实小活）

> 都是这阶段能力就能接的活儿，描述自包含。它们也是你转型作品集与技术讲解的第一批素材。

1. **给团队配一套 CC + Codex 双基座工作流。**
   帮同事把 Claude Code 接好第三方模型（cc-switch 配 provider 或 CCR 路由）、装好课程全家桶，再立一份分工习惯：谁写服务、谁写测试。交付物 = 一份可复用的接入 + 路由验证清单。

2. **给一个项目立 AGENTS.md 规约，让 Agent 少问少猜少乱改。**
   用 Codex 在项目里自动生成 AGENTS.md（项目说明、启动、测试命令、哪些文件别动、提交规范），再验证新开会话它会自动读取。适合任何「每次都要重新交代背景」的项目。

3. **给项目配一层安全边界，别让 Agent 误删误改。**
   按 `deny > ask > allow` 和五层配置来源，为项目写 `.claude/settings.json` 权限、把真实 Key 挪到只该放的三个地方、给 `.env` 与数据库文件加进忽略清单。交付物 = 一份能通过自检的权限配置。

4. **帮团队排查「Agent 接了模型但不生效」的静默故障。**
   你会先分层判断断在 provider 配置 / CCR / 模型服务哪一层，再逐字核对大小写敏感字段（如 transformer 名称）和已废弃的模型 ID，最后用三处外部证据确认请求真到目标模型。这是一单实打实的「环境搭建 / 链路排障」小服务。

5. **用多 Agent 并行给一个中等项目加几个互不重叠的功能。**
   拆成几件不重叠的活，开多个会话各挂一棵 worktree 并行改，再逐个合并回主分支、每合一个跑测试。适合演示你对 Codex 多 Agent 协作与工程纪律的掌握。
