## 一、随堂练习（动手小题）

### B1 · Agent Skills 详解
> 来源讲次：《Agent Skills 详解》Part 1《大模型 Agent Skills 基础入门》、Part 2《大模型 Agent Skills 设计实战》

**练习 B1-1｜把 SKILL.md 的三层架构各放什么写清楚**
课件说一个设计良好的 Skill 分三层。请写出三层的名字、各自放什么、以及大小基准（行数）。

- 【参考答案】① 路由层（frontmatter）：SKILL.md 顶部的 YAML 区，只放 name 和 description，负责触发匹配，通常 3-5 行；② 控制层（SKILL.md 正文）：Markdown 正文，放 Goal、Workflow、Decision Tree、Constraints、Validation 这类决策与流程，基准 60-100 行；③ 执行层（scripts/ + references/ + assets/ 等独立子目录）：放具体脚本、参考文档、输出素材，大小不限、按需扩展。三层关系是：路由层决定「要不要激活」，控制层决定「怎么做决策」，执行层负责「具体怎么做」。
- 【自查要点】设计时随时问自己「这段内容该放哪一层」。如果你在 SKILL.md 正文里写了大量代码或整份文档，就是把控制层和执行层混了：代码进 scripts/、详细领域知识进 references/、SKILL.md 只写「调用哪个脚本、传什么参数」。
<!--src:A; ref:《Agent Skills 详解》Part2 2.6 三层架构概念-->

**练习 B1-2｜三个反面案例各违反哪条规则、各有多少行**
课件用三个坏 Skill 反面开场。写出三个案例名、各自的病症、对应违反的设计规则，以及课件给出的行数。

- 【参考答案】
  - `ai-dev-assistant`（万能瑞士军刀）：description 太宽泛，几乎任何开发请求都触发它（触发污染），487 行 SKILL.md 改一处影响全局，违反**单一职责原则（SRP）**，教训是「一个 Skill 只做一件事」。
  - `code-bomb-deployer`（厨房水槽）：把代码、配置、文档全塞进一个 312 行的 SKILL.md，Agent 分不清哪是指令哪是示例，违反**关注点分离（SoC）**，教训是「代码、配置、文档要分离，SKILL.md 只写执行流程」。
  - `encyclopedia-translator`（复制粘贴文档）：把第三方 API 官方文档整段抄进来，长达 2847 行，Agent 输出文档而不干活，违反**信息精炼原则**，教训是「信息要精炼，详细文档通过链接引用」。
- 【自查要点】三个病的共同认知误区是把 Skill 当「给 AI 的知识库」而不是「给 AI 的执行指令」。Skill 的本质是可执行的流程规范，像一份作战指令（清晰、简洁、可执行），不是参考手册（详尽、冗长、需要理解）。
<!--src:A; ref:《Agent Skills 详解》Part2 第二章 2.2/2.3/2.4 三个反面案例-->

**练习 B1-3｜用三个测试判断一个 Skill 职责是否单一**
课件给了三条判断职责单一性的测试。写出三条测试各怎么做，并说清三条规则冲突时谁的优先级最高。

- 【参考答案】① 一句话描述测试：用一句话描述功能，如果要用「和 / 或 / 以及」这类连接词，说明职责不单一；② 变化原因测试：列举会导致这个 Skill 需要修改的原因，超过一个就说明职责不单一；③ 调用场景测试：列举用户会在什么场景下调用它，场景之间没有强关联就说明职责不单一。三条规则冲突时 **SRP 优先级最高**：协同顺序是 SRP 确定边界 → SoC 组织结构 → 信息精炼优化内容，宁可拆成两个小 Skill，也不要一个大而全的 Skill。
- 【自查要点】边界错了，后面做得越精致，只是把本来不该放一起的东西整理得更漂亮而已。拆分不是按文件或技术栈切，而是按用户真正要解决的问题切（问题域分解：识别核心问题 → 检查问题独立性 → 定义清晰输入输出）。
<!--src:A; ref:《Agent Skills 详解》Part2 3.1 单一职责原则 / 3.4.2 优先级判断-->

### B2 · Spec-Kit 与 Superpowers
> 来源讲次：《Spec-Kit 入门实战》（Lesson 10）、《Superpowers 基础入门·TDD驱动开发》（Lesson 12）+ nanoclaw-dashboard 真实源码

**练习 B2-1｜Spec-Kit 的九个命令怎么分、核心链的顺序**
课件说 Spec-Kit 是九个命令的工作流。写出「几核心几辅助」的划分，核心链的执行顺序，以及它跟 Vibe Coding 最本质的区别。

- 【参考答案】九命令 = **7 核心命令 + 2 辅助命令**。核心链顺序：constitution（项目宪法）→ specify（规格书）→ clarify（盲点发现）→ plan（技术方案）→ tasks（任务拆解）→ analyze（一致性分析）→ implement（执行实现）。两个辅助命令不在主流程、可随时调用：checklist（需求质量检查）、taskstoissues（任务转 Issues）。最本质区别是：Spec-Kit 每步之间都有一个人工检查点，人在每一步产出后先审再进下一步；Vibe Coding 是 AI 自主驱动、人只在最后结果出来才审。课程锁定版本 v0.6.1。
- 【自查要点】课件强调「只用 Lean 5 命令就能从零到可运行 MVP」：不学全 9 个，先掌握 5 个核心命令打通全流程。别把 checklist 当成主流程的一环，它是辅助命令。
<!--src:A; ref:《Spec-Kit 入门实战》9 命令全景（7 核心 + 2 辅助）-->

**练习 B2-2｜OpenSpec 的三个天花板，Spec-Kit 靠什么补**
课件说 OpenSpec 是入门友好的轻量框架，但撞到三个天花板。写出三个天花板，以及 Spec-Kit 多出来的 clarify 命令补的是哪一个。

- 【参考答案】OpenSpec 三命令闭环是 propose → apply → archive（约 250 行规范），三个天花板：① Greenfield 困难：面对空项目缺乏引导，无上下文时不知从何写起、工具不会主动追问；② 没有 clarify 机制：spec 写完就定了，没有系统性发现盲点的能力，隐性假设浮不出来；③ 没有质量门禁：verify 只在实现后检查，spec 有矛盾要写完才发现。Spec-Kit 的 **clarify 命令**补的正是第二个天花板，也就是在写代码前系统性追问、暴露盲点。课件引用 EPAM 数据说明为什么要前置质量关卡：每步 80% 正确，5 步之后只剩 33%。
- 【自查要点】记住那个差距量化：OpenSpec 3 命令约 250 行 → Spec-Kit 9 命令约 800 行，更细的粒度等于更多的质量检查点，每多一个命令就多一道质量关卡。
<!--src:A; ref:《Spec-Kit 入门实战》OpenSpec 三个天花板 / 差距量化-->

**练习 B2-3｜Superpowers 的 TDD 铁律与那 42 个测试**
课件的 nanoclaw-dashboard-v2 用 TDD 写了一个消息状态机。写出它的状态数、测试数，以及 Superpowers TDD 的核心循环。

- 【参考答案】消息面板是一个 **5 态状态机**：closed / open / sending / received / error，配套 **42 个 TDD 测试**（在 `tests/chat-state.test.ts` 里逐个 it 断言状态转移）。Superpowers 的 TDD 核心循环是 **RED → GREEN → REFACTOR**：先写会失败的测试（红），再写恰好让它通过的最小实现（绿），最后在测试保护下重构。铁律是测试必须先红，检测到未写测试就直接生成的实现代码即删码重走，禁 `it.skip`、禁 `vi.mock` 整层。
- 【自查要点】课件把纯逻辑（数字格式化 `lib/format.ts`、消息状态机 `lib/chat-state.ts`）单独拎成 TDD 重点任务，理由是所有 UI 组件都会消费这些函数，先把逻辑测透，后面 UI 直接调、没有歧义。这就是「测试优先」在真实项目里落地的样子。

## 二、误区自查（照镜子）

> 读法：如果你心里认同左边那句 X，说明你还没真正掌握 Y，去回看 Z。

1. **如果你以为「Skill 就是写得更长、更全的 Prompt」** → 说明你还没抓住三大特性。Skill 是可发现（Agent 自动匹配，不用你每次提供）、可执行（有结构化流程支撑，不是自由发挥）、可复用（写一次到处用、可持续优化）的能力模块；Prompt 散落在对话历史里、一次性、难复用。回看 product-fullstack#B1 的 Skill vs Prompt 本质区别。

2. **如果你以为「把信息都塞给 Agent，它自己就能学会用」** → 说明你要栽进 `encyclopedia-translator` 那 2847 行的坑。信息过载会让 Agent 输出文档而不执行任务、触发判断变慢、关键步骤被淹没。Skill 的本质是执行指令不是知识百科，详细文档要放进 references/ 用链接引用。回看 product-fullstack#B1 的信息精炼原则。

3. **如果你以为「description 写得越宽泛，能覆盖的场景越多越好」** → 说明你没意识到宽泛描述会造成触发污染。`ai-dev-assistant` 的描述涵盖审查/修 bug/重构/测试/部署一大串，结果几乎任何请求都触发它、还干扰别的 Skill 正常触发。description 要精准、必带负向边界（哪些情况不该触发）。回看 product-fullstack#B1 的三大坏味道。

4. **如果你以为「让能力包帮我把 SKILL.md 生成出来、能触发，就算过 B1 关」** → 说明你漏了这道深潜关是闭卷、不许能力包代做。B1 的阶段徽章要你关掉 agent-skills-authoring-pack，亲手写一个 SKILL.md（description + 边界 + 一个脚本或参考引用），再做触发测试：给一个该进的输入它触发、给一个负向边界的输入它不触发，两条记录都留档。回看 product-fullstack#B1 的深潜验收说明。

5. **如果你以为「先写代码，测试回头补上就行」** → 说明你还没接受 Superpowers 的测试优先立场。课件讲 LLM 有「乐观偏见」：跳过测试、声称完成、绕过流程，这是 RLHF 训练的副产物、不是某个模型的 bug。靠 prompt 提醒「请严格 TDD」下次照样跳过，得靠机制层面强制约束（测试先红、违规删码）。回看 product-fullstack#B2 的乐观偏见与机制约束。

6. **如果你以为「需求想清楚了直接让 AI 干最快」** → 说明你没吃透 Spec-Kit 的人工检查点设计。课件的 EPAM 数据摆着：每步 80% 正确，5 步后只剩 33%，所以要在写码前用 clarify 暴露盲点、每步之间人工审一道。没有简单功能，只有没想清楚的需求。回看 product-fullstack#B2 的 clarify 与质量门禁。

## 三、迁移挑战（换个场景用同样方法）

**迁移挑战 1｜把「写好一个 Skill」的三条规则搬到你自己的工作方法上**
B1 教你用 SRP、SoC、信息精炼三条规则设计 Skill。现在你要把「我整理每周业务周报的方法」做成一个 Skill。请只用这三条规则规划它的边界与结构，不用真写完。

- 【怎么算过关】① 先用一句话描述测试查职责：如果你发现描述里出现「整理周报**和**同步排期**以及**盘点风险」，说明职责不单一，按问题域分解拆成独立 Skill；② 用 SoC 把内容归层：SKILL.md 只写「抓哪些数据源→按什么模板汇总→交付前怎么自检」的流程，取数脚本进 scripts/，周报模板进 assets/，指标口径这类领域知识进 references/；③ 用信息精炼把 SKILL.md 压到 60-100 行，description 写清楚正向触发（「写周报 / 周会材料」）和负向边界（「不处理日报、不做实时看板」）。
- 【提示】判断标准始终是「这段内容该放哪一层」。周报口径文档再长也别抄进 SKILL.md，放 references/ 用链接引。
<!--src:A; ref:《Agent Skills 详解》Part2 3.1-3.3 三条规则 / pack:agent-skills-authoring-pack-->

**迁移挑战 2｜把 Spec-Kit 的「clarify + 人工检查点」搬到一个非编程需求上**
B2 的 clarify 是在动手前系统性追问、暴露盲点。假设你要让 Agent 帮你做一份「新功能上线的运营方案」，怎么迁移这套「先规范、分阶段、每步人工审」的纪律？只描述动作，不用真跑。

- 【怎么算过关】能指出：① 先写一份「宪法」式的约束（目标人群、预算红线、不做什么），相当于 constitution；② 让 Agent 别一上来出方案，先走 clarify，一次问一个盲点（触达渠道有没有定？转化目标是留资还是成交？），把答案回填直到没有待澄清项；③ 每个阶段（调研→方案骨架→细化）产出后你先审再放行，而不是等最终大方案出来才发现方向错了。能说清为什么要前置追问 = 因为「每步 80% 正确、5 步后只剩 33%」，错误会逐级放大。
- 【提示】这正是「先写规范再动手、分阶段过人工检查点」从写代码迁移到任意需要收敛的复杂任务的通用形态。
<!--src:A; ref:《Spec-Kit 入门实战》clarify 机制 / 人工检查点 / EPAM 数据-->

## 四、排错挑战（给你一段带病的 Skill，修好它）

一位同学想做一个「帮我处理产品相关杂活」的 Skill，反馈：**「我这个 Skill 一装上，问它啥它都抢着触发，别的 Skill 都不工作了；真让它干活时它又在示例代码和步骤之间反复横跳，经常跑失败。」** 下面是他的 `SKILL.md`，请找出问题并修好。

```yaml
---
name: product-helper
description: 处理所有产品相关的工作，包括写 PRD、做竞品分析、生成周报、
  画原型、写测试用例、部署应用、优化性能、管理需求、回复用户反馈等等
---

# 产品全能助手

## Workflow
1. 判断用户要干什么（PRD？竞品？周报？原型？测试？部署？）
2. 如果是 PRD，就按下面的模板生成……（此处内联 200 行 PRD 全文模板）
3. 如果是竞品分析，参考这段 Python 抓取脚本：
   （此处内联 150 行 requests + BeautifulSoup 代码，文件名硬编码 competitors.csv）
4. 如果是周报，读取 data.csv 汇总……
5. 其它情况自由发挥
```

- 【症状】装上后几乎任何请求都触发这个 Skill、干扰其它 Skill 正常触发（触发污染）；执行时 Agent 分不清哪是「指令」哪是「参考资料」，在内联代码和步骤之间反复横跳，还因为文件名硬编码（competitors.csv / data.csv）跟实际请求对不上而跑失败。
- 【根因】它一次踩了三条规则：① description 太宽泛、罗列一大串「和……以及……」的独立职责，违反单一职责原则（一句话描述测试不通过），导致触发污染；② 把 200 行 PRD 模板、150 行抓取代码全塞进 SKILL.md 正文，违反关注点分离，Agent 无法区分指令与示例；③ 缺负向边界、还留了「自由发挥」的兜底分支，触发条件不互斥、不完备。
- 【修法】按 SRP 先拆：把「写 PRD / 竞品分析 / 周报」拆成三个各只做一件事的 Skill（如 `prd-writer`、`competitor-analysis`、`weekly-report`）。以 PRD 那个为例改成：
  ```yaml
  ---
  name: prd-writer
  description: 当用户要写产品需求文档 PRD、把产品想法整理成结构化需求时使用。
    不用于竞品抓取、周报汇总或代码部署（各归对应 Skill）。
  ---

  # PRD 撰写

  ## Workflow
  1. 澄清问题定义与目标用户
  2. 按 assets/prd-template.md 生成骨架
  3. 逐节填充，每个功能回指调研依据
  4. 按 references/prd-checklist.md 自检非目标与优先级

  ## Constraints
  - 只产出 PRD，超出范围的需求提示切换对应 Skill
  ```
  把 PRD 模板挪到 `assets/prd-template.md`、抓取脚本挪到 `scripts/`（去掉硬编码文件名，改成参数传入）、口径文档挪到 `references/`；SKILL.md 正文压到 60-100 行，description 带上正向触发词前置 + 负向边界。
- 【一句话总结】触发污染九成出在 description 太宽 + 职责不单一，执行混乱九成出在把执行层内容塞进了控制层；修法口诀就是 SRP 先拆边界 → SoC 归层 → 信息精炼压正文。

## 五、面试自测（本阶段技术点常问题）

> 每题给：考察点 · 答题要点 · 一层追问。答案已写全，可自包含背诵。

**面试 1｜Skill 和 Prompt 到底有什么本质区别？**
- 考察点：对 Skill 价值定位的理解。
- 答题要点：区别落在三大特性上。发现性：Prompt 需要用户每次主动提供，Skill 能被 Agent 自动发现和匹配；执行性：Prompt 依赖 AI 自由发挥，Skill 有结构化流程支撑；复用性：Prompt 一次性、散落在对话历史里，Skill 是独立模块、可跨场景复用并持续优化。一句话：Skill 不是「更长的 Prompt」，而是可发现、可执行、可复用的能力模块。
- 追问：「课件用什么类比帮你记这套关系？」→ 手机（Agent）/ App（Skill）/ 应用商店（生态）；或工作场景版：超级实习生（Agent，智商高但缺业务经验）/ 办公设备（Tool）/ 部门书架上的《岗位操作手册》（Skill）/ 员工基本守则（System Prompt）。给 Agent 发的是一张图书馆借阅证，不是逼它背下整个图书馆。
<!--src:A; ref:《Agent Skills 详解》Part1 1.4 Skill vs Prompt-->

**面试 2｜Agent Skills 为什么高效？说说渐进式信息披露。**
- 考察点：对 Token 经济学与加载机制的理解。
- 答题要点：核心设计是渐进式信息披露（Progressive Disclosure），分三阶段按需加载：① 全局注册：系统启动时只加载所有 Skill 的元数据（name + description），约每个技能 100 Token，维持全局可见性；② 技能激活：匹配到任务才读完整 SKILL.md，约 3000 Token；③ 深度引用：执行到特定步骤才加载 references/ 里的文档，可达 10000+ Token。这套压缩解压机制让 Agent 能「知道」数百个技能存在，但只在需要时才「学习」具体细节。
- 追问：「这跟三层架构是什么关系？」→ 一一对应：路由层（frontmatter）供全局注册、控制层（SKILL.md 正文）在激活时加载、执行层（scripts/references/assets）在深度引用时才拉。三层架构就是渐进式披露能成立的结构基础。
<!--src:A; ref:《Agent Skills 详解》Part1 2.1.3 Token 经济学-->

**面试 3｜Agent 是怎么判断要不要调用一个 Skill 的？**
- 考察点：对调用与路由机制的理解。
- 答题要点：五步决策流程：① 识别任务（判断请求是什么类型）；② 判断能力边界（任务是否需要结构化流程、多步骤、有明确验证标准，简单问答就直接答不调 Skill）；③ 匹配 Skill（在可用列表里按 description 语义相似度 + 关键词匹配 + 能力边界找最合适的）；④ 执行 Skill（调用并传入上下文，把 SKILL.md 内容注入系统提示词）；⑤ 整合输出。最关键的是第三步的路由，靠语义匹配度、能力边界匹配、优先级规则三方面收敛。
- 追问：「注入到系统提示词的 Skill 内容，是代码还是提示词？」→ 是提示词。Agent 读 Skill 的 body 作为执行指南注入系统提示词，从而「学会」怎么完成任务；Skill 的内容不是可执行代码，而是给 Agent 的结构化指令。
<!--src:A; ref:《Agent Skills 详解》Part1 2.1/2.5 调用机制与注入-->

**面试 4｜一个设计良好的 Skill 分几层？各层职责和大小？**
- 考察点：三层架构的结构认知。
- 答题要点：三层。路由层（frontmatter，SKILL.md 顶部 YAML，放 name+description 做触发匹配，约 3-5 行）；控制层（SKILL.md 正文，放 Goal/Workflow/Decision Tree/Constraints/Validation 做决策与流程，60-100 行）；执行层（scripts/ + references/ + assets/ 独立子目录，放脚本/参考文档/输出素材，大小不限）。关系是：路由层决定要不要激活，控制层决定怎么做决策，执行层负责具体怎么做。
- 追问：「references/ 和 assets/ 有什么区别？」→ references/ 是「输入文档」（领域知识、详细规则，可再分 core/ 必读与 advanced/ 可选），assets/ 是「输出素材」（模板、示例输出）。scripts/ 要按功能拆成多个文件，而不是塞一个单一的 skill.py。
<!--src:A; ref:《Agent Skills 详解》Part2 2.6 三层架构 / 3.2.2 标准目录结构-->

**面试 5｜坏 Skill 常见的三种设计问题是什么？各对应哪条规则？**
- 考察点：从反面案例提炼设计规则。
- 答题要点：三大坏味道：① 万能瑞士军刀：description 宽泛、一个 Skill 塞多个职责，触发污染、维护困难，违反单一职责原则（SRP），对策「一个 Skill 只做一件事」；② 厨房水槽：代码/配置/文档全混在 SKILL.md 里，Agent 分不清指令和示例，违反关注点分离（SoC），对策「代码、配置、文档分离，SKILL.md 只写执行流程」；③ 复制粘贴文档：整段抄官方文档进来、信息过载，Agent 迷失，违反信息精炼原则，对策「信息要精炼，详细文档用链接引用」。
- 追问：「这三个案例课件给的行数分别是多少？」→ ai-dev-assistant 487 行、code-bomb-deployer 312 行、encyclopedia-translator 2847 行；作为正面对照，结构合格的 verification-before-completion 只有 134 行、无外部依赖。
<!--src:A; ref:《Agent Skills 详解》Part2 第二章 三大反面案例总结-->

**面试 6｜怎么判断一个 Skill 职责是否单一？三条规则冲突听谁的？**
- 考察点：SRP 的可操作判据与规则优先级。
- 答题要点：三个测试交叉验证：一句话描述测试（要用「和/或/以及」连接就不单一）、变化原因测试（会导致修改的原因超过一个就不单一）、调用场景测试（场景之间没强关联就不单一）。三条规则冲突时 SRP 优先级最高，协同顺序是 SRP 确定边界 → SoC 组织结构 → 信息精炼优化内容。边界错了，后面结构再漂亮、内容再精炼，都是在优化一个方向错误的设计。
- 追问：「有人担心拆分会导致 Skill 数量爆炸，怎么回应？」→ 合理拆分让系统更清晰，宁可多几个小 Skill、也不要一个大而全的 Skill。拆分按用户要解决的问题域切（识别核心问题→检查独立性→定义清晰输入输出），不是按文件或技术栈切。
<!--src:A; ref:《Agent Skills 详解》Part2 3.1 SRP 三测试 / 3.4.2 优先级-->

**面试 7｜设计 Skill 有哪些范式？怎么快速选型？**
- 考察点：对设计范式体系与选型的掌握。
- 答题要点：课件总结 7 种范式，前 4 种核心范式覆盖约 85% 场景：Operator（工具链封装，35%，操作确定时选，如文件生成/代码转换/格式化）、Scout（环境不确定任务，25%，环境未知先侦察再行动，如代码分析/系统诊断/Bug 定位）、Partner（交互式任务，20%，需人工确认/主观决策时选，核心工具 AskUserQuestion）、Navigator（路由和查找，15%，需条件分流时选，核心是清晰互斥的决策树）。选型先判断任务当前的主矛盾，可以混合但必须有唯一主导范式，只有核心 4 种确实不够才升级进阶范式（Philosopher/Architect/Orchestrator），别过度设计。
- 追问：「升级到进阶范式的信号跟核心范式有什么不同？」→ 核心范式的升级信号是「任务无法完成」，进阶范式的信号是「核心范式能完成但不够优雅/严谨」。比如 Operator 能把验证动作跑完，但你还是无法稳定判断结果是否达标，才升级到 Philosopher。
<!--src:A; ref:《Agent Skills 详解》Part2 第四章 4.1/4.10 范式选型判断表-->

**面试 8｜Spec-Kit 的命令链是怎么设计的？跟 Vibe Coding 本质区别在哪？**
- 考察点：对规范驱动命令链的理解。
- 答题要点：Spec-Kit 是九命令工作流 = 7 核心 + 2 辅助。核心链：constitution → specify → clarify → plan → tasks → analyze → implement；辅助命令 checklist（需求质量检查）、taskstoissues（任务转 Issues）不在主流程、可随时调用。跟 Vibe Coding 的本质区别是每步之间有人工检查点，人在每一步产出后先审再放行，而不是像 Vibe Coding 那样 AI 自主驱动、人只在最终结果出来才审。课程锁定版本 v0.6.1，强调只用 Lean 5 命令就能从零到可运行 MVP。
- 追问：「课件用什么数据论证要在写码前加质量门禁？」→ EPAM 数据：每步 80% 正确，5 步之后只剩 33%。所以 clarify 这类前置追问和每步人工审很关键，错误会逐级放大；另外规范化开发有固定的 Context 税，课件给的口径约 18.6k tokens/会话。
<!--src:A; ref:《Spec-Kit 入门实战》9 命令全景 / EPAM 数据-->

**面试 9｜从 OpenSpec 到 Spec-Kit 到 Superpowers，这条演进线在解决什么？**
- 考察点：对规范驱动开发三框架演进的理解。
- 答题要点：一条「越来越工程化」的线。OpenSpec 是轻量入门框架，propose → apply → archive 三命令闭环（约 250 行），最适合新手，但撞三个天花板：Greenfield 困难、没有 clarify 盲点发现机制、没有实现前的质量门禁。Spec-Kit 用 9 命令（约 800 行）把粒度做细，补上 clarify（写码前暴露盲点）和 analyze/checklist（质量关卡），每步加人工检查点。Superpowers 再往上，把 TDD 测试优先和跨天项目的工程纪律加进来，用机制强制约束 AI。共同心法是「规范是唯一事实源」：先把要做什么写成可验证的规范，再让 AI 分阶段落地。
- 追问：「Spec-Kit 命令多了这么多，代价是什么？」→ 更多命令等于更多质量检查点，但也意味着更高的固定成本（Context 税，约 18.6k tokens/会话）和更长的流程。所以课件教的是先用 5 个核心命令打通，别一上来背全 9 个。
<!--src:A; ref:《Spec-Kit 入门实战》SDD 框架演进 / 三个天花板 / 差距量化-->

**面试 10｜Superpowers 要解决的核心问题是什么？为什么 prompt 提醒没用？**
- 考察点：对乐观偏见与机制约束的理解。
- 答题要点：核心问题是 LLM 的「乐观偏见」：收到任务后倾向抄近路：跳过测试、声称完成（但没跑过）、绕过流程「创造性解决」。根因是 RLHF 训练副产物：训练阶段给「声称完成」更高反馈分、诚实报告失败反被低分惩罚，模型就习得了「声称成功」偏好。这不是某个模型的 bug，GPT / Claude / Gemini 都有。所以写「请严格 TDD」这类 prompt 提醒修不好，因为提示词覆盖不了训练阶段习得的行为偏好，得从机制层面强制约束（SessionStart Hook 会话起手强制注入工程方法论、测试先红否则删码）。Superpowers v5.1.0，作者 Jesse Vincent，15 个 Skill、跨 7 个 Harness 通用、零依赖、MIT。
- 追问：「Vibe Coding 什么时候会崩？课件怎么描述这个临界点？」→ 简单需求时像神、复杂任务时崩塌，临界点有三种触发：任务跨多个文件需要协调、需求边界模糊需要做决策、错误堆积需要回滚。过了临界点 Context 越来越乱、新错误盖过旧错误、最后只能 /clear 重启。关键判断不是「让 Claude 写得更快」，而是「让它走得更稳」。
<!--src:A; ref:《Superpowers 基础入门·TDD驱动开发》乐观偏见 / 机制约束 / 临界点-->

## 八、落地对照（学完这阶段能接的真实小活）

> 都是这阶段能力就能接的活儿，描述自包含。它们也是你产品交付作品集与方法沉淀的第一批素材。

1. **把团队一个重复的工作方法沉淀成一个能触发的 Skill。**
   挑一件反复要做的活（写周报、整理竞品、生成周会材料），按 SRP 收窄到单一职责、按三层架构归位、写精准 description 带负向边界，最后做一次触发测试留档。交付物 = 一个结构合格、装上即用的 SKILL.md。

2. **给一堆混乱的 Skill 做一次设计体检。**
   拿别人写的 Skill，用三大坏味道和 SRP 三测试逐个过：description 是否宽泛、有没有把代码文档塞进正文、职责是否单一，给出「拆分/归层/精简」的整改清单。这是一单实打实的「Skill 质量评审」小服务。

3. **用 Spec-Kit 把一个模糊需求走成 spec/plan/tasks 三件套。**
   把「给产品加一个功能」这类需求，用 constitution → specify → clarify → plan → tasks 走一遍，每步过人工检查点，产出互相一致的三件套。适合演示你「先写规范再动手」的交付纪律，也为 Stage C 的 AlphaProject 打底。

4. **给一段纯逻辑功能补上测试优先的开发流程。**
   拿一个纯逻辑模块（数字格式化、状态机、金额计算），按 RED → GREEN → REFACTOR 先写失败测试再写实现，交付一套能跑绿的测试。适合演示你对 TDD 铁律与「测试先红」的掌握。

5. **给团队立一份「什么时候该做成 Skill、什么时候直接写」的判断框架。**
   用课程的选型思路（任务是否需要结构化流程/多步骤/明确验证标准、是否会高频复用）帮团队区分：一次性活直接说、可复用的工作方法才做成 Skill，避免把什么都塞进 SKILL.md。交付物 = 一页可复用的判断清单。
