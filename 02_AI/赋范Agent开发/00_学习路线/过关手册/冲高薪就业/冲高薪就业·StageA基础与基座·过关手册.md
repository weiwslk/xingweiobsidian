## 一、随堂练习

按节点来，做完对答案。每题先自己写，再看参考答案和自查要点。

### A1 大模型在线 API 调用与本地部署

**练习 1｜Token 与计费**
你调用一次模型，输入是 800 字中文的提示词，模型回了 400 字中文。用课件的快速估算法，分别估这次的输入 Token 和输出 Token 大概各是多少？为什么输出那部分的钱通常比输入贵？

【参考答案】课件的中文估算口径是「字数 × 0.5 ~ 1」。输入 800 字约 400 ~ 800 Token，输出 400 字约 200 ~ 400 Token。几乎所有官方平台（OpenAI、Anthropic、Google、DeepSeek、阿里云、智谱）都按 Token 计费，而且输入（prompt）和输出（completion）分开计价，输出 Token 单价更高，因为输出是模型逐步生成、算力占用更重的部分。
【自查要点】你有没有把中文和英文的系数搞混（英文是字数 × 0.25，代码是字符数 / 4）；有没有说清「按 Token 不按字符 / 不按请求次数」这条计费本质。
<!--src:A; ref:A1《大模型在线API接入基础入门实战》Token 与计费小节-->

**练习 2｜API-Key 安全**
说出 API-Key 的三个职能，并写出「把 Key 放进代码仓库」为什么是红线。给出课件推荐的正确管理方式。

【参考答案】三职能：身份认证（证明你是谁）、权限控制（决定你能调哪些模型、QPS 与上下文上限）、费用归属（这个 Key 产生的账单记到你头上）。Key 泄露最危险的就是账户被恶意消耗。正确做法：Key 走环境变量注入，绝不硬编码；用 `.env` 文件集中管理并把 `.env` 加进 `.gitignore`；Python 里用 `os.getenv()` 读取，或用 `python-dotenv` 的 `load_dotenv(override=True)` 动态加载。
【自查要点】API-Key 的特征你记得吗（通常以 `sk-` 或 `ak-` 开头，长度 40~60 字符）；有没有把「硬编码在代码 / 提交到 Git / 日志明文打印」这三条禁忌说全。
<!--src:A; ref:A1《大模型在线API接入基础入门实战》API-Key 小节-->

**练习 3｜OpenAI 兼容格式**
课件说「几乎所有平台都声称兼容 OpenAI API 格式」。要把一段调用 DeepSeek 的代码切到阿里百炼，最少改哪几个配置项？为什么能做到这么少？

【参考答案】最少改两项：`base_url`（平台地址）和 `model`（模型名）。因为 OpenAI 的 `chat.completions.create()` 接口以 `model` 和 `messages` 两个必填参数为核心，已成行业事实标准，DeepSeek、阿里百炼、智谱、OpenRouter 都实现了这套格式，所以业务代码不用重写，只换配置就能跨平台。
【自查要点】你能说清 SDK 到底替你处理了什么（HTTP 头部、JSON 序列化、错误处理）；能不能举出「不用 SDK 手写 requests.post」和「用 SDK」两种写法的差别。
<!--src:A; ref:A1《大模型在线API接入基础入门实战》OpenAI SDK 兼容格式小节-->

### A2 部署软硬件环境准备

**练习 1｜显卡显存对照**
不看课件，写出 H100、A100、4090、3090 各自的显存容量。再回答：单卡显存不够时，课件给的解决思路是什么？

【参考答案】课件显存表：H100 80GB、A100 80/40GB、H800 80GB、A800 80GB、4090 24GB、3090 24GB。单卡不够时用多卡配置堆总显存，只要总显存超过官方推荐配置即可，配合流水线并行 / 张量并行 / CPU 卸载让小显存卡也能跑大模型。
【自查要点】选显卡的首要准则你记得吗（显卡显存要高于模型官方最低显存要求）；有没有混淆消费级（RTX 3090/4090）和数据中心级（A100/H100）。
<!--src:A; ref:A2《开源大模型本地部署硬件指南》选择满足显存需求的 GPU 小节-->

**练习 2｜4090 与 A100 之争**
课件为什么说做推理选 4090 很划算，但做大模型训练 4090 就吃力？请用「算力」和「通信带宽」两个词解释。

【参考答案】按课件数据，4090 的 FP16 算力约 330 Tflops，甚至略高于 A100 的 312 Tflops，而推理主要吃算力、显卡单模型跑就够，所以 4090 推理性价比高（售价约 1600 美元 vs A100 约 15000 美元）。但训练要在大量 GPU 间做数据 / 流水线 / 张量三种并行，极度依赖通信带宽；4090 的通信带宽仅 64 GB/s，A100 是 900 GB/s，大规模训练时通信会成为瓶颈，短板理论下整卡能力被拉低。
【自查要点】你能不能顺带说清「预算相近时两张 3090（共 48G）比一张 4090 更适合跑大模型」这个结论及理由（总显存更多、还能练多卡代码）。
<!--src:A; ref:A2《开源大模型本地部署硬件指南》单卡4090 vs A100 / 双卡3090 小节-->

### A3 DeepSeek 部署与调用方法

**练习 1｜四种部署方式**
课件把 DeepSeek 的部署与调用分成哪四类？如果你手上没有 GPU，只想先跑通，选哪条路，为什么？

【参考答案】四类：本地部署、企业级部署、API 调用、高性能量化部署（KTransformers）。无 GPU 时先走 API 调用，因为它不占本地显存、按 Token 付费即可跑通，部署那部分可以先看讲解，等有卡再本地或量化落地。
【自查要点】你分得清 `deepseek-chat` 对应 V3、`deepseek-reasoner` 对应 R1 吗；知道本地 Ollama 一键起的是量化版（如 `ollama run deepseek-r1:32b` 约占 20GB 显存），要满血 V3/R1 得走官方 API 或企业级部署这个区别吗。
<!--src:A; ref:A3《大模型部署与调用方法》DeepSeek 四种部署方式-->

**练习 2｜调用 R1 API 的坑**
你把一段调 `deepseek-chat` 的代码直接把模型名换成 `deepseek-reasoner`，还传了 `temperature=0.2` 并要求 Json 输出。课件里说会出什么问题？

【参考答案】DeepSeek-R1（`deepseek-reasoner`）在 API 上不支持 Function Call、Json Output、FIM 补全，也不支持 `temperature`、`top_p`、`presence_penalty` 等参数（设置不报错但不生效）。它的最大上下文是 64K，会多返回一个与 `content` 同级的 `reasoning_content` 思维链字段，且这段思维链长度不计入 64K。所以你要的 Json 输出拿不到，`temperature` 也是白设。
【自查要点】你能说出 R1 相对 V3 多了什么（`reasoning_content` 思维链）、少了什么（上面那几项功能与参数）。
<!--src:A; ref:A3《大模型部署与调用方法》DeepSeek-R1 API 调用小节-->

### A4 部署策略与工具详解（Ollama / vLLM）· 深潜关卡

**练习 1｜五维选型对照**
按课件口径，从「适用规模、并发能力、显存 / 硬件占用、易用性、生产就绪」五个维度，各写一句 Ollama 与 vLLM 的差别。

【参考答案】Ollama：面向个人本地，单人调试友好，一键安装单命令启动，CPU-GPU 混合应用，并发弱，生产就绪度低。vLLM：面向企业多并发，优先性能与可扩展，纯 GPU 优化，靠 PagedAttention 管理 KV cache、持续批处理、张量并行做到高吞吐（比 Transformers 传统推理库吞吐高一个数量级），并发强、适合生产，但实现更重、仅支持 Linux。一句话判据：单人调试用 Ollama，要扛并发 / 上生产才上 vLLM。
【自查要点】这是本阶段过关关卡的核心产物，你的手绘对照表要覆盖这五维；vLLM 的三个核心优化点（内存管理 / 持续批处理 / 张量并行）能不能不看书说出来。
<!--src:A; ref:A4《大模型部署策略与工具详解》Ollama 与 vLLM 框架概览-->

**练习 2｜环境先决条件**
你打算在一台 Windows 机器上用 vLLM 起服务，同事说不行。课件里 vLLM 的两个硬性先决条件是什么？

【参考答案】vLLM 仅支持 Linux 操作系统，官方没有 Windows 兼容版本；且运行的 Python 版本要求在 3.8 ~ 3.12 之间。这两条是先决条件，不满足就起不来。课件也点明生产环境不会在 Windows 上部署模型服务。个人本地想在 Windows 上跑，改用 Ollama（跨 Mac / Linux / Windows）。
【自查要点】你记得 Ollama 一键安装命令的形态吗（`curl -fsSL 官方 install.sh 地址 | sh`，再 `systemctl status ollama` 看状态、`ollama run deepseek-r1:32b` 拉模型）。
<!--src:A; ref:A4《大模型部署策略与工具详解》vLLM 本地私有化部署先决条件-->

### A5 Claude Code 快速入门（Fufan-CC Flow）

**练习 1｜完整循环**
用 Claude Code 完成一个真实小任务，验收标准是什么？请说出这一阶段要建立的核心手感。

【参考答案】验收：任务产物 + 一条真实的 git commit 记录都在仓库里。核心手感是走通「对话 → 改码 → 自测 → 提交推送」的完整循环，从「自己写每一行」转向「指挥 Agent 干活并对结果负责」。这也是后面四个旗舰项目全程用 Claude Code 部署验收的基础。
【自查要点】你有没有真的产生一次 commit（而不是只在对话框里看它说改好了）；连不上模型时先跑通最小对话再让它改码。
<!--src:A; ref:A5《Claude Code 快速入门公开课（Fufan-CC Flow）》-->

**练习 2｜为什么先学基座 Agent**
本路径把 Claude Code 放在 RAG、微调、部署这些硬技术之前学，理由是什么？对求职有什么直接好处？

【参考答案】Claude Code 这类基座智能体是后续所有快车道的操作台：工具链没就绪时可以让它按课件章节陪你把脚本先跑起来，装上课程全家桶后它还能按课堂工程方法干活。先建立「指挥 Agent 完成带提交的真实任务」这个手感，后面每一站都能提速。对求职的直接好处：面试常问你怎么用 AI 编程工具协作，你能拿出真实提交记录而不是空谈。
【自查要点】你能区分「基座 Agent 本体（Cursor / Claude Code）」和「课程能力包」两层吗（前者是操作台，后者是装进去的方法）。

### A7 Agent 开发基础 + MCP 实战

**练习 1｜TAO 循环与四阶段演进**
写出 Agent 的底层运行逻辑 TAO 循环的三个环节，再用课件那句话说清提示工程、函数调用、RAG、Agent 各解决什么问题。

【参考答案】TAO 循环：Think（思考）→ Act（行动）→ Observe（观察），三者构成可控的自治循环。课件原话：提示工程解决理解问题，函数调用解决行动问题，RAG 解决知识问题，Agent 解决能力问题。Agent 不是更聪明的聊天机器人，它和聊天机器人是范式差别（有感知、决策、执行的完整闭合链路）。
【自查要点】你能不能说清 Function Calling 的时间点和本质（OpenAI 2023 年 6 月引入；LLM 从不真正执行函数，只生成结构化的 JSON 调用指令，执行由你的代码完成）。
<!--src:A; ref:A7《大模型 Agent 基础入门》TAO 循环与技术演进脉络-->

**练习 2｜MCP 三种传输选型**
你写了个 MCP Server 在本机调通了，客户要从异地、且高并发地调它。该选哪种传输方式？为什么不用 stdio 或 SSE？

【参考答案】选 StreamableHttp。stdio 靠 stdin/stdout 做本机进程间通信，没有网络端口、必须作为本地子进程启动，异地必然连不上；SSE 是基于 HTTP 的单向流，无多通道并发、长连接不稳，撑不起企业级。StreamableHttp 双向、长连接、支持请求批处理、并发高，是异地企业级的首选（SDK v1.8.0 起内置 `StreamableHTTPSessionManager`）。
【自查要点】本机调试起步该用哪种（stdio，`mcp.run(transport='stdio')` 一行搞定）；FastMCP 里工具怎么注册（`@mcp.tool`，docstring 就是工具契约）。
<!--src:A; ref:A7《MCP 快速入门实战》 + mcp-dev-pack 传输选型能力文件-->

**练习 3｜tool_choice 与消息拼接**
面对「让 LLM 决定要不要查天气」这种场景，`tool_choice` 该设 auto 还是 required？另外，工具执行成功了但模型却回答「无法获取」，最可能是哪里错了？

【参考答案】设 `auto`（自主判断是否调用，通用首选）。设 `required` 会逼出「为了调用而调用」的怪行为。工具成功却答「无法获取」，最常见根因是消息拼接时 `tool_call_id` 没和 LLM 返回的 `tool_call.id` 完全一致，导致模型关联不上工具结果。修法：把 `tool_call.id` 原样回填到 `role:"tool"` 的结果消息里，一字不改。
【自查要点】四种模式你记全了吗（auto 自主 / required 强制调至少一个 / none 只出文本 / 指定某工具）；知道「问实时数据时 none 下模型说无法获取是预期表现不是 bug」。
<!--src:A; ref:A7 agent-dev-basics-pack tool_choice 与消息拼接四铁律-->

## 二、误区自查

下面 8 条是本阶段最容易踩的坑，逐条问自己「我是不是这么以为的」。是，就回看对应节点。

1. 「按请求次数收费吧？」错。几乎所有官方平台按 Token 计费，且输入和输出分开计价、输出更贵。回看 career-sprint#A1。
<!--src:A; ref:A1 Token 计费小节-->

2. 「Key 硬编码在代码里，反正只有我看。」错，且危险。Key 泄露等于账户被人替你花钱，必须走环境变量 + `.env` + `.gitignore`。回看 career-sprint#A1。
<!--src:A; ref:A1 API-Key 安全小节-->

3. 「换个平台就要重写调用代码。」错。绝大多数平台兼容 OpenAI 格式，通常只改 `base_url` 和 `model` 两项。回看 career-sprint#A1。
<!--src:A; ref:A1 OpenAI 兼容格式小节-->

4. 「显存越大就一定越强，选卡只看显存。」不全对。显存要够是底线，但训练还高度依赖算力和通信带宽；4090 通信带宽只有 64 GB/s，大规模训练会卡在通信上。回看 career-sprint#A2。
<!--src:A; ref:A2 单卡4090 vs A100 小节-->

5. 「本地跑不动就没救了。」错。没 GPU 可以先走 API 调用跑通，或用量化 / 云 GPU（AutoDL）过渡，不必一开始就本地部署满血模型。回看 career-sprint#A3。
<!--src:A; ref:A3 部署方式选择-->

6. 「Ollama 和 vLLM 差不多，随便选一个。」错。Ollama 面向个人本地、单命令启动；vLLM 面向企业多并发、纯 GPU 优化、仅支持 Linux。单人调试用 Ollama，上生产扛并发才用 vLLM。回看 career-sprint#A4。
<!--src:A; ref:A4 Ollama 与 vLLM 选型-->

7. 「Agent 就是更强的聊天机器人。」错，这是范式差别。Agent 有 TAO（Think-Act-Observe）自治循环，能多步规划、自主决策、调用工具，聊天机器人只是单轮问答。回看 career-sprint#A7。
<!--src:A; ref:A7 Agent 与聊天机器人的范式区别-->

8. 「工具报错就是模型不行 / 工具没生效就是模型没调。」错。工具成功却答「无法获取」多半是 `tool_call_id` 没对齐；LLM 从不真正执行函数，它只生成 JSON 调用指令，执行在你的代码里，排错要先看消息拼接和工具注册。回看 career-sprint#A7。
<!--src:A; ref:A7 消息拼接四铁律与故障速查-->

## 三、迁移挑战

学过的东西换个场景还会用，才算真会。

**挑战 1｜给一个「企业内部 20 人客服团队」选部署方案**
需求：要接一个 14B 左右的开源模型做内部问答，20 人可能同时提问，机房里有一台装了 4 张 3090 的 Linux 服务器。请你给出选型：用 Ollama 还是 vLLM？显存够不够的判断思路是什么？如果老板又说「先给我一个能在我 Windows 笔记本上单人试玩的版本」，你怎么办？

【参考思路】面向 20 人并发、上内部生产，选 vLLM（纯 GPU 优化、持续批处理扛并发、仅 Linux，正好机房是 Linux + 4×3090 共 96G 显存）。显存判断：先按模型参数量和精度估权重占用，再留出 KV cache 与并发批处理的余量，总显存要高于官方最低要求，4 卡可用张量并行分摊。老板要 Windows 单人试玩版：改用 Ollama，`ollama run` 拉一个量化版单人对话即可，两套并存不冲突。这题把 A2 的显存判断、A4 的选型判据、A3 的量化降级串到了一起。
<!--src:A; ref:A2/A3/A4 显存判断 + 部署选型迁移-->

**挑战 2｜把「查天气」从一个函数升级成一个会多步的 Agent**
你已有一个能被 LLM 调用的 `get_weather(city)` 工具。现在要它能回答「我明天从北京飞上海，两地都带伞吗」这种要查两次、还要综合判断的问题。用 A7 学的东西，说清你要加哪几件事，以及并行调用两次天气该注意什么。

【参考思路】把单轮工具调用升级成 ReAct / TAO 多步循环：模型 Think（要查北京和上海两地）→ Act（发起工具调用）→ Observe（拿结果）→ 再 Think 综合判断，循环直到能回答，并设硬性步数上限防止死循环。一次响应里若模型同时要查两个城市，可并行执行两次 `get_weather` 提速，但要保证结果按 `tool_call_id` 保序回填、任一工具异常不中断整个流程（统一异常包装）。`tool_choice` 保持 `auto` 让模型自主决定查几次。这题把 Function Calling、ReAct 循环、并行调用、消息拼接红线串到了一起。

## 四、排错挑战

下面是一段「看起来对但跑不通」的真实场景，按症状 → 根因 → 修法自己先诊断，再看解析。

**场景：本地部署的 R1 服务，调用方拿不到 Json、还发现设了温度没用**

一位同学在本机用 API 调用 DeepSeek-R1（模型名 `deepseek-reasoner`），代码是从之前调 `deepseek-chat` 的脚本改的，直接把模型名换掉，其余不动。他还加了 `temperature=0.1` 想让输出更稳定，并用 `response_format` 要求返回 Json。运行后：程序不报错，但拿到的不是 Json，`temperature` 调了也感觉没变化，另外日志里多出一大段 `reasoning_content`。他怀疑是本地服务坏了。

【症状】调用不报错，但要求的 Json 输出拿不到；`temperature` 设了不起作用；返回里多出一段与 `content` 同级的 `reasoning_content`；同学误判为「服务坏了」。

【根因】不是服务坏了，是把 V3 的用法套到 R1 上了。DeepSeek-R1（`deepseek-reasoner`）在 API 上不支持 Function Call、Json Output、FIM 补全，也不支持 `temperature`、`top_p`、`presence_penalty` 等参数。课件明确：为了兼容已有软件，设置这些参数不会报错，但也不会生效。而 `reasoning_content` 是 R1 的思维链，与 `content` 同级、本就会返回，属于正常特性，不是异常。

【修法】① 想要 Json 结构化输出，就用 `deepseek-chat`（V3）这类支持 Json Output 的模型来做，或让 R1 只出自然语言、由后处理解析；② 删掉对 R1 无效的 `temperature` 等参数，别再靠它们调稳定性；③ 把 `reasoning_content` 当作思维链单独读取或忽略，不要塞进给用户的最终答案；④ 记住 R1 API 上限是 64K 上下文，且 `reasoning_content` 长度不计入这 64K。
<!--src:A; ref:A3《大模型部署与调用方法》DeepSeek-R1 API 调用能力与参数限制-->

**面试题 1｜Token 计费与成本控制**
面试官：你怎么估一次大模型调用的成本？上线后发现账单太高，你从哪几个方向压成本？
【考察点】Token 计费机制的理解、成本敏感度、工程优化意识。
【答题要点】按 Token 计费、输入输出分开计价且输出更贵；用课件估算法（中文字数 × 0.5~1、英文 × 0.25）预估；压成本方向：精简提示词与上下文、控制输出长度、能用小模型 / 本地部署就不硬用贵模型、用提示词缓存、必要时走中转聚合（如 OpenRouter 自动路由到更便宜的供应商）。
【追问 1】那本地部署是不是一定比 API 便宜？答：不一定，要把显卡采购 / 电费 / 运维摊进去算总拥有成本，低频调用往往 API 更划算，高频稳定负载本地才可能回本。
【追问 2】怎么在不牺牲效果的前提下砍上下文？答：只喂相关片段（RAG 而非全文塞入）、历史对话做摘要压缩、结构化字段代替长自然语言。

**面试题 2｜API-Key 与密钥安全**
面试官：团队里怎么管理大模型的 API-Key？你会怎么防止泄露？

【追问 2】多人协作怎么让每个人都能跑又不共享同一把 Key？答：每人各自申请个人 Key 放本地 `.env`，代码只读环境变量、不进仓库，权限和账单按人隔离。

**面试题 3｜OpenAI 兼容格式的意义**
面试官：为什么说「兼容 OpenAI API 格式」对工程落地很重要？
【考察点】是否理解事实标准带来的可切换性。
【答题要点】`chat.completions.create(model, messages)` 已成事实标准，DeepSeek / 百炼 / 智谱 / OpenRouter 都实现它；业务代码写一套，换厂商通常只改 `base_url` 和 `model`；这让多供应商容灾、按价格 / 速度切换、灰度对比成本极低。
【追问 1】那不同厂商就完全一致、可以无脑切吗？答：不是，接口形状一致但能力有差异，比如 DeepSeek-R1 不支持 Function Call / Json Output、部分参数不生效，切换前要核对目标模型的功能与参数支持。
【追问 2】怎么在代码层做到一行切换厂商？答：把 `base_url`、`model`、`api_key` 抽成配置 / 环境变量，用统一的 OpenAI 兼容客户端读取，切换只改配置不改逻辑。

**面试题 4｜在线 API 还是本地部署**
面试官：一个新项目，你怎么决定用在线 API 还是本地部署开源模型？
【考察点】这是 Stage A 的过关口述题，也是面试高频。
【答题要点】从四个维度权衡：数据合规（敏感数据不能出内网就本地）、成本（低频用 API、高频稳定负载考虑本地回本）、性能与并发（要扛并发上 vLLM 本地或专用推理服务）、可控性与迭代速度（要微调 / 定制走本地）。先跑通再优化，无卡先用 API 验证价值。
【追问 1】本地部署你会先选哪个框架起步？答：个人验证用 Ollama（一键装、单命令启动、跨平台），企业多并发上 vLLM（纯 GPU、PagedAttention、持续批处理、仅 Linux）。
【追问 2】混合方案有意义吗？答：有，常见做法是主链路本地模型 + 兜底 / 高峰溢出走 API，或简单任务本地小模型、复杂任务调云端大模型，兼顾成本与效果。

**面试题 5｜显存怎么估、卡怎么选**
面试官：给你一个 7B 到 14B 的开源模型要本地跑推理，你怎么判断需要什么显卡、几张？
【考察点】显存判断的工程直觉。
【答题要点】先按参数量 × 精度字节数估权重占用（FP16 每参数 2 字节，量化到 INT4 每参数约 0.5 字节），再加 KV cache 和运行开销；对照课件显存表选卡（4090 / 3090 各 24GB，A100/H100 80GB）；单卡不够就多卡堆总显存并用张量并行；显存紧张先量化降级。
【追问 1】为什么推理选 4090 常比 A100 划算？答：推理主要吃算力、单模型跑，4090 FP16 算力约 330 Tflops 甚至略高于 A100 的 312，而售价差约十倍，性价比高。
【追问 2】那预算相近时一张 4090 还是两张 3090？答：跑较大模型选两张 3090，总显存 48G 更大，还能练多卡并行代码，更贴近企业多卡环境。

**面试题 6｜Ollama 与 vLLM 的选型**
面试官：Ollama 和 vLLM 有什么区别？分别什么场景用？
【考察点】本阶段过关关卡的核心知识，面试几乎必问。
【答题要点】Ollama 面向个人本地，一键安装单命令启动、CPU-GPU 混合、跨 Mac/Linux/Windows、并发弱；vLLM 面向企业多并发，纯 GPU 优化，靠 PagedAttention 管 KV cache、持续批处理、张量并行做到高吞吐（比传统推理库高一个数量级），仅支持 Linux、Python 3.8~3.12。判据：单人调试 Ollama，扛并发上生产 vLLM。
【追问 1】vLLM 靠什么把吞吐做上去的？答：核心是 PagedAttention 对 KV cache 的分页管理减少显存浪费，加上连续批处理和张量并行，最大化 GPU 利用率。
【追问 2】还知道别的部署框架吗？答：llama.cpp（纯 C/C++ 无依赖、性能高但上手难），主流三选一是 llama.cpp / Ollama / vLLM。

**面试题 7｜量化是什么、代价是什么**
面试官：模型量化解决什么问题？INT4 相比 FP16 有什么代价？
【考察点】对精度与资源权衡的理解。
【答题要点】量化通过降低数值精度来减小模型体积、加快推理、降低显存与能耗，让模型能塞进资源受限的设备；FP32 是标准训练推理格式，FP16 半精度速度快更省显存且效果相近，INT4 只保留很低精度、显存占用最小但输出精度下降。量化程度越高对硬件要求越低，但精度损失越大。
【追问 1】什么场景值得量化？答：显存不够、要在消费级卡或边缘设备上跑推理、对延迟和成本敏感而能容忍轻微精度损失时。
【追问 2】课件里高性能量化部署提到什么方案？答：KTransformers 这类高性能部署 + 动态量化，可以在有限显存上跑起更大的 DeepSeek 模型。

**面试题 8｜Agent 和聊天机器人的本质区别**
面试官：你怎么跟非技术的人解释 AI Agent 和 ChatGPT 的区别？
【考察点】认知层是否清晰，能否讲人话。
【答题要点】聊天机器人是单轮问答，你问一句它答一句；Agent 有感知 / 决策 / 执行的完整闭合链路，能自己拆解任务、多步规划、调用工具、看结果再调整。二者是范式差别不是程度差别，类比是定速巡航和自动驾驶。底层运行逻辑是 TAO 循环（Think → Act → Observe）。
【追问 1】那 Agent 的能力从哪来，为什么不用为每个任务重训模型？答：靠大模型的涌现能力，通过提示工程、工具描述、示例演示就能让它学会新技能，模型规模够大后这种推理才可靠，所以 Agent 到 2024 年后才真正可用。
【追问 2】提示工程、函数调用、RAG、Agent 的关系？答：提示工程解决理解问题，函数调用解决行动问题，RAG 解决知识问题，Agent 把这些整合起来解决能力问题。

**面试题 9｜Function Calling 的本质**
面试官：Function Calling 里，模型到底有没有执行你的函数？
【考察点】一个高频「陷阱题」，答错暴露没写过工具调用。
【答题要点】没有。LLM 从不真正执行函数，它只根据工具定义生成结构化的调用指令（JSON，含函数名和参数），真正的执行由你的代码完成，再把结果回传给模型继续推理。所以工具定义质量、消息拼接精度、执行层健壮性三处决定成败。
【追问 1】那工具定义里最影响调用准确率的是什么？答：参数的 `description`，多写示例和格式要求投入产出比极高，`required` 要声明清楚必填项。
【追问 2】工具执行成功但模型回答「无法获取」，怎么排查？答：优先查 `tool_call_id` 是否与 LLM 返回的 `tool_call.id` 完全一致，不一致模型就关联不上结果。
<!--src:A; ref:A7 agent-dev-basics-pack 核心认知与消息拼接四铁律-->

**面试题 10｜tool_choice 四模式**
面试官：`tool_choice` 有哪几种取值，分别什么时候用？
【考察点】工具调用的控制粒度。
【答题要点】auto（自主判断是否调用，通用首选、最常用）、required（强制至少调一个，适合每轮必须记日志等场景，但对不需要工具的问题会为调而调）、none（只出文本，如生成报告）、指定某个工具（强制走特定工具）。
【追问 1】用户问实时数据、你设了 none，模型说「无法获取」，是 bug 吗？答：不是，是预期表现，none 下模型本就不该调工具，要实时数据应放开为 auto。
【追问 2】什么时候该慎用 required？答：面对不确定是否需要工具的通用问答，required 会逼出「为了调用而调用」的怪行为，反而降低质量。

**面试题 11｜ReAct 循环与死循环防护**
面试官：把单轮工具调用升级成能多步推理的 Agent，你会怎么设计循环？怎么防死循环？
【考察点】自治循环的工程落地。
【答题要点】用 ReAct / TAO 循环：Think 决定下一步、Act 调工具、Observe 读结果，循环到能给出最终答案；设计智能停止条件（模型判断信息已足够）+ 硬性步数上限兜底；每步把工具结果按 `role:"tool"` 消息回填，任一工具异常做统一包装不中断整个流程。
【追问 1】硬上限设太小会怎样，太大又怎样？答：太小复杂任务没走完就被截断答不全，太大遇到绕圈会烧掉大量 Token 和时间，要按任务复杂度设并配合智能停止。
【追问 2】ReAct 和 CoT 有什么区别？答：CoT 是纯思维链推理不与外界交互，ReAct 在推理里穿插工具调用和对结果的观察，能获取外部信息、纠正中间错误。

**面试题 12｜MCP 是什么、解决什么**
面试官：MCP 是什么？它和 Function Calling 是什么关系？
【考察点】对当下工具生态标准的认知。
【答题要点】MCP（Model Context Protocol，模型上下文协议）是把外部工具 / 数据源标准化接入模型的协议，让工具生态统一，一次开发多处复用。它和 Function Calling 不冲突：Function Calling 是模型层「决定调哪个工具」的机制，MCP 是把工具以统一协议暴露给各种客户端的标准，MCP Server 里的工具最终仍通过模型的工具调用能力被触发。
【追问 1】MCP 有哪几种传输方式，怎么选？答：stdio（本机默认起点）、SSE（单向流、过渡选项）、StreamableHttp（异地企业级高并发首选）。判据是服务器和客户端在不在同一台机器、要不要高并发。
【追问 2】用 FastMCP 写一个工具，关键是什么？答：用 `@mcp.tool` 注册函数，docstring 就是工具契约（模型据此理解何时调、怎么传参），凭证走环境变量不硬编码。

**面试题 14｜岗位校准题：讲一个你做过的部署 / 调用实战**
面试官：说一个你把开源模型部署或调用起来的经历，遇到过什么坑？
【考察点】岗位校准题；面试官想听真实动手细节而非背概念。
【答题要点】选一个真做过的：比如本地用 Ollama 起 DeepSeek-R1 对话，或用 vLLM 在 Linux 多卡上起服务扛并发，或 API 调用并算清 Token 账。讲清选型理由（成本 / 并发 / 合规）、遇到的坑（显存不够→量化降级、Windows 上 vLLM 起不来→换 Ollama、把 V3 用法套 R1 导致 Json / 参数失效）和怎么定位解决的。
【追问 1】显存不够时你的处理顺序是什么？答：先量化降级（如 QLoRA / INT4）、再减 batch / 开梯度累积、还不行就多卡或换 API，别盲改参数。
【追问 2】怎么验证服务真的可用而不只是「起来了」？答：从外部发一次真实请求拿到正确结果，压一轮并发看吞吐和稳定性，接口带鉴权和错误处理。

**面试题 15｜岗位校准题：把 Stage A 能力讲成一段自我介绍**
面试官：一分钟讲讲你在大模型这块的基础能力。
【考察点】岗位校准题；能不能把技能组织成让面试官记得住的一段话。
【答题要点】按「会调、会部署、会算账、会指挥 Agent」组织：能调主流大模型在线 API 并算清 Token 成本，能在本地 / 云用 Ollama 与 vLLM 部署开源模型并按场景选型，理解显存 / 量化 / 并发的取舍，能用 Claude Code 完成带提交的真实开发，懂 Function Calling / ReAct / MCP 并能接工具给 Agent。落一个能演示的产出（脚本 / 提交记录 / 对照表）收尾。
【追问 1】这些里你最擅长哪块，深挖一下？答：挑一个你真吃透的（如 vLLM 部署或工具调用排错），准备好能撑住三层追问的细节。
【追问 2】接下来你想往哪深入？答：顺路径讲 RAG 与微调（Stage B/C），点出微调实战记录是你要重点做的简历差异化项。

## 六、模拟面试官指令

把下面这段话整段发给一个装好全家桶的 Agent，让它扮演面试官闭卷考你。别提前看答案。

**给 Agent 的角色设定与指令：**

> 你现在是一家做大模型应用的公司的资深面试官，我在面试「大模型 / Agent 应用开发工程师」岗位。请只考「大模型调用 / 部署 / 成本」和「基座智能体 + Function Calling / MCP」这两块（对应我学的 Stage A）。规则如下：
>
> 1. 一次只问一道题，等我答完再点评，不要把答案和下一题一起抛出来。
> 2. 每道主问后追问两层，第二层要针对我上一句的漏洞往深里挖（比如我说「4090 推理划算」，你就追问「那训练为什么不行，具体卡在哪个指标」）。
> 3. 覆盖这些必考点：Token 计费与成本控制、API-Key 安全、OpenAI 兼容格式、在线 API 与本地部署取舍、显存估算与选卡、Ollama 与 vLLM 选型、量化代价、Agent 与聊天机器人的范式区别、Function Calling 本质（模型是否执行函数）、tool_choice、ReAct 循环、MCP 三种传输选型。
> 4. 我答错或答含糊时，别直接给标准答案，先反问一句逼我自己修正；两轮还不对再给正解并指出我该回看哪个节点。
> 5. 我说「模拟结束」时，按「概念准确度 / 工程落地感 / 表达清晰度」三项各打一句评语，并列出我最该回看的 2 个节点。
>
> 现在从第一题开始。

**自评触发句：** 如果连续两题被追问到第二层就卡壳，停下回看对应节点再来；能扛住两层追问并主动点破课件与一手来源的细微差异（例如 DeepSeek-R1 在 API 上的功能限制），才算这一节过关。
